# 재무자료 일괄 업데이트 설계 논의

2026-11-12 설계 인터뷰 기록이다. 아래 합의는 구현 전 설계이며, 현재 동작과 구분한다. 원본 기능 규칙은 [spec #155](https://github.com/Soochol/vallythevally/issues/155)의 후속 변경 절에 반영했다. 이 문서는 인터뷰와 발행 이력을 보존하며, 구현 규칙은 spec을 따른다.

상태: Q1~Q10의 추천안과 `to-spec` 검증 경계·`to-tickets`의 5개 작업 및 선행 관계를 사용자가 승인했다. 기존 spec #155의 규칙 12·수집 완료 기준을 갱신하고 후속 변경을 추가했으며, 추가 작업을 위해 spec을 다시 열었다. 하위 작업 #227~#231의 본문·라벨·상위 spec·실제 blocked-by 관계를 재조회로 확인했다. 이후 `implement` 요청으로 첫 작업 #227의 증분 갱신·일관된 표시·실패 복구를 구현하고 합의한 경계에서 검증한다. #228의 전 회사 최근 자료·공통 창·저장 조회 분리에 이어 #229에서 과거 이어받기와 영속 일시정지를 구현한다. #230에서 인증·한도 영속 정지와 단일 확인 후 명시적 재개를 구현한다. 자동 일정은 #231에 남아 있으며 이 문서의 전체 기능을 구현 완료로 뜻하지 않는다.

## 현재 동작

- DART 재무 원자료는 사용자 자료 DB와 별개인 SQLite `financials.db`에 회사별로 저장한다.
- 재무지표를 처음 사용하는 종목을 수집하고, 이후 접근 시 일일 공시 확인이나 미완료 작업을 시작한다. 차트에는 종목별 수동 갱신 기능이 있다.
- 현재 수동 갱신은 공시 목록이 그대로여도 해당 회사의 전체 보고서·배당 요청을 다시 받는다. 일일 확인에서 공시 목록이 바뀌어도 회사 전체를 다시 받는다.
- 기존 spec은 전 종목 선수집을 하지 않는다고 정했다. 이번 논의는 이 범위와 수집 시작 조건을 바꾼다.
- 스크리너는 [ADR 0010](adr/0010-screener-reads-a-disk-daily-store.md)에 따라 KRX 일봉을 DuckDB에 저장한다.
- 키움의 PER·PBR 등 종목 기본 정보는 DART 재무지표와 별개이며, 현재 재무 SQLite에 저장하지 않는다.

현재 재무 수집 계약은 [DART 재무 원자료 수집](dart-financial-source.md), 계산·조회 계약은 [보고기간별 재무지표 API](financial-indicators-api.md)를 따른다.

## 합의한 방향

첫 라운드의 세 추천안에 대한 사용자 동의로 다음을 기록한다.

- 대상은 분기·연간 매출액, 영업이익, 지배주주 ROE, 투자 현금흐름, DPS, 부채비율이다. 키움 종목 기본 정보의 저장 정책은 이번 범위에 포함하지 않는다.
- 차트에서 열어 본 종목에 한정하지 않고 코스피·코스닥의 재무자료 지원 회사 전체를 미리 수집한다.
- 차트 조회는 저장 자료만 읽는다. 외부 원천 호출은 별도 업데이트 작업에서 수행하고, 저장 자료가 없으면 미수집 상태를 표시한다.
- 일괄 업데이트를 한곳에서 시작하고 진행 상황을 확인할 수 있게 한다.
- Q4에서 추천안을 선택했다. 재무 원자료는 기존의 독립 SQLite 저장소를 유지하며, 이번 작업은 일괄 수집·저장·차트 표시까지로 한다. 재무지표를 이용한 스크리너 조건 검색은 후속 범위로 분리한다.
- Q5에서 2015년 이후 가능한 전체 이력을 수집하기로 했다. 모든 회사의 최근 3개 사업연도(올해 포함)를 먼저 채운 뒤 오래된 자료를 이어 받는다.
- Q6에서 수동 업데이트와 매일 오전 7시(KST)의 자동 업데이트를 함께 제공하기로 했다. 새 공시·정정을 확인해 필요한 자료를 갱신하며, 서버가 꺼져 놓친 확인은 다음 기동 때 수행한다. 차트 조회는 업데이트를 시작하지 않는다.
- Q7에서 일부 회사·보고서의 조회 실패는 나머지 수집을 막지 않기로 했다. 마지막 성공 자료와 진행 지점을 보존하고 실패·미수집 상태를 표시하며, 중단 후 이어 받는다. 인증 오류·호출 한도처럼 전체에 영향을 주는 문제는 작업을 일시 중지한다.
- Q8에서 수동 업데이트도 새 공시·정정·누락·실패한 자료만 받기로 했다. 변경 없는 정상 자료는 재사용하고, 반복 요청은 진행 중인 작업 하나로 합친다.
- Q9에서 차트·스크리너의 공통 상단에 `재무자료` 버튼을 두기로 했다. 데스크톱과 모바일에서 공용 업데이트 창을 열 수 있으며, 차트의 재무 상태에서도 같은 창으로 연결한다. 창에는 최근 자료·과거 자료 수집 단계, 완료 회사 수, 실패 목록, 마지막·다음 확인 시각과 시작·일시정지·재개를 제공한다.
- Q10에서 사용자 일시정지는 서버 재시작·자동 확인 시각에도 유지하고 명시적으로 재개하기로 했다. 인증 오류도 설정 수정 후 명시적으로 재개한다. 호출 한도는 다음 자동 확인 시각에 요청 하나로 확인해 성공하면 이어 받고, 계속 제한되면 대기한다.

용어는 `GLOSSARY.md`의 재무자료·재무자료 업데이트·재무지표·보고기간 정의를 따른다. 보고기간 배치·최신 정정 반영·연결 우선 규칙은 [ADR 0011](adr/0011-financial-indicators-use-reporting-periods.md), 조회와 업데이트 분리는 [ADR 0015](adr/0015-financial-charts-read-collected-data.md)를 따른다.

## 운영 규칙

- 저장 자료만 읽는 계약은 차트와 원자료·계산 결과 GET에 적용한다. 진행 상태를 반복 조회해도 외부 원천 호출을 시작하지 않는다.
- 같은 회사의 여러 주식 종류가 확인된 경우 회사 재무는 공유한다. 기존 회사 매핑과 주식 종류별 배당 검증 규칙을 유지하며 미확인을 추측으로 채우지 않는다.
- 가능한 전체 이력은 2015년 이후 각 회사에 실제 존재하고 지원되는 보고기간을 뜻한다. 아직 공시되지 않은 기간·공시 없음·매핑 미확인·수집 실패·미수집을 구분하고, 금액이 없다고 0을 넣지 않는다.
- 최근 자료를 채우는 동안 관련 계산에 필요한 앞선 보고기간의 입력도 확보한다. 과거 자료를 이어 받는 중 새 일일 확인이 도래하면 최신 공시 확인과 영향을 받는 자료를 먼저 처리하고 과거 채우기를 계속한다.
- 기존 자료와 성공 시각은 실제로 해당 자료를 다시 받아 저장한 경우에만 바뀐다. 목록 확인 시각, 현재 단계의 완료 회사 수, 전체 과거 이력 완료 여부를 구분해 표시한다.
- 한 작업의 수동·자동 시작 요청은 합친다. 서버가 오래 꺼져 있었어도 놓친 날짜마다 중복 작업을 만들지 않고 한 번의 이어받기와 미확인 구간 확인으로 처리한다.
- 사용자가 일시정지하면 새 요청을 배정하지 않고 진행 중 요청의 결과를 저장한 뒤 멈춘다. 정지 의도와 사유·진행 지점은 재시작 후에도 유지한다.
- 호출 한도의 다음 자동 확인은 한국 시각 기준 다음 오전 7시다. 한도 해제를 보장하는 시각으로 간주하지 않으며 확인 요청이 계속 제한되면 작업 전체를 재개하지 않는다. 사용자 재개도 확인 요청과 기존 전송 간격을 따른다.
- 재시도 가능한 개별 통신·원자료 오류는 간격과 횟수를 제한해 재시도하며, 실패 한 건이 나머지 회사의 진행을 막지 않는다. 디스크 저장 실패는 진행을 저장했다고 처리하지 않고 작업을 멈추며 기존 저장 자료를 유지한다.
- 기존 DART 전송 간격을 유지하고 전체 작업이 함께 제한을 따른다. API 키가 없는 상태에서는 설정 필요 상태를 표시하고 원천 호출을 반복하지 않는다.
- 재무자료 업데이트 창은 스크리너 KRX 일봉 업데이트와 별도 작업으로 표시한다. 스크리너의 DuckDB·업데이트 규칙은 변경하지 않는다.

## 완료 기준과 검증

자동 시험은 합성 DART·XBRL·KIND 응답과 fake-kiwoom, 작업 폴더 안의 임시 저장소만 사용한다. 실제 인증 API나 사용자 서버를 호출하지 않는다.

1. 첫 실행에서 대상 회사 전체를 계획하고 최근 3개 사업연도를 먼저 처리한 뒤 2015년 이후 과거를 채운다. 같은 회사가 중복 수집되지 않고 미지원·미확인 종목은 상태로 남는다.
2. 수집 전·중·후 및 서버 재시작 후 차트·원자료·재무지표·진행 GET을 반복해도 외부 호출이 증가하지 않는다. 기존 SQLite 자료를 재사용한다.
3. 수동 업데이트와 일일 확인에서 변경 없는 성공 보고서를 다시 받지 않는다. 새 공시, 과거 보고기간의 정정, 누락·실패한 자료만 처리하고 관련 Q4·현금흐름·ROE를 일관된 입력으로 다시 계산한다.
4. 갱신 중 관련 보고서 하나가 실패하면 마지막 일관된 성공 값을 유지하고 갱신 미완료 상태를 알린다. 서로 다른 정정 기준의 입력을 섞어 새 계산값을 내지 않는다.
5. 오전 7시, 시각 직전·직후 기동, 여러 날 꺼진 뒤 기동, 진행 중 중복 요청에서 예정 작업을 놓치거나 중복 생성하지 않는다. 사용자·인증 정지는 유지하고 호출 한도 정지는 정한 시각에 확인 요청 하나로 검사한다.
6. 처음부터 실패하는 경우와 도중에 실패하는 경우 모두 검사한다. 개별 회사 실패는 다른 회사를 막지 않고, 인증·호출 한도·저장 실패는 전체 작업을 멈추며 진행 지점과 마지막 성공 자료를 보존한다.
7. 일시정지·재개와 프로세스 재시작에서 완료 자료를 불필요하게 다시 받지 않는다. 저장하지 못한 결과를 완료로 표시하지 않는다.
8. 데스크톱·모바일의 공통 진입점과 차트 상태 진입점에서 같은 작업을 본다. 단계·완료 수·실패 목록·확인 시각·정지 사유·조작이 실제 서버 상태와 맞는다.
9. 가격 차트·스크리너·기존 회사 매핑·보고기간 검증·연결/별도 및 배당 규칙의 회귀가 없다.

각 작업의 변경 범위에 맞춰 다음 관리 명령으로 검증한다. 원본 spec과 작업 이슈의 완료 기준을 사용하며 전체 설계의 시험 통과와 개별 작업의 시험 통과를 구분한다.

```sh
python3 scripts/dev.py build
python3 scripts/dev.py cargo clippy -p server --all-targets -- -D warnings
python3 scripts/dev.py cargo test -p server
python3 scripts/web.py check
python3 scripts/web.py e2e e2e/financials.spec.ts
python3 scripts/web.py e2e e2e/financial-consistency.spec.ts
```

신규 전체 업데이트·자동 확인·일시정지/재개의 서버·웹 시험도 해당 명령의 검사 대상에 포함한다. 실행 준비와 산출물 확인은 [개발 빌드](development-builds.md)와 [웹 검사](web-checks.md)를 따른다.

## 발행한 작업 티켓

원본 spec #155의 수집 범위·시작 조건·완료 기준과 후속 변경 절에 이 결정을 반영하고 그 아래 작업 티켓으로 발행했다. `to-tickets`의 수직 기능 단위 규칙에 따라 기존의 계층별 3개 초안을 다음 5개로 구체화했다. 각 티켓은 기존 또는 새 UI→HTTP→원천·저장→표시·검증까지 확인할 수 있는 동작 하나를 마친다. 각 이슈에는 `ready-for-agent` 라벨, 실제 상위 이슈와 blocked-by 관계를 설정했다.

주 검증 경계는 기존 제품 HTTP API이며 가짜 원천·임시 SQLite·제어 가능한 서버 시계를 사용한다. UI는 기존 실제 앱 브라우저 E2E 경계를 사용한다. 새 전체 작업의 상태·조작 API도 같은 HTTP 경계 안에서 검증한다.

기존 [#204](https://github.com/Soochol/vallythevally/issues/204)의 회사별 재무 상태 점·팝오버 계획과 프론트엔드 티켓의 경계를 맞춘다. 재무지표로 검색하는 스크리너 조건은 이번 티켓들에 포함하지 않는다.

## 구현 검토 근거

현재 계산기는 여러 보고기간의 입력이 같은 갱신 세대인지 확인한다. 변경된 보고서만 다시 받는 정책을 택할 경우, 기존 입력의 검증 근거를 유지하면서 정정된 입력과 함께 계산 가능한 자료 묶음을 확정해야 한다. 세대 검사를 단순히 없애거나, 받지 않은 자료의 성공 시각을 갱신해 일치시키면 안 된다.

공시 확인은 최근 사업연도의 보고서만 확인해서는 오래된 보고기간의 정정을 놓칠 수 있다. [공식 공시검색](https://opendart.fss.or.kr/guide/detail.do?apiGrpCd=DS001&apiId=2019001)의 접수일·페이지 범위와 정정 전 공시 포함 옵션을 고려한다.

[공식 전체 재무제표 안내](https://opendart.fss.or.kr/guide/detail.do?apiGrpCd=DS003&apiId=2019020)의 요청 제한 오류는 `020`이며 제한 설정이 다를 수 있다. 모든 키에 같은 호출 한도가 적용되거나 특정 시각에 반드시 한도가 풀린다고 가정하지 않는다.
