# 데스크톱 앱이 개인 엔진을 돌리고, 공용 서버는 로그인과 공용 자료만 맡는다

[ADR 0038](0038-user-kiwoom-keys-stay-in-the-browser-and-collection-runs-on-one-server.md)과 [ADR 0041](0041-browser-keys-are-locked-by-default-and-the-kiwoom-engine-runs-in-the-browser-as-wasm.md)은 사용자 키를 브라우저에만 두고 브라우저가 증권사를 직접 부르게 했다. 사용자가 그리는 최종 모습은 사용자 N명이 각자 N개 증권사를 쓰는 시스템이다. 한투는 브라우저에서 직접 부를 수 없다. REST는 preflight에 501을 주고 CORS 허용 헤더가 없으며, 실시간은 평문 `ws://`라 https 페이지에서 mixed content로 막힌다(조사일 2026-11-22). 다른 증권사도 브라우저 직접 호출을 보장하지 않으므로 그 방향은 N개 증권사로 넓힐 수 없다. 사용자가 정했다(2026-11-23). 플랜은 [`docs/plans/desktop-app.md`](../plans/desktop-app.md)다. 사용자는 설계에서 성능을 가장 중요하게 본다.

## 정한 것

- **최종 배포물은 데스크톱 앱이다.** 앱은 화면(`web/`)과 Rust **개인 엔진**으로 이뤄진다. 개인 엔진은 사용자 키로 증권사에 직접 연결하고 시세 캐시, 실시간, 계좌, 주문을 맡는다. 키는 사용자 PC 밖으로 나가지 않는다.
- **공용 서버가 맡는 일**: 로그인, 계정별 셋업([ADR 0024](0024-setup-storage-and-sync.md)), 공용 자료(수집 데몬이 만든 순위, 시장 개요, 30초 스냅샷, 히트맵, 분봉. [ADR 0043](0043-collector-makes-shared-data-and-the-server-only-reads-it.md)). **맡지 않는 일**: 사용자 키를 받는 것, 사용자 키로 하는 모든 일.
- **웹 공개판은 운영하지 않는다.** 앱이 나오기 전에 브라우저로 쓰는 공개 서비스는 없다. 공개 리스너는 공용 서버의 입구로 남고 Funnel 운영 단계는 공용 서버용으로만 한다.
- **껍데기는 Tauri 2다.** 첫 지원 OS는 Windows 10/11 x64이고 macOS는 그 다음이다. Linux는 개발용으로만 빌드하고 배포하지 않는다. 첫 지원 증권사는 키움과 한투다. 세 번째 증권사는 조사 결과를 보고 정한다.
- **화면은 개인 엔진의 루프백 HTTP/WS만 부르고 껍데기 IPC에 기대지 않는다는 것을 기대값으로 둔다.** 지금 화면이 같은 출처의 `/api/*`와 `/api/ws`만 부르므로 화면 코드를 고치지 않아도 된다. 껍데기를 다시 고르는 비용도 창을 띄우는 부분으로 줄어든다. 엔진을 프로세스 안에 둘지와 IPC를 쓸지는 측정 뒤 `engine-split-design`이 확정한다.
- **앱 로그인은 [ADR 0023](0023-connector-and-account-server.md)의 루프백 흐름(RFC 8252, PKCE)과 커넥터 토큰을 다시 쓰는 것을 기대값으로 둔다.** 데스크톱 앱이 그 네이티브 앱이고 코드가 `crates/server/src/account/`에 남아 있다. 브라우저 세션 쿠키([ADR 0040](0040-the-public-listener-serves-browser-logins-and-shared-data-apart-from-the-operator-listener.md))는 앱에 필요 없다. 확정은 설계가 한다.

## 바꾸는 것

- **ADR 0038**: 사용자 키움 키와 그 키로 하는 셋(내가 보는 종목의 실시간, 계좌 실시간, 토큰·계좌 조회·주문)을 브라우저가 한다는 부분, 사용자는 웹 화면만 연다는 부분. 셋은 앱 안의 개인 엔진이 한다. 수집이 서버 한 곳에서 돈다는 부분은 그대로다.
- **ADR 0040**: 웹 공개판을 운영한다는 전제. 공개 리스너는 공용 서버의 입구로 남는다. 브라우저 세션 로그인과 공개 모드 화면은 앱 로그인 화면이 어떤 모양일지에 달려 있어 설계 뒤 후속 플랜이 정한다.
- **ADR 0041**: WASM 엔진, SharedWorker, Web Locks 방향은 거둔다. 엔진은 앱 안의 네이티브 Rust이고 지금 서버 코드를 쓴다. 키 보관은 OS 키체인 쪽으로 간다. 기대값은 키체인에 설치마다 자료 키 하나를 두고 키 목록 파일을 그 키로 암호화하는 것이다(Windows 자격 증명 관리자의 항목 크기 한도 2,560바이트를 피한다). 확정은 설계가 한다.
- **ADR 0023**: 커넥터가 앱 안의 개인 엔진으로 돌아온다. 사용자 키와 키로 하는 일이 다시 사용자 PC에 있다.
- **공용 자료 플랜의 U5**(미리 만들 수 없는 요청: 차트 과거 봉, 현재가·당일 요약, 기본 정보, 투자자, 체결·호가·프로그램 조회)는 개인 엔진이 사용자 키로 받는 쪽을 권한다. 사용자가 이 안을 골랐다. 수집 데몬이 요청을 받는 길은 만들지 않는다.
- 두 파일에 다는 개정 줄 중 ADR 0023·0041의 것은 이 변경이 단다. ADR 0038·0040의 개정 줄은 같은 시각 다른 작업이 두 파일을 고치므로 뒤 작업 `public-web-retire`가 단다.

## 껍데기 선택

| 축 | Tauri 2 | Electron |
|---|---|---|
| Windows 화면 엔진 | WebView2(Chromium) | 앱에 넣은 Chromium. 차트 성능은 같다 |
| macOS 화면 엔진 | WKWebView. Chromium과 다를 수 있다 | Chromium. 모든 OS에서 같다 |
| 설치 크기(추정) | 껍데기는 수 MB에 개인 엔진 크기를 더한다 | 약 80~150MB |
| 메모리(추정) | Node 프로세스가 없다 | Node 메인 프로세스가 더해진다. Windows에서는 차이가 작을 수 있어 잰다 |
| Rust 엔진 재사용 | 같은 언어 | 자식 프로세스나 napi. 런타임이 하나 더 있다 |
| 보안 기본값 | 기능 허용 목록 | `contextIsolation`·sandbox를 직접 맞춘다 |

첫 대상이 Windows이고 거기서는 화면 엔진이 같다. 남는 차이(크기, 메모리, 같은 언어)가 모두 Tauri 쪽이 낫다. 약점은 macOS의 WKWebView다. 맥을 지원할 때 측정 명령을 맥에서 돌려 판단한다.

## 성능

| 경로 | 지금 아는 것 | 확인 방법 |
|---|---|---|
| 앱 화면의 차트 그리기 | 추정: Windows WebView2는 Chromium이라 Chrome과 같다. 측정(ADR 0038): 체결 한 건 처리 4~11µs, 병목은 그리기 | `desktop-bench`가 같은 차트 부하의 프레임 시간을 Tauri 창과 Playwright Chromium에서 견준다. Windows 값은 Windows PC에서 같은 명령으로 잰다 |
| 개인 엔진 ↔ 화면 통신 | 추정: 루프백 WS가 병목일 가능성은 낮다 | `desktop-bench`가 합성 체결 흐름을 루프백 WS와 Tauri IPC로 보내 건당 지연 p50·p99와 화면 CPU를 잰다 |
| 공용 서버 부하(N명) | 추정: 앱 하나가 순위 10초, 보드 30초, 흐름·시장 개요 60초마다 받으면 사용자당 약 0.17건/초, 100명이면 약 17건/초이고 모두 메모리에서 읽어 준다 | `engine-split-design`이 창 간 중복 제거, 판 번호 조건부 요청(304), 밀어주기를 견준다. 실제 부하는 운영 단계에서 `GET /api/public-usage`로 본다 |
| 개인 엔진 자체 | 설계에서 확정: 공용 자료를 만들지 않으므로 일봉 저장소(DuckDB)가 필요 없다 | 설계 문서에 남는 모듈과 메모리 추정을 적는다 |

측정은 한 프로세스에 정한 부하만 건다. 위 표의 추정은 측정 전 값이고, 측정이 어긋나면 껍데기와 IPC 결정을 다시 본다.

## Considered Options

- **브라우저 직접(ADR 0038·0041의 방향)**: 한투를 부를 수 없다(위 근거, 조사일 2026-11-22). 키움만 되는 구조로는 N개 증권사를 지원하지 못한다.
- **운영 서버 중계**: 한투도 부를 수 있지만 사용자 키가 서버를 지난다. 키는 사용자 PC 밖으로 나가지 않는다는 조건을 깬다. 사용자 수에 비례해 서버 부하와 키 보관 책임도 는다.
- **Electron**: Windows에서 화면 엔진이 같아 성능 이득이 없고, 설치본이 크고 Node 런타임이 하나 더 있다. 오래 쓰여 업데이트·서명 도구가 성숙한 점과 macOS에서도 같은 엔진이라는 점이 장점이다. 화면이 루프백 HTTP/WS만 부르므로 나중에 바꾸는 비용은 작다.
- **브라우저 확장**: 확장이 증권사 호출을 중계할 수 있으나 확장 권한과 배포 심사, 실시간 연결 수명이 브라우저 정책에 묶인다. 개인 엔진의 Rust 코드를 그대로 쓰지 못한다.

## Consequences

- 앱을 쓰는 사용자는 사용자 PC에서 증권사에 직접 연결한다. 공용 서버는 키를 받지 않으므로 키 유출 면적이 서버에 생기지 않는다.
- 이미 들어온 브라우저 키 보관, 키 화면, 공개 리스너 CSP의 키움 출처는 쓰는 사람이 없다. 후속 작업 `public-web-retire`가 걷는다.
- 증권사 연결과 시세 코드를 개인 엔진으로 옮기는 구현은 다중 증권사 작업이 병합된 뒤 `engine-split-design`이 설계하고 후속 플랜이 나눈다.
- 증권사 키가 없어도 로그인하면 공용 자료 화면은 쓴다. 차트, 실시간, 주문은 키가 있어야 한다.
- 받아들일 한계: 개발 PC 측정은 Windows 값이 아니다. 첫 뼈대의 엔진은 지금 서버 전체이고 루프백 API는 같은 PC의 다른 프로그램에 열려 있다. 루프백 API 보호가 들어가기 전에는 앱에서 주문을 켜지 않는다.
