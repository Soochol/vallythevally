# 공개 리스너는 운영자 리스너와 따로 열려 브라우저 로그인과 공용 자료를 주고, 계정 기능은 라이브러리로 붙인다

[ADR 0038](0038-user-kiwoom-keys-stay-in-the-browser-and-collection-runs-on-one-server.md)에 따라 이 도구를 여러 사람이 웹 화면만 열어 쓰는 서비스로 연다. 공개 방법은 Tailscale Funnel이다(사용자가 정했다, 2026-11-22). 지금 코드로는 다음이 막는다.

- 로그인은 루프백 흐름뿐이다. 계정 서버가 일회용 코드를 `http://127.0.0.1:<포트>/auth/complete`로 보내고 커넥터가 그것을 커넥터 토큰으로 바꾼다. 원격 브라우저에서는 끝나지 않고, 계정 서버에는 브라우저 세션이 없다.
- `vally-server`에는 사람을 가리는 계층이 없다. 루프백이나 설정한 tailnet 이름([ADR 0036](0036-remote-access-goes-through-tailscale-serve-and-a-configured-tailnet-name.md))으로 오면 모든 라우트에 닿는다. 쓰기 가드는 Host·Origin·Content-Type 형식만 보고, 사용자 자료 `PUT`, 가드 밖 `POST` 아홉(스크리너 갱신·취소·실행, 순위, 재무 갱신·멈춤·다시 시작·소스·지표), `/api/ws`, 모든 읽기에는 걸리지 않는다.
- 같은 프로세스에 운영자의 실전 키와 주문 라우트가 있다. 그대로 Funnel로 열면 인터넷의 누구나 운영자 계좌에 닿는다.
- 응답에 CSP 같은 보안 헤더가 없고, 압축이 요청마다 brotli 기본 품질로 돈다.
- 사용자 자료는 한 사람의 로컬 SQLite 하나다. 히트맵 보드도 그 DB의 테마 하나를 읽는다.

이 ADR은 공개 서버의 뼈대를 정한다. 구현은 플랜 `docs/plans/browser-keys-funnel.md`의 작업들이 한다. 브라우저 키 보호와 엔진 방향은 [ADR 0041](0041-browser-keys-are-locked-by-default-and-the-kiwoom-engine-runs-in-the-browser-as-wasm.md)이 다룬다. 스크리너 스냅샷을 비롯해 공용 자료를 수집 데몬이 만드는 설계는 다음 플랜 `collector-shared-data`의 ADR이 정한다.

## 정한 것

### 공개 서버 구조

- **리스너를 하나 더 둔다.** 공개 모드는 지금 `vally-server` 프로세스에 두 번째 리스너(공개 리스너)를 더해 받는다. `VALLY_PUBLIC_BIND`(루프백만)와 `VALLY_PUBLIC_ORIGIN`이 둘 다 있을 때만 뜨고, 없으면 지금과 똑같다. 기존 리스너는 **운영자 리스너**라고 부른다.
- **허용 목록으로 라우터를 만든다.** 공개 리스너에 넣는 것은 다음이다.
  - 화면 파일
  - `/v1`의 (메서드, 경로) 명시 목록: 브라우저 로그인 시작, callback, 세션 조회, 로그아웃, 계정 삭제
  - 서버 모드 조회
  - 공용 자료 읽기: 종목 목록·검색, 스크리너 실행·상태, ETF, 재무 읽기, 순위, 시장 개요, 히트맵 보드·흐름
  - 계정별 셋업
  - 수집 현황(운영자 계정만)
- **넣지 않는 것**: `/api/ws`, `/api/system/*`, `/api/trading/*`, 커넥터 계정 라우트, 셋업 내보내기·가져오기, 스크리너·재무 갱신 `POST`. 차트 봉, 현재가·당일 요약, 기본 정보, 투자자, 체결·호가·프로그램 조회는 `collector-shared-data`의 사용자 결정이 정해질 때까지 넣지 않는다. 읽기와 쓰기가 한 모듈에 섞인 스크리너·재무는 공개 모듈이 (메서드, 경로) 허용 목록으로 감싼다. 시험이 운영자 라우트 목록을 공개 리스너에 보내 모두 404인지 확인한다.
- **공개 입구는 공개 리스너만 연다.** Funnel은 노드와 포트 단위로 켜므로 운영자 리스너의 `tailscale serve`(tailnet 전용)는 그대로 두고 망 수준에서 인터넷에 닿지 않게 한다. 입구는 사용자가 플랜 승인 때 (가)안을 권장안으로 받아들였다. 실제 호스트 이름은 운영 단계 P0에서 정하고, 공개 전에 정해야 한다. 나중에 바꾸면 출처가 바뀌어 사용자들의 브라우저 키 보관소가 빈다. 코드는 `VALLY_PUBLIC_ORIGIN`만 보므로 어느 안이든 같다.
  - (가) 별도 노드의 443(아래 "공개 입구를 별도 호스트 이름으로 여는 안", 권장)
  - (나) 같은 호스트의 8443
- **계정 기능은 라이브러리로 붙인다.** `account-server` 크레이트를 라이브러리로 써서 공개 리스너 프로세스 안에 붙인다. `server`가 `account-server`에 의존하고 그 반대는 없다. 세션 확인이 함수 호출이 되고 ADR 0023의 의존 방향 규칙도 지켜진다. 별도 `vally-account` 실행과 커넥터 루프백 흐름은 지우지 않는다.
- **Host와 Origin.** 공개 리스너는 모든 요청의 Host가 `VALLY_PUBLIC_ORIGIN`의 호스트(포트 포함)와 정확히 같은지 확인한다. Origin이 있으면 그 출처와 같아야 한다. `GET`·`HEAD`·`OPTIONS`가 아닌 요청은 Origin이 반드시 있어야 하고 본문은 `Content-Type: application/json`이어야 한다. 인터넷에 열리면 읽기도 보호 대상이다. Funnel이 Host를 어떤 모양으로 넘기는지는 운영 단계에서 확인한다.
- **세션 문.** 공개 리스너의 `/api/*`는 서버 모드 조회를 빼고 모두 세션이 있어야 한다. 세션이 없으면 `401`이고 본문은 지금 오류 모양 그대로 `{"error":{"code":"signed_out","message":…}}`이다. `ApiErrorCode`에 값 하나를 더하는 최소 변경을 한다. 웹의 오류 해석이 이 모양만 읽는다. 화면 파일과 로그인 시작은 세션 없이 받는다.
- **공개 모듈 위치.** 설정 해석과 공개 쪽 장치는 `crates/server/src/public/` 안에 둔다. 다른 탭의 다중 증권사 플랜이 같은 서버 파일(`http.rs`, `app.rs`, `config.rs`, `main.rs`, `lib.rs`, `api.rs`)을 다시 짜고 있어서, 이 파일들에는 몇 줄 더하는 최소 변경만 한다. 순위·시장 개요·ETF 모듈은 그 모듈의 `routes()`를 그대로 붙이고 고치지 않는다. 캐시, 쪽 수 제한, 예산은 공개 모듈이 감싸서 건다.
- **로컬 전용 모드와 커넥터 계정 모드는 이번에 바꾸지 않는다.** 예외는 셋이다. 압축 품질, 운영자 리스너의 출처 검사, 운영자 쪽 응답 시간 계수. 웹은 서버 모드 조회로 공개 모드인지 안다. 같은 화면 빌드가 두 리스너에서 돈다.

### 로그인과 세션

- **로그인 흐름.** 화면이 로그인 시작으로 최상위 이동한다 → 계정 서버 코드가 `state`·`nonce`와 기존 로그인 흐름 쿠키를 두고 IdP로 보낸다 → 같은 callback으로 돌아온다 → 계정을 찾거나 만들고 세션 쿠키를 둔 뒤 공개 출처의 `/`로 302한다. 돌아갈 곳은 늘 `/`이고 질의로 받지 않으므로 열린 리다이렉트가 구조로 없다. 실패하면 `/?login=error&reason=<cancelled|idp_failed|account_limit|blocked>`로 보낸다. callback이 커넥터 흐름과 같으므로 IdP에는 하나만 등록한다. IdP는 Google과 Naver, 계정 식별 `(provider, subject)`, 셋업 범위는 ADR 0023 그대로다.
- **세션 쿠키.** 이름은 `__Host-vally_session`이고 `HttpOnly; Secure; SameSite=Lax; Path=/`를 붙인다. 값은 32바이트 난수이고 DB에는 SHA-256만 둔다. 30일 동안 쓰지 않거나 만든 지 90일이 지나면 만료한다. 마지막 사용 시각은 한 시간 넘게 지났을 때만 다시 쓴다. 절대 수명이 없으면 훔친 쿠키가 계속 살고, 요청마다 쓰면 SQLite 쓰기가 몰린다. `__Host-` 접두는 같은 tailnet의 다른 노드가 `Domain=` 쿠키로 덮어쓰지 못하게 한다.
- **로그아웃과 계정 삭제.** 로그아웃(`POST`)과 계정 삭제(`DELETE /v1/account`)는 세션 확인과 Host·Origin·JSON 검사를 거친다. 계정 삭제는 identity, 세션, 커넥터 토큰, 셋업을 모두 지우고 세션을 폐기한다. 브라우저의 키는 서버가 모르므로 지우기는 화면이 따로 권한다.
- **가입 상한과 차단.** 새 계정 수 상한은 설정이고 기본은 100이다. 차면 새 가입을 거절하고 기존 계정의 로그인은 받는다. 차단 계정 목록 `VALLY_PUBLIC_BLOCKED_ACCOUNTS`(`provider:subject`를 쉼표로 이어 적는다)의 계정은 세션 확인에서 401이고 로그인도 거절된다. 목록을 바꾼 뒤 재시작하면 적용된다. 가입이 찬 뒤 악성 계정을 끊을 수단이 없으면 Funnel 전체를 끄는 것밖에 남지 않는다. 차단할 계정은 요청 수 상위 계정 목록에서 찾는다.
- **수집 현황 판정.** 공개 리스너의 `/api/collector/*`는 요청한 세션의 계정이 `VALLY_COLLECTOR_ADMINS`에 있어야 보인다. 운영자 리스너의 판정은 그대로다. 지금 판정은 서버에 저장된 커넥터 계정으로 하므로, 공개하면 누구나 같은 판정을 받게 된다.

### 요청 제한과 한도 설정

- **계정 단위로 센다.** 계정마다 토큰 버킷 하나를 두고 같은 계정의 세션 여럿이 한 버킷을 쓴다. 세션 단위로 세면 세션을 여러 개 만들어 한도를 늘릴 수 있다. 메모리만 읽는 경로(종목 하나 조회, 종목 검색, 스크리너 상태, 서버 모드)는 한 번에 0.1을 쓴다. 지도 화면이 종목마다 `/api/symbols/{code}`를 부르므로, 가중치가 없으면 종목이 100개를 넘을 때 한 사람이 혼자 429를 맞는다.
- **전체 버킷과 익명 버킷.** 로그인한 요청 전체에 버킷 하나, 익명 요청에 따로 버킷 하나를 둔다. 익명 요청은 화면 파일을 빼고 로그인 시작, callback, 세션 조회, 401 응답이다. 익명 요청을 계정 한도 밖에 두면 익명 요청만으로 전체 자원을 채울 수 있기 때문이다. 로그인 시작에는 버킷이 하나 더 있고 기존 대기 로그인 한도도 그대로다.
- **초과 응답.** 넘으면 `429`와 `Retry-After`를 내고 본문 `error.retryAt`에 다시 시도할 시각을 싣는다. 웹은 `Retry-After` 헤더가 아니라 본문의 `retryAt`만 읽는다. 시계는 주입한다.
- **IP별 제한은 하지 않는다.** Funnel이 클라이언트 IP를 넘기는지 확인하지 않았고, 확인하지 않은 헤더를 믿으면 위조된다. 이 때문에 로그인 시작 버킷을 한 사람이 다 써서 그동안 다른 사람이 로그인을 시작하지 못할 수 있다. 확인하지 않은 헤더를 믿는 것보다는 전체 버킷이 막히는 쪽이 낫다고 보고 받아들인다. 대기 로그인 한도(기본 10,000)는 분당 30으로는 차지 않는다. 운영 단계에서 Funnel이 IP를 넘기는지 확인한 뒤 IP별 버킷으로 고친다.
- **모든 한도는 설정(env)이다.** 다시 빌드하지 않고 바꾼다. 이름과 기본값은 `docs/public-operations.md`의 한 표에 둔다. 설정 해석은 `crates/server/src/public/` 안에 두고 `config.rs`에는 부르는 몇 줄만 더한다. 기본값은 첫 값이고 바꿀 근거는 아래 계수가 남긴다.
- **조정 근거를 센다.** 지금 대기열 사용량에는 운영자 화면과 샘플러의 호출이 섞여 있으므로 공개 요청이 직접 낸 TR 수와 운영자 쪽 지연을 따로 센다.
  1. 경로 묶음별 응답 수, `429`와 `503` 횟수, 동시 한도에서 기다린 시간(합계와 최대), 공개 요청이 직접 낸 TR 수. 흐름·보드·순위·시장 개요는 공개 경로가 TR 예산을 쓰므로 정확히 세고, 나머지는 대기열 사용량으로 추정한다.
  2. 캐시 적중: 보드, 흐름, 시장 개요 응답 캐시, 스크리너 상태 캐시. 스크리너 결과 재사용은 `collector-shared-data`가 센다.
  3. 운영자 리스너의 키움 경로 응답 시간(분마다 p50과 최대).
  4. 요청 수 상위 계정 10개.
  이 값들은 운영자 리스너 전용 `GET /api/public-usage`와 분 단위 로그 한 줄로 낸다.

### 공용 자료를 여러 사용자에게 줄 때의 부담

같은 TR을 부르는 요청은 키움 대기열에서 TR마다 초당 5회([ADR 0035](0035-kiwoom-queue-counts-each-tr-per-second.md)), 같은 우선순위 단계 안에서는 들어온 순서대로 나간다. 공개 요청도 운영자 화면과 같은 `Priority::Screen` 단계로 나간다. 그래서 공개 요청이 같은 TR을 N회 쌓아 두면 운영자 화면의 같은 TR 요청은 최대 N/5초 늦어진다. 아래 한도는 이 N을 묶는 데 목적이 있다. 요청 하나가 부르는 TR 수는 다음과 같다(`c795199b` 기준).

| 요청 | TR 호출 | 지금 캐시 |
|---|---|---|
| 시장 개요 `index` | `ka20003` 1회 | 없음 |
| `/sectors`, `/turnover`, `/streaks` | 각 1~2회 | 없음 |
| `/flow?period=P` | 웜 3회, 콜드 최대 P+2회(60일 약 62회, 약 12초) | 투자자 일 캐시뿐 |
| 시장 개요 `flow/intraday` | 샘플러가 받음 | 샘플러 |
| `/api/rankings` | 쪽 수 p회(최대 30) | 8초, single-flight. 웹은 10초마다 p쪽 전부 다시 받음 |
| `/api/heatmap/board` | ⌈오래된 종목/100⌉회 `ka10095`(최대 60) | 종목별 45초, 미스 합류 없음 |
| `/api/heatmap/flow` | 오래된 종목마다 `ka10080` 1회 이상(최대 60, `join_all`) | 종목별 45초. 웹은 60초마다 다시 받아 매 갱신이 전부 미스 |
| `/api/screener/run` | `ka10095` 40회. 같은 대상·기준의 진행 중 수집이 있으면 합류해 0회 | 없음 |
| `/api/symbols/{code}`, 스크리너 상태 | 0회(메모리·DuckDB) | — |

- **계정별 셋업과 히트맵 보드.** 공개 리스너의 사용자 자료 라우트(관심종목, 조건식, 히트맵 테마, 화면 상태, 레이아웃, 드로잉)는 지금과 같은 경로, 같은 JSON으로 받는다. 저장은 계정 서버 저장소의 그 계정 셋업 문서에 한다. revision 규칙, 삭제 표시, 크기 한도는 ADR 0024와 `crates/setup` 그대로다. 히트맵 보드와 흐름은 세션 계정의 히트맵 테마 문서를 쓴다. 보드는 그 문서의 테마로 계산하고, 흐름의 `symbols`는 그 문서에 있는 종목만 받으며 없는 종목은 `over_limit`처럼 응답에 따로 돌려준다. 보드가 운영자 DB의 테마를 읽으면 모든 사용자가 운영자 테마를 보고, 흐름이 임의의 종목 60개를 받으면 종목 조합을 바꿔 캐시를 피하며 키움 슬롯을 독점할 수 있기 때문이다. 테마로 묶으면 계정이 부를 수 있는 종목이 테마 저장 한도(100×60) 안으로 정해진다. 두 모듈에는 공개 경로가 쓸 진입 함수 하나씩을 더하는 최소 변경만 한다.
- **운영자 키 호출 보호(임시 장치).** 공개 부하가 운영자 화면의 같은 TR 요청을 늦추는 크기에 계산한 상한을 둔다. 요청 수로 묶으면 한 요청이 TR을 0~62회 부르므로 보호가 되지 않고, 묶음을 나누지 않으면 무거운 흐름 하나 때문에 가벼운 시장 개요 카드까지 모두 503이 되며, 계정당 동시 한도가 없으면 한 계정이 슬롯을 독점한다. 장치는 아홉이다.
  1. **경로 묶음별 동시 한도.** 시장 개요 4, 순위 2, 보드 1, 흐름 1. 따로 계정당 키움 경로 동시 1. 자리가 없으면 기다리지 않고 바로 `503`과 `retryAt`을 낸다. 보드·흐름·시장 개요는 키움을 실제로 부를 때만 자리를 잡고, 캐시 적중만으로 끝나는 요청은 자리를 쓰지 않는다. 순위는 모듈 안의 캐시를 밖에서 알 수 없으므로 늘 자리를 잡는다.
  2. **TR 예산은 요청 수가 아니라 TR 수로 센다.** 흐름과 보드의 공개 진입 함수가 캐시에 없는 종목을 받을 때마다 TR 하나를 뺀다. 흐름은 종목 하나, 보드는 100종목 묶음 하나가 TR 하나다. 예산이 없으면 그 종목을 `missing`으로 돌린다. 흐름 예산은 전체 분당 60, 계정당 분당 60이고 보드 예산은 45초 창당 전체 45다.
  3. **흐름은 요청 안에서 동시에 5종목까지만 받는다.** 지금은 `join_all`로 60개를 한꺼번에 받는다.
  4. **흐름 캐시를 분에 맞춘다.** 공개 경로에서는 같은 KST 분에 받은 값을 유효로 본다. 공개 모드 웹은 흐름을 분이 바뀐 뒤 2~10초 사이의 무작위 시각에 다시 받는다. 서버 캐시 45초가 웹 갱신 60초보다 짧아 매 갱신이 전부 미스였는데, 분 단위로 맞추면 공개 사용자 수와 상관없이 종목마다 분당 1회로 준다. 운영자 경로의 45초 규칙은 그대로다.
  5. **시장 개요 카드 응답을 캐시한다.** 공개 모듈이 질의 단위로 15초 동안 캐시한다.
  6. **순위는 공개 리스너에서 5쪽까지만 받는다.** 더 많이 요청해도 5쪽으로 줄이고, 공개 모드 웹은 5쪽만 요청한다.
  7. **공개 경로가 키움 오류 `Gated`나 한도 대기를 받으면** 기다리지 않고 바로 짧은 `retryAt`과 `503`을 낸다. `Gated`가 대기열 공용 관문을 통해 운영자 조회로 번지는 것은 이 단계에서 구조로 막지 못하므로, 공개 쪽이 바로 물러나게 하고 남는 한계로 적는다.
  8. **공개 오류 본문은 고정 문구다.** 키움 오류의 원문, 포털 IP 등록 안내, 토큰 파일 오류, `manualActionRequired`를 싣지 않는다.
  9. **계산한 상한.** 운영자 화면의 같은 TR 요청이 공개 부하 때문에 더 기다리는 시간은 (그 TR을 부르는 공개 묶음의 동시 한도 × 공개 요청 하나가 그 TR을 동시에 쌓는 최대 수) ÷ 5초다. 흐름 `ka10080`은 1×5÷5 = 1초, 보드 `ka10095`는 1×1÷5 = 0.2초, 순위는 2×5÷5 = 2초, 시장 개요는 웜에서 4×3÷5 = 2.4초다. 시장 개요 `flow`의 하루 첫 콜드(기간마다 최대 약 62회)는 응답 캐시와 투자자 일 캐시가 차기 전 한 번뿐이고, 그 한 번은 최대 약 12초까지 늘 수 있다. 이것은 받아들일 한계로 둔다. 실제 값은 시험이 합성 transport와 가짜 시계로 단정한다.
- **스크리너 동시 실행.** 공개 리스너의 `/api/screener/run`에 동시 4(판정 CPU용, 자리가 없으면 바로 503), 계정당 분당 2회, 공개 전체 분당 3회를 둔다. 스크리너 상태는 공개 모듈이 2초 동안 공용으로 캐시한다. 지금 실행은 매번 전 종목의 오늘 시세를 받는다(약 3,960종목, `ka10095` 약 40회). 동시 실행은 같은 대상·기준의 수집 하나에 합류하므로 동시 한도로는 TR이 줄지 않고, 비용은 이어지는 실행이다. 그래서 TR은 분당 실행 수로 묶고 동시 한도는 판정 CPU와 DuckDB 잠금만 지킨다. 이 한도는 임시이고 스크리너 스냅샷 플랜(`collector-shared-data`)이 푼다. 스냅샷 자체의 ADR은 그 플랜이 쓴다.
- **Funnel 대역폭: 압축과 화면 파일.** 1.4MB JS를 brotli 기본 품질로 압축하는 데 1.50초가 걸렸고 품질 4는 24ms였다. 576KB 보드 응답은 0.58초였다. 이 압축은 운영자 리스너와 같은 tokio 작업 스레드에서 돈다.
  1. 두 리스너 모두 실시간 압축 품질을 4로 낮춘다. 이미 압축된 형식(`font/woff2`, `image/*`, `application/zip` 등)은 압축하지 않는다. 운영자 리스너 쪽 변경은 `http.rs` 한 줄이다.
  2. 공개 리스너는 화면 파일을 시작 때 한 번 읽어 메모리에 둔다. br(품질 11)과 gzip 사본도 시작 때 블로킹 스레드에서 만들고 `ETag`와 `304`로 답한다.
  3. e2e가 첫 로딩 바이트 수를 기록한다. 운영 단계에서는 Funnel 너머의 첫 로딩 시간과 보드 응답 시간을 잰다.
  4. 빌드 때 미리 압축하는 것과 JS 번들 나누기는 하지 않는다. 시작 때 압축이 같은 효과를 내고 번들 나누기는 화면 작업이다.
  실시간은 브라우저와 키움 사이에서 바로 오가고 Funnel을 거치지 않는다.

### 한 프로세스의 위험과 격리 장치

공개 리스너와 운영자 리스너가 같은 프로세스에 있고 그 프로세스에는 운영자 실전 키와 주문 라우트가 있다. 허용 목록은 라우트를 나눌 뿐이다. 그 밖의 실패(공유 처리 코드의 실수, panic, 자원 고갈)는 인터넷에서 운영자 화면이나 계좌에 닿을 수 있다. 이것을 **알려진 위험**으로 둔다. 지금 빌드는 `panic = "abort"`가 아니므로 요청 처리 중 panic은 그 연결 작업만 끝낸다. 그러나 공개 요청이 쥔 `std::sync::Mutex`가 오염되면 운영자 처리도 실패한다. 같은 프로세스에서는 이것을 구조로 막지 못한다. 첫 단계에서 줄이는 장치는 다음이다.

1. 공개 라우터 전체를 `CatchPanicLayer`로 감싼다.
2. 동시 처리 상한을 둔다. 전체 64, 계정당 8, 익명 16이고 화면 파일은 세지 않는다. 넘으면 기다리지 않고 바로 `503`과 `retryAt`을 낸다.
3. 요청 시간 상한은 60초다. 콜드 60일 흐름이 12초를 넘을 수 있다.
4. 키움 경로와 스크리너는 위 한도를 받는다.
5. 공개 리스너는 운영자 SQLite(`data/vally.db`)를 쓰지 않는다.

DuckDB 읽기 연결은 `try_clone`으로 만들어 수의 한도가 없고 병목은 `Mutex<Connection>` 하나다. 그래서 연결 수가 아니라 실행 수와 상태 캐시로 묶는다.

### 운영자 리스너의 출처 검사

지금 `/api/ws`와 읽기에는 Origin 검사도 Host 검사도 없다. Origin 비교만 하면 `no-cors` `GET`과 `<img>`(Origin을 붙이지 않음), DNS rebinding(Host가 Origin과 같음)이 통과한다. `ts.net`은 Public Suffix List에 있어서 같은 tailnet의 노드끼리, 같은 호스트의 다른 포트끼리는 **같은 사이트**다. 그러니 `same-site`도 거절해야 한다. 그래서 운영자 리스너의 모든 메서드와 `/api/ws` 업그레이드에 다음 셋을 건다.

1. Host 검사(`check_host`, 지금 쓰기 가드의 규칙).
2. Origin이 있는데 자기 출처가 아니면 거절한다.
3. `Sec-Fetch-Site`가 `cross-site`나 `same-site`이면 `/api/*`를 거절한다. `same-origin`, `none`, 헤더 없음은 받는다.

층 하나를 더하는 최소 변경으로 하고 `ws.rs`는 고치지 않는다. Vite 개발 프록시에는 `changeOrigin`이 없어서 Host 검사가 `vite dev`의 `/api/ws`를 깰 수 있다. 개발 흐름(`vite dev` 프록시, `scripts/web.py live`)이 깨지면 프록시 쪽을 고친다.

### 쿠키와 출처 공유 분석

같은 호스트의 443과 8443일 때다.

1. **쿠키.** 쿠키는 포트로 나뉘지 않으므로 공개 세션 쿠키도 운영자 리스너로 가는 요청에 실린다. 운영자 리스너는 쿠키를 읽지도 두지도 않으므로 지금은 해가 없다. 운영자 리스너가 나중에 쿠키 인증을 쓰면 섞이므로, 그때는 별도 호스트 이름 안이 필요하다.
2. **같은 사이트.** 같은 호스트의 두 포트도, 같은 tailnet의 두 노드도 같은 사이트다. 그러므로 `SameSite=Lax`는 공개 화면에서 운영자로 가는 요청을 막지 않는다. 막는 것은 출처 검사다.
3. **공개 화면의 스크립트(XSS 등)가 운영자 리스너로 요청하는 경우.** 운영자가 tailnet 기기로 공개 화면을 열었을 때만 생긴다. 운영자 PC의 브라우저에서 연 임의의 외부 사이트도 같은 길로 요청할 수 있다.
   - **쓰기**: 쓰기 가드는 Origin을 비교하므로 막는다. 가드 밖 `PUT`과 JSON 본문은 preflight를 부르고 운영자 리스너에는 CORS 응답이 없으므로 브라우저가 보내지 않는다. 그러나 단순 `POST`는 preflight 없이 가고, `POST /api/financial-update`는 본문이 없어도 전 종목 DART 갱신을 시작한다. 운영자 리스너의 출처 검사 (2)·(3)이 막는다.
   - **읽기**: CORS가 없으므로 응답은 읽히지 않는다. 그러나 요청은 가므로 키움 `GET`이 운영자 키 한도를 쓴다. Origin을 붙이는 요청은 (2)가, Origin이 없는 `no-cors` 요청은 `Sec-Fetch-Site`를 보내는 브라우저에서 (3)이 막는다. 그 헤더를 보내지 않는 오래된 브라우저의 `no-cors` `GET`은 남는다.
   - **`/api/ws`**: WebSocket에는 CORS가 없어서 운영자 실시간 시세, 연결 상태, 계좌 변경 알림을 읽을 수 있다. 첫 단계에서 반드시 막을 구멍이다. 브라우저는 WebSocket에 늘 Origin을 붙이므로 (2)가 막는다.
   - **DNS rebinding**: Host가 공격자 이름이 되므로 (1)이 막는다.
4. **운영자 화면의 스크립트가 공개 리스너로 요청하는 경우.** 공개 리스너는 모든 요청의 Host와 Origin을 정확히 비교하고 CORS 응답이 없으므로 막힌다.

### 공개 입구를 별도 호스트 이름으로 여는 안

호스트가 다르면 host-only 쿠키를 서로 보내지 않고 출처도 이름으로 나뉜다. 운영자 노드에는 Funnel을 켤 권한 자체가 없다. 공개 주소에 포트가 붙지 않는다. 다만 `ts.net`이 공개 접미사라서 두 노드는 여전히 같은 사이트이고, `SameSite`와 `Sec-Fetch-Site` 수준에서는 분리되지 않는다. 그 부분은 운영자 리스너의 출처 검사가 막는다. `tsnet`은 Go 라이브러리라 Rust 서버에 넣을 수 없다. 그래서 서버 PC에 두 번째 `tailscaled`를 상태 폴더와 소켓을 따로 쓰고 `--tun=userspace-networking`으로 띄워 tailnet의 별도 노드로 만든다. `funnel` 노드 속성은 그 노드에만 주고, 그 노드의 443에서 공개 리스너만 연다.

사용자 결정(호스트 이름): (가)안을 권장안으로 채택했다. 실제 이름은 운영 단계 P0에서 정한다. 비교를 위해 두 안을 적어 둔다.

- (가) 별도 노드(권장): 주소는 `https://<공개 노드>.<tailnet>.ts.net`이다. host-only 쿠키와 출처가 나뉘고 운영자 노드에는 Funnel 권한이 없다. 대신 기기 하나와 systemd 단위 하나가 는다. 같은 사이트라는 점은 그대로라서 운영자 리스너의 출처 검사가 필요하다.
- (나) 같은 호스트의 8443: 운영 절차가 가장 적다. 쿠키를 같이 보내지만 운영자 리스너가 쿠키를 쓰지 않아서 지금은 해가 없다.

### 임시 장치와 걷어낼 것

첫 단계의 공개 리스너는 순위, 시장 개요, 히트맵을 운영자 시세 키로 직접 받는다. 위 키움 경로 한도(운영자 키 호출 보호, 스크리너 동시 한도)는 `collector-shared-data`가 공용 자료를 수집 데몬이 만들도록 넘길 때까지의 **임시 장치**다. 임시 장치는 `crates/server/src/public/` 안의 한 모듈에 모아 걷기 쉽게 둔다. 그 플랜이 끝난 뒤의 처리는 다음과 같다.

| 장치 | 그 뒤 |
|---|---|
| 경로 묶음별 동시 한도, 계정당 키움 경로 동시 1, TR 예산, 흐름 요청 안 동시 5 | 걷는다. 공개 요청이 키움을 부르지 않는다 |
| 흐름 분 맞춤 캐시와 웹의 분 맞춤 재요청 | 걷는다. 웹은 데몬 자료의 갱신 주기에 맞춰 받게 바꾼다 |
| 시장 개요 응답 캐시, 순위 5쪽 | 걷는다. 데몬이 만든 자료가 이미 주기 캐시다 |
| `Gated` 처리 | 걷는다 |
| 공개 오류 문구 고정 | 남긴다. 오류 원문을 공개하지 않는 규칙은 계속 맞다 |
| 운영자 쪽 지연 상한 단정 | 바꾼다. "공개 요청이 운영자 대기열에 TR을 하나도 넣지 않는다"는 단정으로 바꾼다 |
| 스크리너 동시·전체 분당 한도 | 걷는다. 계정 버킷과 상태 캐시는 남긴다 |
| 흐름 `symbols`를 계정 테마로 제한 | 남긴다. 응답 크기를 묶는다 |
| 계정·익명·전체 버킷, 동시 처리·시간 상한·panic 격리 | 남긴다. 서버 PC와 Funnel을 지킨다 |
| 계수 | TR 수 계수는 걷는다. 데몬 자료의 나이와 낡음 계수를 더한다 |
| 압축과 화면 파일, CSP, 운영자 리스너 출처 검사 | 남긴다. 키움과 상관없다 |

임시 장치를 지금 더 줄이지 않는 이유가 있다. 흐름 장치 넷(테마 제한, TR 예산, 동시 5, 분 맞춤 캐시) 가운데 하나라도 빼면 흐름 두 건이 운영자 분봉을 최대 약 24초 밀어내는 문제가 다시 열린다. 압축은 첫 로딩을 지키므로 그대로 둔다.

### 다음 목표: 운영자 키가 없는 별도 공개 프로세스

이렇게 옮기면 위 "한 프로세스의 위험"에 남은 것(잠금 오염, 공유 코드의 실수, CPU 고갈, 대기열 관문 전파)이 구조로 사라진다. 막는 것과 푸는 방법은 다음과 같다.

| 막는 것 | 푸는 방법 |
|---|---|
| 스크리너 일봉 저장소(DuckDB)는 두 프로세스가 함께 열 수 없다 | 업데이트 뒤 읽기 전용 사본을 만든다. 또는 `collector-shared-data` 뒤의 메모리 판정 자료를 내보낸다 |
| 공용 자료가 운영자 시세 키로 키움을 부른다 | `collector-shared-data`가 푼다. 공용 자료를 수집 데몬이 만들면 공개 프로세스는 키가 필요 없고 데몬의 자료를 읽기만 한다 |
| 종목 목록과 시세 캐시가 운영자 프로세스 메모리에 있다 | 내부 API나 스냅샷 파일로 넘긴다 |
| 재무 SQLite | WAL이라 여러 프로세스가 읽을 수 있다. 막지 않는다 |
| 계정 DB | 공개 쪽만 쓴다. 막지 않는다 |

## Considered Options

- **공개 인스턴스를 따로 띄우기**: 스크리너 DuckDB 파일을 두 프로세스가 열 수 없고, 같은 키움 키로 두 프로세스가 붙게 된다([ADR 0004](0004-dedicated-kiwoom-app-key.md)). 종목 목록, 재무 DB, 시세 캐시, 운영자 키의 대기열도 나눠 쓰지 못한다. 위험은 줄지만 첫 단계에는 맞지 않아 다음 목표로 둔다.
- **계정 서버를 별도 프로세스로 두고 경로로 나누기**: 세션 확인이 프로세스 사이 호출이 되고 설정과 배포 단위가 늘어난다. 라이브러리로 붙이면 세션 확인이 함수 호출이 되고 의존 방향도 지켜진다.
- **운영자 라우터를 걸러 쓰기**: 운영자 라우터에 새 라우트가 생길 때 공개 리스너에도 저절로 열린다. 계정 서버 라우터를 통째로 붙이면 Bearer 경로(`/v1/auth/token`, `/v1/me`, `/v1/setup/*`)와 커넥터 흐름 시작도 열려 세션 문과 출처 검사를 우회한다. 허용 목록은 새 라우트가 닫힌 채로 시작한다.
- **443에 Funnel**: 운영자 리스너가 받는 같은 노드의 443을 열면 운영자 리스너까지 인터넷에 닿는다. Funnel은 노드와 포트 단위라서, 공개 입구는 별도 노드의 443이나 같은 호스트의 8443으로 한다.
- **확인 안 된 IP 헤더 믿기**: Funnel이 클라이언트 IP를 어떤 헤더로 넘기는지 확인하지 않았다. 믿으면 위조된 헤더로 버킷을 피하거나 남의 버킷을 비울 수 있다. 확인한 뒤 IP별 버킷으로 고친다.
- **대기열 안 우선순위로 막기**: 공개 요청을 운영자 요청보다 낮은 우선순위 단계로 보내는 안이다. 이번에 하지 않는다. 우선순위 단계는 `kiwoom/` 대기열의 구조이고 다른 탭의 다중 증권사 플랜이 그 파일을 다시 짜고 있다. 우선순위가 낮아도 이미 나간 호출과 공용 관문의 `Gated`는 막지 못하고, 공용 자료를 수집 데몬이 만들면 이 문제 자체가 사라지므로 위 임시 장치로 묶는다.

## Consequences

- 지금 서버 PC의 로컬 전용 운영과 수집은 그대로 돈다. 공개 모드 설정이 없으면 서버는 지금과 같다.
- 운영자 리스너가 출처를 보게 되므로 개발 흐름(`vite dev` 프록시)이 영향받을 수 있다. 깨지면 프록시 쪽을 고친다.
- 호스트 이름이나 출처를 바꾸면 사용자들의 IndexedDB 키 보관소가 비어, 사용자가 키를 다시 넣어야 한다. 이 안내를 운영 문서에 둔다.
- 실제 Funnel 켜기, IdP 앱 등록, 배포는 나중에 따로 승인한다. IdP의 공개 가능 여부(가입 100명을 받을 수 있는지)는 호스트 이름과 함께 먼저 확인한다.
- 공개 한도는 모두 설정이므로 `GET /api/public-usage`와 분 단위 로그를 보고 조정한다.
- 별도 `vally-account` 실행과 커넥터 계정 모드는 나중에 거둔다.

### 받아들일 한계

- **같은 프로세스.** 공개 처리 중 panic이 `std::sync::Mutex`를 오염시키면 운영자 쪽(`market/hub.rs`, `bars.rs` 등의 `lock().expect`)도 계속 실패한다. 운영자 키가 없는 별도 공개 프로세스가 없앤다.
- **대기열 공유.** 공개 요청은 운영자 화면과 같은 `Priority::Screen` 단계로 나가므로, 같은 TR에서 계산한 상한(흐름 1초, 보드 0.2초, 순위 2초, 시장 개요 웜 2.4초)만큼 운영자를 늦출 수 있다. 시장 개요 `flow`의 하루 첫 콜드는 한 번 약 12초까지 늘 수 있다. 공개 부하가 만든 실패가 공용 관문(`GATE_WAIT` 30초, 반복 실패 시 5분, [ADR 0009](0009-kiwoom-errors-closed-categories.md))을 닫으면 운영자 조회에도 `Gated`가 번진다. `collector-shared-data`가 공개 요청의 키움 호출을 없애서 이 문제도 없앤다.
- **키움 경로 동시 한도의 근거.** 공개 경로의 키움 동시 한도는 운영자 키의 남는 처리량을 계산해 정한 값이 아니다. 운영자 쪽 지연 상한 계산으로 정한 첫 값이고, 계수를 보고 조정한다.
- **IP를 모름.** 로그인 시작 버킷을 한 사람이 다 쓸 수 있다.
- **오래된 브라우저의 `no-cors` `GET`.** `Sec-Fetch-Site`를 보내지 않는 브라우저의 Origin 없는 `GET`은 운영자 리스너에 닿는다. 응답은 읽히지 않는다.
- **가입 상한 선점.** 가입 100명을 악성 계정이 먼저 채울 수 있다. 차단 목록이 있으므로 받아들인다.
- **추정 부하표.** 10·50·100명 부하표는 사용 패턴 가정에 기댄 추정이다. Funnel의 실제 한계는 운영 단계에서 잰다.
