# 셋업은 문서 단위로 계정 서버에 두고, 커넥터가 로컬 사본과 동기화한다

사용자가 정했다(2026-11-17). 구조와 로그인은 [ADR 0023](0023-connector-and-account-server.md)이 다룬다. 이 ADR은 [ADR 0006](0006-user-data-in-sqlite.md)의 결정을 바꾼다. 커넥터의 로컬 SQLite는 그대로 있고, 계정 서버에 계정별 사본이 더해진다.

## 셋업

- **셋업**은 **문서**의 모음이다. 문서는 `(종류, id)`로 구분한다. 종류는 관심종목(그룹 포함), 조건식, 화면 상태(각 하나)와 레이아웃, 드로잉(id마다 하나)이다. 종류는 닫혀 있다.
- 문서 본문은 지금 HTTP API 본문 JSON 그대로이고, 문서마다 revision과 삭제 여부를 갖는다. 지금 저장 단위와 revision 규칙을 그대로 쓰고 새 병합 규칙을 만들지 않는다.
- 셋업이 아닌 것: 키움 키, 토큰, 등록 IP 기록, OpenDART 키, 스크리너 저장소, 재무자료 저장소. 내보내기와 동기화에 들지 않는다. 키와 시세는 커넥터에만 둔다는 ADR 0023의 결정이다. 시험으로 내보낸 묶음에 이 값들이 없음을 확인한다.
- 셋업 내보내기·가져오기(`GET /api/setup/export`, `PUT /api/setup/import`)가 동기화보다 먼저 있다. 내보낸 묶음이 동기화가 주고받는 형식의 원형이다. 가져오기는 로컬 셋업 전체를 바꾸고, 기존 검증 함수를 통과한 것만 받는다.
- 두 쪽이 함께 쓰는 형식은 작은 크레이트 `crates/setup`에 둔다. serde 타입, 형식 버전, 크기 한도만 갖는다. 계정 서버가 `server` 크레이트를 끌어오지 않고 같은 타입을 쓰고, 형식이 바뀌면 두 쪽이 함께 컴파일 오류를 낸다.

## 계정 서버 저장소

- 계정 서버 저장소는 SQLite와 sqlx이고 프로세스는 하나다(ADR 0006과 같은 도구). 셋업은 계정당 수 MB이고 쓰기는 사람 손 속도라 충분하다. 운영 방식은 사용자가 정한다.
- 계정 서버는 문서 본문을 해석하지 않는다. 종류, id 모양, 문서 크기, 계정 전체 크기만 검사한다. 커넥터가 받을 때 기존 검증 함수로 확인하고, 통과하지 못한 문서는 적용하지 않고 로그와 동기화 상태에 남긴다. 잘못된 문서의 피해는 그 계정에만 간다.
- 문서 크기 한도는 지금 라우트 한도를 `crates/setup`으로 옮겨 두 쪽이 같이 쓴다. 계정 전체 한도는 32MB다.
- 계정 서버는 계정마다 늘어나는 순번을 문서 쓰기에 매기고, 커넥터는 "이 순번 이후 바뀐 문서"를 받는다. 전체를 매번 받지 않고 놓친 변경 없이 이어 받는다.

## 충돌과 삭제

- 충돌은 문서 단위로 **revision이 큰 쪽이 이긴다**. 병합하지 않고 진 쪽 내용은 버린다. 지금 로컬 저장 규칙(`check_newer`)과 같다. revision이 사실상 밀리초 시각이라 늦게 고친 쪽이 이긴다. 충돌은 두 PC를 동시에 오프라인으로 고칠 때뿐이다.
- 삭제는 revision을 가진 삭제 표시로 남긴다. 레이아웃·드로잉 삭제 때 커넥터가 `max(저장된 revision + 1, 지금 밀리초)`를 매긴다. 삭제 표시가 없으면 다른 PC가 지운 문서를 다시 올린다.

## 동기화

- 시점: 로그인 직후, 커넥터 시작 때(로그인돼 있으면), 로컬 쓰기 뒤 5초 모아 보내기, 5분마다 받기.
- 계정 서버에 닿지 못하면 최대 5분까지 늘려 가며 다시 시도한다. 그동안 화면은 로컬 사본으로 그대로 돈다. 한 번 로그인한 뒤에는 계정 서버 없이도 계속 쓴다. 시세는 원래 로컬이기 때문이다. 계정 서버 주소가 있는 커넥터의 첫 사용에는 로그인이 필요하다.
- 받은 변경은 열린 화면을 바로 바꾸지 않는다. 커넥터가 WebSocket에 새 메시지 `setup_changed`를 보내고, 화면은 "다른 PC에서 바뀐 셋업이 있습니다"와 새로 고침 단추를 보인다. 지금 웹은 시작 때 한 번 읽고 그 뒤에는 자기 편집만 쓰므로, 편집 중인 레이아웃을 밑에서 바꾸면 자동 저장과 엉킨다. 기존 `hello`·`status` 메시지 모양은 바꾸지 않는다.

## 로컬 사본과 첫 로그인

- 로컬 사본은 한 계정의 것이다. 커넥터 DB에 소유 계정을 적는다. 다른 계정으로 로그인하면 바로 바꾸지 않고, 화면이 "이 PC의 셋업은 다른 계정 것입니다"와 "지우고 바꾸기"를 보인다. 올리지 못한 변경이 있으면 그 수를 함께 보인다.
- 소유 계정이 없는 로컬 자료(지금의 `data/vally.db`)로 처음 로그인하면: 계정 셋업이 비어 있으면 로컬 자료를 올린다. 계정에도 셋업이 있으면 화면이 "이 PC 셋업 올리기"와 "계정 셋업 받기"를 묻는다. 지금 쓰는 자료를 잃지 않는다.

## Considered Options

아래는 검토했지만 **고르지 않은 안**이다. 다시 꺼내려면 새 ADR로 이 결정을 바꾼다.

- **필드 단위 병합**: 문서마다 필드별 revision과 병합 규칙이 필요하다. 충돌이 두 PC를 동시에 오프라인으로 고칠 때뿐이라 과하다.
- **진 쪽을 충돌 사본으로 보관**: 사용자가 정할 결정으로 남아 있다(2026-11-17 기준 권장은 버리기). 원하면 동기화 범위가 커진다.
- **Postgres**: 계정당 수 MB와 사람 손 속도의 쓰기에는 별도 DB 서버를 운영할 이유가 없다. 바꾸려면 계정 서버 구현 전에 정해야 마이그레이션을 두 번 쓰지 않는다. 사용자가 정할 결정으로 남아 있다.
- **전체 묶음을 한 문서로 동기화**: 레이아웃 하나를 고쳐도 모든 자료를 올리고, 한 곳의 충돌이 모든 자료의 충돌이 된다.

## Consequences

- 셋업 기록(이전 판 되돌리기), 알림의 동기화(알림은 아직 저장하지 않는다), 두 PC에서 동시에 열린 화면의 실시간 병합은 범위 밖이다.
- 여러 프로세스가 쓰는 DB가 아니므로 계정 서버를 여러 대로 늘리려면 이 결정을 바꾼다.
