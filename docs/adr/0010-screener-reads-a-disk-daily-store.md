# 스크리너는 전 종목 일봉을 디스크에 모아 두고, 그것만 읽어 조건을 따진다

[ADR 0014](0014-screener-includes-current-krx-day.md)은 당일 기준 검색에 조회한 오늘 KRX 시세를 반영하는 예외를 추가한다.

스크리너는 대상 종목 전체(약 3,960종목, ETF 포함)의 봉을 보고 조건식을 따진다. 실행할 때마다 키움에서 받으면 초당 4회 한도 때문에 한 번에 10분 넘게 걸린다. 그래서 **스크리너만 쓰는 일봉 저장소**를 디스크의 DuckDB 파일에 두고, 스크리너는 이 저장소만 읽는다.

차트, 현재가, 종목 기본 정보는 지금처럼 키움에서 받아 보여 준다. 이것들은 이 저장소를 읽지 않고, ADR 0003을 그대로 따른다.

- 저장소는 키움 **KRX** 일봉(접미사 없는 종목코드)의 사본이다. 거래소는 KRX로 고정하고, 통합·NXT는 받지 않는다. 원본은 여전히 키움이다. 저장소는 언제 지워도 키움에서 다시 받아 채울 수 있다.
- 상장일부터 최근일까지 전체 이력을 모은다(키움 일봉은 1985-01-04부터 준다). 보관 기간에 상한을 두지 않는다.
- 사용자가 업데이트 버튼을 누르면 빠진 관측일을 채우고, 덜 찬 과거를 이어 받는다. 오늘 봉은 20:00 이후에만 받는다. 장중 시세는 저장하지 않는다.
- 같은 종목이라도 스크리너가 본 봉과 차트가 그린 봉이 다를 수 있다. 스크리너는 KRX이고 차트의 기본 거래소는 통합이다(ADR 0007). 수정주가가 반영되는 시점이나 주봉·월봉을 만드는 방법이 달라도 생긴다.
- 파일은 `data/` 아래에 두고 git에서 뺀다. 사용자 자료 SQLite(ADR 0006)와 섞지 않는다. 사용자 자료는 원본이고 이 저장소는 사본이라, 지우거나 다시 만드는 방식이 다르기 때문이다.

## ADR 0003에서 달라지는 것

ADR 0003은 "전 종목 시세를 미리 수집"하는 안을 "보지도 않는 종목까지 수집하는 것은 낭비"라는 이유로 버렸다. 스크리너는 모든 종목을 보는 기능이라, 이 근거는 스크리너에는 맞지 않는다. 스크리너 저장소에 한해 다음이 달라진다.

- **미리 수집:** 화면에서 열지 않은 종목도 일봉을 받아 둔다.
- **디스크:** 일봉을 디스크에 남긴다.
- **수정주가 대조:** 저장해 둔 과거 봉은 권리락이나 액면분할로 틀어진다. 07:45 비우기로는 해결되지 않는다. 그래서 수정 사건을 감지하면 그 종목의 전체 이력을 다시 받는다(#92).
  - 하루치 덧붙이기에서는 기준가가 저장된 전일 종가와 30% 넘게 다를 때 감지한다.
  - 일봉 1페이지를 받을 때는 겹친 날짜의 봉이 하나라도 다르면 감지한다.
  - 기준가는 정규장 종가이고 KRX 일봉 종가는 애프터마켓까지의 마지막 체결가라서, 둘은 매일 조금씩 다르다(#88). 그래서 단순히 같은지로는 견주지 않는다.
- **봉 주기 파생:** 스크리너의 주봉·월봉은 저장한 KRX 일봉에서 집계한다. 키움 주봉·월봉은 받지 않는다(스크리너 맵의 주봉·월봉 티켓 #90). ADR 0003의 "다른 봉 주기에서 파생하지 않는다"는 차트에만 적용된다.

## Considered Options

아래는 검토했지만 **고르지 않은 안**이다. 다시 꺼내려면 새 ADR로 이 결정을 바꾼다.

- **실행할 때마다 키움에서 전 종목 받기:** 저장소가 필요 없다. 하지만 한 번에 10분 넘게 걸리고, 그동안 차트와 키움 한도를 나눠 쓴다.
- **차트도 디스크 저장소를 읽게 ADR 0003을 바꾸기:** 원본이 하나로 합쳐진다. 하지만 분봉, 실시간 봉, 거래소별 캐시까지 바꿔야 해서 범위가 스크리너를 크게 넘는다.
- **사용자 자료 SQLite(`data/vally.db`)에 같이 두기:** 파일 하나와 이미 쓰는 sqlx로 끝난다. 고르지 않은 이유는 둘이다.
  - 검색 모양이 맞지 않는다. 스크리너는 수백만 행을 훑으며 고가 같은 열 한두 개만 보고, 종목마다 N봉 창을 밀며 최댓값을 구한다. SQLite는 행 단위로 저장해서 열 하나만 필요해도 줄 전체를 읽는다. DuckDB는 열 단위로 저장하고 이런 분석을 하라고 만든 DB다. 이 앱에서 둘을 견주어 재지는 않았다.
  - 성격이 다른 자료가 섞인다. 사용자 자료는 되찾을 수 없는 원본이고, 일봉은 언제든 다시 받는 사본이다. 한 파일에 두면 파일이 수백 MB로 커지고, 일봉을 대량으로 쓰는 동안 자동 저장이 기다린다. 저장소를 다시 만들 때도 파일을 지우지 못하고 일봉만 골라 지워야 해서, 실수하면 사용자 자료가 다친다.
  - ADR 0006은 DuckDB를 사용자 자료에는 맞지 않는다고 뺐지만, 종목 분석 리포트 같은 분석용으로는 "그때 따로 검토한다"고 남겨 두었다. 스크리너도 같은 분석 용도라서 여기서 DuckDB를 고른다.
