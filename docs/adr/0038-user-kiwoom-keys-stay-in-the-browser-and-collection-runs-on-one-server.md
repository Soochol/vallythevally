# 사용자 키움 키는 브라우저에만 두고 브라우저가 키움을 직접 부르며, 수집은 운영 서버 한 곳에서만 한다

여러 사람이 쓰는 서비스로 열 때의 구조다. 사용자가 정했다(2026-11-22). 사용자는 자기 PC에 프로그램을 설치하지 않고 웹 화면만 연다. [ADR 0023](0023-connector-and-account-server.md)은 키움 키와 시세를 각 사용자 PC의 커넥터에 두었다. 이 ADR은 그 자리를 각 사용자의 브라우저로 바꾼다. ADR 0023이 Considered Options에서 고르지 않은 (c)안에 수집 서버를 더한 모습이다.

## 정한 것

- **사용자 키는 브라우저에만 있다.** 사용자가 프론트엔드에서 키움 앱키와 시크릿을 입력하고, 그 PC의 브라우저에 저장한다. 키, 키움 토큰, 계좌번호는 서버로 보내지 않는다. 서버에는 이것을 받는 API가 없다.
- **사용자 키로 하는 일은 브라우저가 키움에 직접 한다.** 토큰 발급, 시세 REST, 실시간 WebSocket, 계좌·주문 TR이 여기에 든다. 시세는 각 사용자의 키로 받아 그 사용자의 브라우저에서만 보인다. 키움 REST와 WebSocket은 다른 출처의 요청을 받는다(2026-11-10 확인).
- **수집은 운영 서버 한 곳에서만 한다.** 수집기와 감독 데몬은 지금의 서버 PC처럼 운영 서버에서만 돈다. 수집 키는 운영자의 키이고 그 서버에만 있다([ADR 0022](0022-hoga-replay-collects-quotes-on-disk.md), [ADR 0026](0026-collector-supervisor-collects-common-and-preferred-stocks.md)). 사용자 브라우저는 수집을 하지 않는다.
- **운영 서버가 맡는 일**: 웹 화면 서빙, 수집기가 만든 자료 제공(일봉 저장소, 스크리너, 재무자료, ETF 구성 같은 것), 계정과 셋업 저장([ADR 0024](0024-setup-storage-and-sync.md)). 운영 서버는 사용자 키로 키움을 부르지 않는다.
- **ADR 0023에서 그대로 두는 것**: 로그인은 Google과 Naver OAuth뿐이고 비밀번호 로그인은 없다. 계정은 `(provider, subject)`로 식별하고 이메일로 잇지 않는다. 셋업에 시세와 시세에서 계산한 값은 들지 않는다.
- **ADR 0023에서 바뀌는 것**: 키와 시세를 커넥터에만 둔다는 결정, 그리고 그 전제 위의 루프백 로그인 흐름과 커넥터 토큰이다. 브라우저가 운영 서버를 직접 상대하므로 커넥터가 로그인 결과를 받을 이유가 없어진다. 새 로그인 흐름과 세션 방식은 따로 ADR로 정한다.
- **키 규칙은 키마다 그대로다.** 토큰을 다시 받으면 이전 토큰이 폐기될 수 있고 토큰 하나에 WebSocket 세션은 하나다([ADR 0004](0004-dedicated-kiwoom-app-key.md)). 키 목록과 시세 키([ADR 0037](0037-kiwoom-keys-are-a-list-with-one-market-key.md)), 발급 간격, 8050 차단도 키마다 지킨다. 이것을 지키는 주체가 서버 프로세스에서 브라우저로 바뀐다.

## 속도 확인

옮기기 전에 시제품으로 쟀다(2026-11-22). 가짜 키움 서버가 `REAL` 0B 형식(항목당 FID 약 40개)으로 100종목의 체결을 흘리고, 브라우저가 받아 1분봉을 만들어 캔버스에 그렸다. 개발 PC의 headless Chromium이다.

- 체결 한 건의 처리(JSON 파싱과 봉 갱신)는 4~11µs였다. 초당 3,000건에서도 CPU 1.3% 안쪽이었고 받은 수와 보낸 수가 같았다.
- 화면 반영 지연 p99는 약 17ms(한 프레임)였고 60fps를 지켰다. 그리기에 30ms를 더하면 메인 스레드와 Worker 모두 30fps였다. 병목은 그리기였다.
- 그래서 JS로 옮겨서 생기는 속도 문제는 결정 근거가 되지 않는다. 숨긴 탭, 실제 키움 네트워크, 휴대폰은 재지 않았다.

## Considered Options

- **각자 PC에 커넥터를 설치(ADR 0023)**: 사용자가 프로그램을 설치해야 한다. 사용자는 웹만 열면 쓰는 모습을 원한다.
- **사용자 키를 운영 서버에 보관**: 서버가 털리면 모든 사용자의 주문 가능한 키가 새어 나간다. 시세를 사용자별로 나누려면 백엔드를 크게 바꿔야 한다.
- **수집도 각 사용자 브라우저에서**: 수집은 탭이 닫혀도 돌아야 하고 전 종목을 다룬다. 지금처럼 운영 서버 한 곳에서 한다.

## Consequences

- 지금 Rust 서버가 하는 키움 연결, 토큰 관리, 시세 허브와 봉 만들기, 실시간, 주문·계좌(`crates/server/src/kiwoom`, `market`, `trading`, `ws.rs`)를 브라우저로 옮겨야 한다. 가장 큰 작업이다. 옮기는 순서와 Rust 코드를 WASM으로 옮길지는 플랜에서 정한다.
- 같은 키로 탭이나 기기가 여러 곳에서 토큰을 받으면 서로의 세션을 끊는다. 한 브라우저 안에서는 연결 하나를 탭들이 나눠 쓰는 장치(SharedWorker나 대표 탭)가 필요하다. 같은 키로 PC와 휴대폰을 함께 쓰는 문제는 아직 풀리지 않았다.
- 키를 브라우저에 두므로 화면에 끼어든 스크립트(XSS)가 키를 읽을 수 있다. 외부 스크립트를 쓰지 않는 엄격한 CSP와 저장 방식(예: 잠금 비밀번호로 암호화)을 따로 정한다.
- 브라우저는 숨긴 탭의 타이머를 늦춘다. 탭이 열려 있지 않으면 사용자 실시간 알림이 오지 않는다.
- 키움 키는 IP를 등록해야 하므로 IP가 자주 바뀌는 휴대폰에서는 쓰기 어렵다.
- 시세 캐시가 브라우저 저장소(IndexedDB) 크기와 수명에 묶인다. 공용 자료는 운영 서버가 주므로 개인 캐시는 작게 둔다.
- 운영 서버를 공개 주소로 여는 방법(지금은 tailnet, [ADR 0036](0036-remote-access-goes-through-tailscale-serve-and-a-configured-tailnet-name.md))과 호스팅은 이 결정 밖이다.
- 로컬 전용 모드의 커넥터는 옮기는 동안 그대로 둔다. 언제 거두는지는 플랜에서 정한다.
