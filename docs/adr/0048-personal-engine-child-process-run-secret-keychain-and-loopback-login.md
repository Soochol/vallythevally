# 개인 엔진은 껍데기의 자식 프로세스로 루프백 HTTP/WS만 열고, 실행마다 바뀌는 입장권과 키체인 자료 키를 표준 입력으로 받으며, 앱 로그인은 루프백 흐름과 Bearer 커넥터 토큰을 쓴다

[ADR 0045](0045-desktop-app-runs-a-personal-engine-and-the-server-keeps-login-and-shared-data.md)가 남긴 기대값 넷을 확정한다. 넷은 프로세스 모양과 통신, 엔진 루프백 API 보호, 키 보관, 앱 로그인이다. 설계 전체와 근거 숫자는 [`docs/desktop-engine.md`](../desktop-engine.md)에 있다. 사용자는 설계에서 성능을 가장 중요하게 본다. 코드 사실의 기준은 `origin/main` `871206b1`이다.

## 정한 것

- **엔진은 껍데기(Tauri 2)의 자식 프로세스다. 화면은 엔진의 루프백 HTTP/WS만 부른다.** 개발 PC 측정([`docs/desktop-performance.md`](../desktop-performance.md))의 결과는 다음과 같다. 초당 3,000건에서 두 길 모두 손실이 없었다. 지연 p99는 1ms 아래였다(WebSocket 0.63ms, IPC 0.36ms). 화면 CPU는 IPC 채널이 16.7%, WebSocket이 6.2%였다. IPC는 얻는 것 없이 화면 CPU를 더 쓴다. 자식 프로세스는 엔진의 panic과 잠금 오염을 창에서 떼어 놓는다. 엔진의 의존성이 껍데기 워크스페이스와 섞이지 않고, 엔진을 앱 밖에서 그대로 시험할 수 있다. 이 숫자는 WebKitGTK와 소프트웨어 그리기에서 나왔으므로 Windows WebView2에서 같은 명령으로 다시 잰다.
- **엔진 루프백 API는 실행마다 바뀌는 입장권과 엔진 쿠키로 지킨다.** 진행은 다음과 같다.
  1. 껍데기가 32바이트 입장권을 만들어 엔진 표준 입력의 첫 줄로 넘긴다.
  2. 창을 `/auth/engine?ticket=…`로 연다.
  3. 엔진은 입장권을 한 번만 받고, 새 32바이트 엔진 쿠키(`HttpOnly; SameSite=Strict; Path=/`)로 바꾼다.

  검사는 운영자 라우터의 출처 검사 층 옆에 하나 더 둔다. 범위는 `/api/*` 전부이고 `/api/ws` 업그레이드도 포함한다. `/auth/complete`(시스템 브라우저가 오는 곳)와 화면 파일만 면제한다. 화면 코드는 바뀌지 않는다. `fetch`와 `WebSocket`이 같은 출처의 쿠키를 저절로 싣기 때문이다. 앱 모드(`VALLY_ENGINE_STDIN=1`)에서만 켠다. 그 모드에서 줄이 없으면 엔진은 시작하지 않는다.
- **키 보관은 OS 키체인의 설치별 자료 키 하나와 파일 암호화다.** 자료 키는 32바이트다. Windows는 자격 증명 관리자, macOS는 키체인에 둔다. 키 목록, 토큰 파일, 계정 상태(`account.json`)는 `PrivateFile` 한 곳에서 AES-256-GCM으로 암호화한다. 연관 자료는 파일 종류 이름이다. 키체인은 껍데기가 읽고 자료 키는 같은 표준 입력 줄로 엔진에 넘긴다. 엔진과 루트 워크스페이스는 OS 키체인을 모른다. 옛 평문 파일은 앱 모드에서 처음 읽을 때 같은 경로에 암호문으로 다시 쓴다. Windows의 `state/`는 `%LOCALAPPDATA%`에 둔다.
- **앱 로그인은 [ADR 0023](0023-connector-and-account-server.md)의 루프백 흐름(RFC 8252, PKCE)과 커넥터 토큰을 그대로 쓴다.** 바뀌는 곳은 셋이다.
  - 껍데기가 엔진 출처 밖으로 가는 창 이동을 막고 시스템 브라우저로 연다.
  - 앱 모드의 `/auth/complete`는 화면 대신 "앱으로 돌아가세요" 문서를 준다.
  - 공개 리스너가 계정 서버의 커넥터 라우트를 열고 `Authorization: Bearer`를 세션과 같은 계정 버킷(`provider:subject`)의 주체로 받는다. Bearer 요청에는 Origin 필수 규칙을 걸지 않는다. 브라우저가 Bearer를 저절로 싣지 않으므로 CSRF가 생기지 않는다. 토큰의 마지막 사용 시각은 세션처럼 한 시간이 넘었을 때만 다시 쓴다.

## 바꾸는 것

- **ADR 0040**: "계정 서버 라우터를 통째로 붙이면 Bearer 경로가 열려 세션 문과 출처 검사를 우회한다"는 이유로 공개 리스너에 Bearer 경로를 열지 않았다. 이 ADR이 커넥터 라우트를 허용 목록으로 열고 Bearer 주체를 문에서 같은 버킷으로 센다. 세션 쿠키 로그인과 공개 모드 화면은 앱 로그인이 병합된 뒤 걷는다(설계 문서 9절). ADR 0040 파일의 개정 줄은 그 작업이 단다.
- **ADR 0023**: 커넥터 토큰을 계정 서버의 별도 리스너가 아니라 공용 서버의 공개 리스너가 받는다. 같은 PC의 악성 프로그램에 대해 받아들인 루프백 한계는 그대로다.
- **ADR 0045의 받아들일 한계** "루프백 API 보호가 들어가기 전에는 앱에서 주문을 켜지 않는다"는 입장권 검사가 병합되면 풀린다.

## Considered Options

- **엔진을 껍데기 프로세스 안에 링크**: 프로세스 하나 몫의 메모리와 시작 시간을 아낀다(추정: 수 MB, 수십 ms, 재지 않았다). 엔진 장애가 창을 같이 죽이고, Tauri 의존성이 루트 워크스페이스로 들어오고, 앱 밖 시험 길을 따로 둬야 한다.
- **화면 통신을 Tauri IPC로**: 지연에서 얻는 것이 없고(둘 다 1ms 아래, 해상도 한계) 화면 CPU가 2.5~2.7배다(측정). 화면의 `http.ts`·`socket.ts`를 바꿔야 하고 껍데기에 묶인다.
- **입장권을 헤더로 싣기**: 브라우저 `WebSocket`은 헤더를 못 붙인다. 질의 문자열이나 `Sec-WebSocket-Protocol`로 따로 넘겨야 하고, 화면 코드 두 곳을 고친다. 쿠키는 0줄이다.
- **입장권을 환경 변수나 명령줄로 넘기기**: 명령줄은 다른 OS 사용자에게 보인다. 환경 변수는 엔진의 자식과 진단 출력으로 샌다. 표준 입력은 닫히면 종료 신호도 된다.
- **보호 없이 Host·Origin 검사만**: 브라우저 페이지는 막지만 브라우저가 아닌 로컬 프로그램은 헤더를 마음대로 적는다. 주문 라우트가 열린다.
- **비밀값마다 키체인 항목**: Windows 자격 증명의 비밀 값 한도가 2,560바이트다. 키 한 줄이 약 150~250바이트(추정)이고 증권사마다 5개라 N개 증권사의 키 목록과 토큰이 들어가지 않는다. 목록과 원자적 교체를 키체인 위에 다시 짜야 한다.
- **Windows DPAPI 직접 사용**: Windows 전용이라 macOS 길을 따로 짠다.
- **잠금 비밀번호 기본**: 엔진이 뜰 때마다 묻는다. ADR 0041이 기본으로 고르지 않은 이유와 같다. 나중에 고르는 선택으로 남긴다.
- **앱 로그인을 앱 WebView 안에서 하기**: RFC 8252가 금하는 내장 사용자 에이전트다. Google은 내장 WebView의 OAuth를 막는다.
- **앱용 별도 로그인 입구(계정 서버를 따로 Funnel에)**: Funnel 노드와 포트가 하나 더 늘고, 공용 자료 요청과 계정 버킷을 다른 프로세스에서 세야 한다. 공개 리스너는 이미 계정 서버를 라이브러리로 붙이고 있다(ADR 0040).

## Consequences

- 앱 화면 코드는 이 넷 때문에 바뀌지 않는다. 생성 타입 `ApiErrorCode`에 `engine_locked` 하나가 더해진다.
- 엔진을 다시 띄우면 입장권과 쿠키가 새로 생기므로 껍데기가 창을 다시 연다.
- 자료 키를 잃으면(키체인 항목 삭제, OS 재설치) 키를 다시 넣어야 한다. 키움 토큰은 최소 10분 간격으로만 다시 발급된다(ADR 0004).
- 같은 사용자로 도는 악성 프로그램은 막지 않는다. 그 프로그램은 키체인과 앱 자료 폴더도 읽을 수 있다(ADR 0023의 받아들인 한계와 같다).
- 디스크 블록에 남은 옛 평문 조각은 지우지 못한다.
- 구현은 설계 문서 11절의 `engine-guard`, `engine-keychain`, `public-bearer`, `app-login`이 한다.
