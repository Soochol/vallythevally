# 키움 대기열은 TR마다 최근 1초 전송 수를 세고, 제한 응답은 창이 비는 시각에 다시 보낸다

서버의 모든 키움 REST 요청은 `crates/server/src/kiwoom/rest.rs`의 대기열 하나를 지난다. 이 대기열은 모든 전송 사이를 260ms 띄웠다(ADR 0003의 "초당 4회"). 종목을 바꾸면 TR 7~9건이 나가므로 건수 × 260ms가 걸려 차트와 호가주문창이 1.6~2.3초 뒤에야 찼고, 주문 한 건은 키움 응답이 아무리 빨라도 0.78초 아래로 내려가지 못했다. 키움 응답은 실서버 기준 6~127ms(중앙값 12ms)다. 느린 쪽은 키움이 아니라 이 간격이었다. 계획은 [키움 대기열 속도](../plans/queue-speed.md)다.

## 결정

- **세는 곳은 대기열 하나다.** 바꾸는 것은 세는 방식뿐이다. 이 대기열은 키 하나에 하나이므로 서버 안에서는 TR(api-id)이 곧 (앱키, TR)이다.
- **TR마다 최근 1초 창으로 센다.** TR 사이에는 간격을 두지 않는다. 그 TR의 최근 전송이 한도(실전 5, 모의 1) 미만이면 곧바로 보내고, 찼으면 창 안 가장 오래된 전송 + 1초 + 여유 50ms(`WINDOW_MARGIN`)에 보낸다. 창이 찬 TR이 줄 앞에 있어도 다른 TR은 먼저 나가고, 기다리는 동안 대기열은 다음 창이 비는 가장 이른 시각까지만 잔다. 같은 TR 안의 순서는 우선순위(주문 → 화면 → 복구 → 배경)와 선착순 그대로다. 연속조회 페이지, 다시 보내기, 토큰 발급, 제한 응답을 받은 전송도 같은 창에 센다. 토큰 발급은 발급 간격(10분)과 "시세보다 먼저"를 그대로 둔다.
- **주문 쓰기 네 TR(`kt10000`~`kt10003`)은 한 창으로 센다.** 모의에서도 같다(한도 1).
- **제한 응답은 그 TR만 붙잡고, 창이 비는 시각에 같은 요청을 다시 보낸다.** 1초 고정 대기와 대기열 전체 멈춤은 없다. 제한 응답을 받은 전송까지 센 창에서 가장 오래된 전송 + 1초 + 여유가 그 시각이다. 같은 요청을 다시 보내는 횟수 규칙은 ADR 0009 그대로다(`MAX_RATE_LIMITED` 3, 전송 예산, 세 번째면 실패와 공용 관문 30초).
- **`유량=N`을 읽는다.** 제한 응답 `return_msg`의 `유량=N`이 지금 한도와 다르면 그 TR(묶음)의 한도를 N으로 바꾸고 경고 로그를 한 줄 남긴다. 서버가 켜져 있는 동안만 기억한다. 읽지 못하면 한도는 그대로다.
- **1분 카운터.** 대기열이 1분마다 TR별로 `sent`·`rate_limited`·`resent`·`max_wait_ms`(창이 차서 기다린 가장 긴 시간)를 로그 한 줄씩 남긴다. 그 1분에 센 값이 모두 0인 TR은 남기지 않는다. 제한 응답은 보낸 분이 아니라 도착한 분에 세므로, 그 분에 전송이 없어도 `rate_limited`가 0보다 크면 줄을 남긴다. 장중에 `journalctl`로 제한 응답이 실제로 나는지, 어느 TR에서 나는지 본다. 값은 api-id와 수뿐이다.
- **`Retry-After`는 읽지 않고 기록만 한다.** 전송 계층(`kiwoom/transport.rs`)이 429 응답에 이 헤더가 있으면 api-id와 함께 로그에 남긴다. 키움이 보낸 기록이 없고, 읽으려면 `HttpResponse`를 바꿔야 해서 여러 시험이 따라 바뀐다.
- **합계 창은 만들어 두고 꺼 둔다.** 이름 있는 상수 `TOTAL_PER_SECOND_LIMIT`(기본 `None`)을 켜면 TR별 창과 별개로 모든 TR의 최근 1초 전송 합계도 그 값 미만일 때만 보내고, 차면 합계 창이 비는 시각(+ 여유)에 보낸다. 둘 다 만족해야 나가고 주문 묶음도 합계에 센다. 토큰 발급은 합계에 세지 않는다. 시세·주문 TR 호출 한도와 다른 발급 경로이고, 발급은 10분 간격 규칙이 따로 있다. 켠 경우 1분 카운터에 합계 창 때문에 기다린 가장 긴 시간(`max_total_wait_ms`)이 더해진다. 꺼진 상태의 동작은 합계 창이 없던 설계와 같다.
- **시험용 간격 손잡이는 지금 뜻 그대로다.** `KiwoomRest::with_send_spacing`·`build(.., spacing, ..)`와 그것을 쓰는 `KIWOOM_SEND_SPACING_MILLIS`는 "모든 전송 사이 최소 간격"이고, 이 손잡이로 만든 대기열은 창 계수와 주문 묶음을 쓰지 않는다(모의는 같은 TR 1초를 지킨다). 실서비스 생성자(`new`, `for_environment`)만 새 규칙이다.

## 근거

- **한도.** 공식 이용안내는 "계좌별(토큰별) 초당 5회"로 적고, API 가이드의 TR 상세(예 `kt10000`)는 "TR 호출 한도: 초당 5회"라고 적는다. 실측(hoga-ops `docs/research/2026-08-03-kiwoom-rest-rate-limit-and-budget.md`)으로는 조회가 (앱키, TR)마다 초당 5회이고 TR끼리 독립이다. `ka10080`이 429를 받은 직후 대기 없이 보낸 `ka10081`이 통과했다. 모의는 TR 하나당 초당 1회다(ADR 0030).
- **429 응답의 모양.** HTTP 429, `return_code` 5, `return_msg`는 `허용된 요청 개수를 초과하였습니다[1700:허용된 API 요청 개수를 초과하였습니다. 유량=5, API ID=ka10080]`다(`tests/fixtures/kiwoom/err_1700.json`). 지금 전송 계층은 `cont-yn`·`next-key` 말고는 헤더를 읽지 않았고 `Retry-After`를 받았다는 기록은 없다.
- **슬라이딩 창이 고정 칸에도 안전하다.** 키움이 고정 1초 칸으로 세는지 최근 1초 슬라이딩으로 세는지는 재지 않았다. 최근 1초 슬라이딩 창으로 5건을 지키면 어느 고정 1초 칸에도 5건을 넘지 않으므로 두 경우 모두 안전하다. 이 대기열의 창은 1초 + 여유 50ms라 더 좁게 센다.
- **여유 50ms.** 키움이 세는 시각은 요청이 키움에 닿은 시각이고 우리가 아는 시각은 보낸 시각이다. 두 요청의 도착 간격은 보낸 간격과 한 방향 지연 차이만큼 어긋난다. 실서버 키움 응답 시간 146건은 최소 6ms, 중앙값 12ms, p95 38ms, p99 53ms, 최대 127ms였다(switch-latency 조사의 실서버 로그). 거의 모든 경우의 어긋남이 50ms 안이다. 여유는 창이 찬 뒤의 전송에만 붙고, 창이 비어 있을 때의 전송은 기다리지 않는다. 이보다 크게 어긋나 429가 나면 위 규칙이 창이 비는 시각에 다시 보내고 1분 카운터가 그 횟수를 보인다. 값은 상수 하나라 카운터를 보고 바꿀 수 있다.
- **주문을 한 창으로 묶는다.** 공식 이용안내는 주문 TR을 "계좌별 초당 5회"로 적고 주문 TR끼리 독립인지는 재지 않았다. 주문은 제한 응답을 맞지 않는 쪽이 낫다. 묶어도 손해는 1초 안에 매수·매도·정정·취소를 합쳐 6건 넘게 보낼 때뿐이다(모두 취소는 `kt10003` 한 TR이라 어차피 같은 창이다).
- **제한 응답을 받은 전송도 센다.** 키움이 거절한 요청을 세는지 모르므로 보낸 것은 모두 센다.
- **제재는 확인하지 못했다.** 공식 안내, 오류코드 문서, hoga-ops 기록, 공개 검색 어디에도 반복 초과로 키가 정지·차단된 사례가 없다. 없다는 확인이 아니라 확인하지 못했다는 뜻이다. 그래서 제한 응답을 지금보다 자주 받지 않도록 한도를 다 쓰되 넘기지 않는 창 계수를 택했고, 카운터로 실제 빈도를 본다.

## 주문 쓰기의 제한 응답 재시도는 ADR 0029 "한 번만 보낸다"의 예외다

ADR 0029는 주문 쓰기를 한 번만 보내게 했다. 이 결정은 한 가지 경우에 그 예외를 둔다. 한 번만 보내는 요청이 **HTTP 429이고 범주가 한도 초과**일 때 위 시각에 같은 본문을 다시 보낸다. 다시 보내기는 최대 두 번(첫 전송을 포함해 세 번)이고, 이름 있는 상수(`ORDER_RATE_LIMIT_RESENDS`, 0이면 끈다) 하나로 끈다. 다시 보내기 전에도 주문 사용 확인(`admit`)을 지나고 꺼졌으면 `NotConnected`로 끝난다. 끝내 429면 지금처럼 실패로 돌려주고 주문 쪽(`trading/orders.rs` `settle`)이 확정 거절로 판정한다. 전송 오류, 시간 초과, 5xx, 읽을 수 없는 응답, 다른 범주는 지금처럼 다시 보내지 않는다. 응답을 알 수 없는 경우를 다시 보내면 같은 주문이 겹칠 수 있기 때문이다.

예외의 근거는 "제한 응답은 처리되지 않았다"다. 공식 문서에 명시는 없고, 근거는 세 가지다.

- 업무 응답이 아니라 접수 전 유량 검사 오류다. `return_code` 5와 공통 오류 `[1700]`이고 업무 거절 `[2000]`과 다른 코드다.
- 다른 오류는 HTTP 200으로 오는데 이것만 HTTP 429다.
- 서버는 이미 주문 쓰기의 429를 "키움이 받지 않음"(확정 거절)으로 판정한다(`kiwoom_said_no`).

429인데 주문이 들어갔다는 반대 사례는 찾지 못했다.

## 남는 위험

- 키움 문서가 "제한 응답을 받은 주문은 처리되지 않는다"고 보장하지는 않는다. 다시 보낸 주문이 겹친 사례가 생기면 `ORDER_RATE_LIMIT_RESENDS`를 0으로 해 주문 쓰기 재시도를 끈다.
- 공식 문구의 "계좌별 초당 5회"가 여러 TR의 합계라는 뜻이면, 한 번에 여러 TR을 보낼 때 제한 응답이 난다. 1분 카운터에 서로 다른 TR의 `rate_limited`가 섞여 보이면 그 신호다. 그때는 `TOTAL_PER_SECOND_LIMIT`을 `Some(5)`로 켠다.

## Considered Options

- **공용 간격을 줄이거나 그대로 두기**(지금까지): 간격이 모든 TR을 한 줄로 세워 전환 한 번에 건수 × 260ms가 걸린다. 한도가 TR마다 독립이라는 실측과 맞지 않아 고르지 않았다.
- **제한 응답에서 대기열 전체를 1초 멈추기**(ADR 0009의 옛 규칙): 다른 TR과 주문이 이유 없이 1초 기다린다. 창이 비는 시각을 알면 그 TR만 그 시각에 다시 보내면 된다.
- **주문 TR을 따로 센 창으로 두기**: 주문 TR끼리 독립이라는 근거가 없어 묶었다.
