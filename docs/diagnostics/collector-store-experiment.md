# 수집 저장소의 처리 방식 실험

수집기가 장 마감 뒤 원문을 정리해 앱이 지난 날을 보여 줄 때, 어떤 방식이 속도·메모리·디스크에서 나은지 쟀다. 결정은 수집기 ADR(PR #435)이 한다. 이 문서는 그 근거가 되는 측정만 적는다. 측정은 2026-11-17에 했다.

## 목표

다음 네 기준을 지키면서 디스크를 가장 적게 쓰는 방식을 찾는다.

- 760종목 하루치 정리를 10분 안에, 최대 메모리 8GB 안에 끝낸다.
- 앱이 한 종목의 한 화면(5분 구간)을 100ms 안에 받는다.
- 브라우저 재생이 60fps를 유지한다.
- 하루 디스크 크기로 보관 기간을 정할 수 있게 한다.

## 입력과 조건

- **실제 원문:** 2026-11-17 정규장 11:35~13:55에 프로토타입 수집기가 받은 8종목(0B·0D·0w·0F)이다. 압축 전 442MB다. 원문과 결과 파일은 저장소에 넣지 않는다.
- **760종목 입력:** 실제 원문을 종목 이름만 바꿔 95벌로 늘렸다(압축 전 42GB). 가격·수량 FID는 벌마다 조금씩 바꿔 압축률이 부풀지 않게 했다. 정렬해 저장한 Parquet 크기가 실제 8종목 × 95와 같아서(570MB와 569MB), Parquet 크기는 복제 때문에 작아지지 않았다. 원문 zstd 크기는 복제 때문에 실제보다 훨씬 작게 나온다. 그래서 원문 크기는 실제 8종목 값만 쓴다.
- **하루치 어림:** 아래 하루 값은 2시간 15분 치 결과에 5를 곱한 어림이다. 실제 하루 양은 아직 재지 않았다.
- **종목 편향:** 8종목이 대형주와 ETF라 760종목 실제 양보다 클 것이다.
- **기계:** 32코어, 91GB 메모리. 처음 측정의 일부는 다른 세션의 C++ 빌드와 겹쳐 경과 시간이 부풀었다. 그 경우는 표에 적었다.
- **실시간 타입:** 네 타입(0B·0D·0w·0F)만 쟀다. 수집기가 받기로 한 나머지 일곱 타입(1h, 0H, 0E, 0g, 0J, 0U, 0s)은 들어 있지 않다.
- **키움과 네트워크:** 키움에는 접속하지 않았다. 원문 수신은 로컬 가짜 WS 서버가 실제 원문을 다시 보내서 쟀다. 브라우저 측정은 루프백이라 네트워크 전송 시간이 빠져 있다.

## 처리 방식

760종목 2시간 15분 치를 원문에서 정리할 때의 값이다.

| 방식 | 경과 | CPU 시간 | 최대 메모리 | 결과 크기 |
|---|---:|---:|---:|---:|
| 지금 `build` (하루를 메모리에 올리고 brotli q11 구간 파일) | 8종목에 64초, 760종목 하루 약 8시간 어림 | | 하루 50GB 넘음 어림 | |
| A. DuckDB에 넣고 Parquet으로 내보내기, 복기 열 | 100초 + 내보내기 12초 | 1,761초 | 5.9GB | 570MB |
| A. 같은 방식, 모든 FID | 826초 (16스레드) | 2,461초 | 8.0GB | |
| B. Parquet 직접 쓰기, 복기 열 | 77초 (다른 빌드와 겹침) | 1,512초 | 2.7GB | 454MB |
| B. Parquet 직접 쓰기, 모든 FID와 부호 열 | **49초** (병합 4스레드) | 636초 (병합 8스레드일 때) | **4.1GB** | 1,569MB |

- **지금 `build`:** 시간 거의 전부가 brotli q11 압축이다. 같은 구간 파일을 q5로 압축하면 100배 빠르고 크기는 14% 는다.
- **B의 방식:** 원문을 스레드마다 읽어 종목 해시로 64개 버킷에 나눠 임시 파일로 흘리고, 버킷마다 종목·시각 순으로 정렬해 Parquet을 쓴다. 정수 열은 delta 인코딩, zstd 3이다.
- **A와 B의 결과 비교:** 실제 8종목에서 네 표 모두 행 단위로 같았다. 양쪽 차집합이 모두 0이었다.
- **B의 메모리:** 병합 스레드 하나가 약 1GB를 쓴다. 병합 스레드 8개면 40초에 8.2GB, 4개면 49초에 4.1GB였다. 하루치에서는 버킷 수를 늘리면 버킷 하나의 크기와 메모리가 그대로다.
- **표본 단계 함정:** 모든 FID 방식이 한때 164초 걸렸다. 열 목록을 정하려고 파일을 한 스레드로 길게 훑는 표본 단계 때문이었다. 실제 수집기에서는 키움 명세로 열을 정하니 이 단계가 없다.
- **부호 열:** 키움은 가격에 `+`(상승), 부호 없음(보합), `-`(하락)을 붙인다. 숫자로만 저장하면 `+`가 사라진다. 실제 원문에서 `+`가 나온 숫자 FID마다 `f{FID}_plus` 열을 더했다. 0B에서 11개가 생겼고 크기는 3.8% 늘었다.

## 디스크

실제 8종목으로 잰 종목 하나·1시간의 크기와, 760종목 하루(6.5~12시간)·1년(245거래일) 어림이다.

| 형태 | 종목·시간 | 하루 | 1년 |
|---|---:|---:|---:|
| 원문, 압축 전 | 24MB | | |
| 원문, zstd 3 (지금) | 1.65MB | 8~15GB | |
| 원문, zstd 9 | 1.14MB | 5.6~10GB | 1.4~2.5TB |
| Parquet, 모든 FID와 부호 열 | 0.91MB | 4.5~8.3GB | 1.1~2.0TB |
| Parquet, 복기 열 | 0.26MB | 1.3~2.4GB | 0.32~0.59TB |

- **정렬:** 종목·시각 순으로 정렬하면 크기가 절반이 된다.
- **압축 수준:** Parquet에서 zstd 1~9와 묶음 크기 1만~12만은 크기 차이가 4% 안이었다. snappy는 1.5배 컸다.
- **delta 인코딩:** 정수 열에 쓰면 복기 열은 19%, 모든 FID는 7% 줄었다.
- **원문 zstd 9:** 실제 원문에서 한 코어로 초당 110MB를 압축했다(zstd 3은 372MB). 3보다 31% 작다. zstd 19는 2시간 15분 치에 28분이 걸려 쓸 수 없다.
- **크기가 줄어드는 이유:** 원문을 모든 FID Parquet으로 바꾸는 것만으로는 23% 준다. 복기 열만 남기면 거기서 3.4배 더 준다.

## 조회

가장 큰 종목 하나, 2시간 15분 치를 DuckDB `query_arrow`로 읽었다.

| 배치 | 호가 | 체결 |
|---|---:|---:|
| 파일 하나, 묶음 122,880행 | 92ms | 23ms |
| 파일 하나, 묶음 30,000행 | 150ms | 30ms |
| 종목 해시 64개 파일, 묶음 30,000행 | 42ms | 16ms |
| 위와 같은 배치, 5종목을 한 번에 (하루치 행 수에 해당) | 159ms | 59ms |
| 종목 해시 64개 파일, 모든 FID 호가 전체 열 | 146ms | |

- **파일 나누기:** 종목 해시로 나눈 파일은 조회 때 파일 하나만 읽어서 가장 빨랐다.
- **정렬:** 정렬하지 않은 파일은 3~5배 느렸다.

### 5분 구간 하나를 만들 때 묶음 크기

모든 FID Parquet(종목 해시 64개 파일)에서 서버가 구간 하나를 만들 때의 조회 시간(p50)과 전체 크기다.

| 묶음 행 수 | 4,000 | 10,000 | 30,000 | 60,000 | 122,880 |
|---|---:|---:|---:|---:|---:|
| 구간 조회 | 57ms | 28ms | 16ms | 14ms | **13ms** |
| 전체 크기 | 1,767MB | 1,619MB | 1,569MB | 1,548MB | **1,533MB** |

이 배치에서는 묶음이 클수록 빠르고 작았다. DuckDB 연결을 스레드마다 유지하거나 메타데이터 캐시(`enable_object_cache`)를 켜도 조회 시간은 달라지지 않았다.

## 받기에서 브라우저까지

### ① 받기 → 원문 저장

가짜 WS 서버 네 개가 키 네 개의 몫(키마다 약 190종목)을 루프백으로 최대 속도로 보냈다. 실제 수집기 세션 코드(`collect::start::execute`)가 LOGIN·REG를 거쳐 받아 원문으로 썼다. 입력은 760종목 30분 치, 프레임 1,383,675개(압축 전 7.9GB)다.

| 원문 압축 | 경과 | 처리량 | 수집기 CPU | 써진 프레임 |
|---|---:|---:|---:|---:|
| zstd 3 | 4.9초 | 1.6GB/초 | 18.7초 | 1,383,675 |
| zstd 9 | 7.6초 | 1.0GB/초 | 29.6초 | 1,383,675 |

- **실제로 필요한 속도:** 실제 8종목 원문은 초당 p99 80.8KB, 최대 131KB였다. 760종목이면 p99 약 7.7MB/초, 최대 약 12.5MB/초다. zstd 9로도 약 80배 여유가 있다.
- **CPU:** 30분 치에 수집기 CPU 29.6초는 장중 평균 약 0.02코어다.

### ② 원문 → Parquet

위 "처리 방식"의 B(모든 FID와 부호 열)다. 2시간 15분 치에 49초, 4.1GB였다. 하루치 어림은 약 4분이다.

### ③ 서버가 구간 하나 만들기

시험용 서버가 모든 FID Parquet에서 한 종목의 5분 구간을 읽고, 복기 화면이 쓰는 열을 골라 구간 형식(`hoga-format`)으로 부호화해 보냈다. 가장 큰 종목 기준이다.

| 단계 | 압축 없음 | zstd 3 | brotli q5 | brotli q11 |
|---|---:|---:|---:|---:|
| Parquet 조회 | 15~17ms | 15~17ms | 15~17ms | 15~17ms |
| 구간 부호화 | 0.1ms | 0.1ms | 0.1ms | 0.1ms |
| 압축 | 0 | 0.5ms | 3.4ms | 약 570ms |
| 보내는 크기 | 312KB | 37KB | 32KB | 31KB |

### ④ 브라우저

기존 복기 화면(`crates/collector/page`)을 Playwright Chromium 158로 열었다. 종목마다 세 번씩, 압축 없음·zstd·brotli q5 세 방식으로 쟀다.

| 동작 | Parquet에서 요청 때 만듦 | 구간 파일을 미리 만들어 둠 (지금) |
|---|---:|---:|
| 처음 열기 (화면이 준비될 때까지) | 대부분 72~94ms, 가장 늦은 것 143ms | 42~65ms |
| 다른 시각으로 이동 | 40~46ms | 27ms |
| 10배속 재생, 프레임 간격 p95 | 16.7~16.8ms | 16.7~16.8ms |
| 재생 중 구간을 기다린 프레임 | 0 | 0 |

- **처음 열기:** 요청 때 만드는 쪽은 760종목 색인(2.5MB)을 받는 4~8ms가 들어 있다. 미리 만든 쪽은 8종목 색인이다.
- **압축 방식:** 세 방식 사이에 화면 시간 차이는 없었다.

### ④′ 브라우저의 구간 풀기

시험용 Worker가 구간마다 세 단계를 `performance.now()`로 재서 `postMessage`로 화면에 넘겼다.
- **요청 → 응답 헤더:** 서버 시간이 들어 있다.
- **본문 받기 끝:** 브라우저 내장 압축 풀기가 들어 있다.
- **구간 해독:** 배열로 푸는 시간이다.

종목마다 구간 24개다. 가장 큰 종목은 `S47500_AL`(실제 069500의 복제), 보통 종목은 `S47380_AL`(실제 005380의 복제)이다.

| 종목 | 전송 | 보내는 크기 | 요청→헤더 p50/p95 | 본문 받기 p50/p95 | 해독 p50/p95 | 합계 p50/p95 | 서버 조회 p50 |
|---|---|---:|---:|---:|---:|---:|---:|
| 가장 큰 | 압축 없음 | 219KB | 17.0 / 18.8 | 1.1 / 2.7 | 0.1 / 0.6 | 18.1 / 22.0 | 15.0 |
| 가장 큰 | zstd | 56KB | 17.7 / 25.3 | 1.2 / 2.2 | 0.1 / 0.7 | 19.3 / 27.6 | 15.6 |
| 가장 큰 | brotli q5 | 48KB | 21.9 / 23.5 | 0.7 / 2.0 | 0.1 / 0.7 | 23.2 / 24.6 | 15.9 |
| 보통 | 압축 없음 | 117KB | 16.2 / 19.2 | 0.5 / 1.5 | 0.1 / 0.8 | 17.0 / 19.5 | 14.7 |
| 보통 | zstd | 7KB | 16.6 / 28.4 | 0.6 / 1.7 | 0.2 / 0.8 | 18.0 / 29.0 | 14.9 |
| 보통 | brotli q5 | 6KB | 17.6 / 20.8 | 0.7 / 1.9 | 0.2 / 0.9 | 18.8 / 23.2 | 14.6 |

단위는 ms다.

- **압축 풀기를 따로 떼지 못한 이유:** 이 Chromium의 `DecompressionStream`은 gzip과 deflate만 풀고 brotli와 zstd는 풀지 못한다. 그래서 두 형식은 HTTP `Content-Encoding`으로만 보낼 수 있고, 압축 풀기는 브라우저 안에서 본문을 받는 단계에 들어간다.
- **압축 풀기 비용:** 본문 받기 시간이 압축 없음과 차이가 1ms보다 작았다. 압축 풀기는 1ms 미만으로 본다.
- **brotli의 헤더 시간이 더 긴 이유:** 서버의 압축 시간(3~5ms)이 들어 있어서다.
- **결론:** 브라우저 쪽 비용은 구간 하나에 1~2ms다. 구간 하나를 받는 시간 대부분은 서버의 Parquet 조회다.

## 측정에서 고른 것

- 정리는 B(Parquet 직접 쓰기, 종목 해시 버킷, 정렬, 정수 열 delta, zstd 3)로 한다. 병합 스레드 4개다.
- 모든 FID와 부호 열을 남긴다. 묶음은 122,880행이다.
- 구간 파일은 미리 만들지 않는다. 서버가 요청 때 만들어 zstd로 보낸다. 이동이 약 17ms 느린 대신 구간 파일 디스크와 그것을 만드는 단계가 없다.
- 원문은 zstd 9로 받는다. Parquet 검증을 마친 날의 원문은 오래 둘 필요가 없다.

## 아직 모르는 것

- 실제 하루 양과 그 하루치의 정리 시간·조회 시간. 지금은 5배 어림이다.
- 나머지 일곱 실시간 타입의 양과 열.
- 키움 명세로 열을 정했을 때의 스키마. 지금은 원문 앞부분에서 뽑았다.
- 네트워크를 거칠 때의 전송 시간. 원격으로 볼 때 압축이 얼마나 득이 되는지는 재지 않았다.

## 측정 코드

측정 코드는 이 PR에 넣지 않았다. 로컬 브랜치 `exp/store-bench`의 `crates/collector/examples/`에 있다.
- `store_bench.rs`: 복제, DuckDB 경로, 직접 쓰기, 조회
- `e2e_bench.rs`: 가짜 WS 수신, 시험용 서버
- `e2e_browser.mjs`: 브라우저 측정
- `e2e_worker.js`: 시간을 재는 Worker

개발용 의존성으로 `parquet`·`arrow-array`·`arrow-schema` 60을 더했다. 원자료는 그 작업 폴더의 `target/store-bench/results.txt`와 `target/store-bench/e2e/*.jsonl`에 있다.
