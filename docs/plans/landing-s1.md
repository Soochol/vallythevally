# S1 스크롤리텔링 랜딩과 실제 로그인 연동 실행 플랜

작성일 2026-11-18. 승인 시점의 기록이며 구현 중 바뀐 것은 반영하지 않는다.

## 사용자가 풀려는 문제

계정 모드에서 로그아웃 상태로 앱을 열면 지금은 가운데에 로그인 카드 하나만 있는 화면(`web/src/features/account/LoginScreen.tsx`)이 보인다. 사용자는 이 자리를 제품을 소개하는 랜딩 페이지로 바꾸고 싶어 한다. 로그인은 화면의 중심이 아니라 상단 막대의 단추 하나여야 하고, 누르면 실제 로그인 창이 열려 실제 백엔드로 로그인되어야 한다. 사용자의 말은 다음과 같다.

1. "메인 랜딩 페이지 만들고 거기서 로그인 기능도 제안해줘 claude artifact 활용. 렌딩 페이지는 너가 생각하는 화려하고 세련된 것 몇개 제안해줘"
2. "컨셉이 잘못된게, 로그인은 상단에 있으면되고 중심이 되면 안돼지"
3. "스크롤리텔링 방식으로 3가지 제안해줘"
4. "s1으로하고 실제 로그인 창도 나오게해주고 백엔드와 연동시켜줘서 정상적으로 운영할 수 있게해줘 ."

고른 시안은 S1 "그려지는 차트"다. 원본은 `/home/dev/.claude/orch/requests/landing-s1/Scrolly1.dc.html`이다. 이 파일은 저장소 밖에 있으며 읽기만 한다. Claude Design 캔버스는 https://claude.ai/artifact/1fEWtce3Qe5kXDkh7XhaoS 의 "스크롤리텔링" 페이지, "S1 · 그려지는 차트" 보드다.

## 지금 코드의 사실 (기준 커밋 `8e3e361e`)

- `web/src/App.tsx`의 `ChartRoute`는 계정 상태가 `signed_out`이면 `LoginScreen`, `owner_mismatch`이면 `ReplaceLocalScreen`을 그린다. 로컬 전용 모드에서는 계정 상태가 `signed_out`이 되지 않으므로 로그인 화면이 없다.
- `LoginScreen`은 `startLogin(provider)`(`POST /api/account/login`)로 계정 서버 시작 주소를 받아 `markLoginStarted()` 뒤 `window.location.assign`으로 이동한다. 실패하면 `role="alert"`로 이유를 보이고 단추를 다시 켠다. `?login=error&reason=…`로 돌아온 실패 문장(`loginFailure.ts`)은 `role="status"`로 한 번 보이고 지운다.
- 흐름의 나머지(커넥터 `/api/account/login` → 계정 서버 `/v1/auth/{provider}/start` → IdP → 계정 서버 callback → `http://127.0.0.1:<포트>/auth/complete`)는 구현되어 있고 `crates/server/tests/account_login.rs`, `crates/account-server/tests/login.rs`가 가짜 IdP로 시험한다.
- `html, body, #root`는 `overflow: hidden`이다(`web/src/styles/index.css`). 긴 페이지는 자기 스크롤 컨테이너가 있어야 한다.
- 앱 글꼴은 Pretendard 하나다. Tailwind의 글자 크기는 `--fs-xs`~`--fs-xl` 토큰만 남기고 기본값을 지웠다. 랜딩의 큰 제목 크기는 토큰에 없다.
- 시안 문구의 "차트를 최대 8개까지"는 `WINDOW_KINDS.chart.maxCount = 8`(`web/src/layout/kinds.ts`)과 맞는다.
- 계정 서버의 로그인 쿠키 이름은 하나(`__Host-vally_login`, 루프백 http에서는 `vally_login`)다. `start`가 호출마다 `pending_logins` 행을 더하고 10분 뒤 지운다. 행 수에 한도가 없다. Google authorize 주소에 `prompt`가 없다.
- e2e는 로그인 화면을 `heading "로그인"`으로 찾는다(`web/e2e/account-login.spec.ts` 여러 곳, `web/e2e/setup-wizard.spec.ts`의 needs_choice 시험 한 곳).
- 계정 서버와 커넥터를 함께 띄워 실제 브라우저로 로그인해 보는 도구는 없다. `verify-vally` 스킬은 로컬 전용 모드의 커넥터만 띄운다. 가짜 IdP(`crates/account-server/src/fake_idp.rs`)는 `fake-idp` 기능 뒤의 라이브러리 모듈이고 실행 파일이 없다.

## 확정된 결정

사용자가 직접 정했거나 요청에 적혀 있다.

1. 랜딩은 S1 "그려지는 차트" 시안을 따른다. 고정 상단 막대(왼쪽 vally 로고, 오른쪽 "로그인" 단추 하나), 400vh 고정 구간에서 스크롤 진행률에 따라 그려지는 라임색 차트 선과 네 장의 큰 문장, 위쪽 진행 막대, 고정 구간 뒤의 "서버에 가는 것은 셋업뿐입니다" 라임 띠, 바닥글이다.
2. 로그인은 상단 막대의 단추 하나다. 화면의 중심에 두지 않는다.
3. 단추를 누르면 실제 로그인 창(Google·네이버 선택)이 열리고, 고르면 지금 있는 커넥터 로그인 흐름으로 실제 로그인이 된다.
4. 색은 앱 토큰(`web/src/styles/tokens.css`의 라임 다크)을 쓰고, 글꼴과 부품은 `docs/design-system.md`를 따른다.
5. 로그인 실패 문장, 로컬 전용 모드, 계정 바꾸기 확인 화면, 첫 실행 마법사는 깨지지 않는다. 기준은 `web/e2e/account-login.spec.ts`, `web/e2e/setup-wizard.spec.ts`다.
6. 휴대폰 폭과 `prefers-reduced-motion`에서도 쓸 수 있다.
7. 실제 Google·네이버·키움은 호출하지 않는다(AGENTS.md, ADR 0023).

## 스스로 정한 결정과 이유

### 랜딩의 자리

| # | 결정 | 이유 |
|---|---|---|
| L1 | 랜딩은 커넥터가 서빙하는 앱 안에 둔다. 계정 모드에서 `signed_out`일 때 `LoginScreen` 자리에 그린다. `LoginScreen.tsx`는 지운다. 공개 웹사이트는 만들지 않는다. | 로그인은 커넥터가 `state`와 PKCE 쌍을 만들어야 시작된다(ADR 0023). 공개 사이트의 단추로는 커넥터의 로그인을 시작할 수 없다. 같은 자리를 쓰면 `signed_out` 밀어 주기, 로그아웃, 계정 삭제 뒤 돌아오는 화면이 그대로 랜딩이 된다. |
| L2 | 로컬 전용 모드와 `owner_mismatch`, `signed_in`의 화면은 바꾸지 않는다. | 랜딩은 로그인이 필요한 사람에게만 뜻이 있다. 로컬 전용 모드에는 로그인이 없다(ADR 0023). |
| L3 | `App.tsx`에서는 `LoginScreen`을 새 컴포넌트로 바꾸는 줄만 고친다. 랜딩은 새 기능 폴더 `web/src/features/landing/`에 둔다. | 다른 플랜(`collector-build`의 `web-collector-board`)이 `App.tsx`에 손댈 수 있다. 바꾸는 줄이 적으면 충돌이 작다. |

### 로그인 창

| # | 결정 | 이유 |
|---|---|---|
| L4 | 로그인 창은 상단 "로그인" 단추에 붙어 열리는 비모달 창이다. 공통 겹침 표면(`.ui-popover`)을 쓰고 `role="dialog"`, 접근성 이름 "로그인", 제목 "로그인"을 둔다. 단추는 `aria-expanded`로 열림을 알린다. Esc나 창 밖 누르기로 닫고, 닫으면 초점이 단추로 돌아간다. | 시안의 구성이다. 겹침 표면을 새로 정의하지 않는다는 디자인 시스템 규칙을 따른다. 제목을 "로그인"으로 두면 지금의 접근성 이름이 이어진다. |
| L5 | 창 안에는 지금 `LoginScreen`의 내용(Google로 로그인, 네이버로 로그인, 고유 번호만 받는다는 문장, Google과 네이버는 다른 계정이라는 문장)을 그대로 옮긴다. 시작 실패는 창 안에 `role="alert"`로 보이고 단추를 다시 켠다. 이동하는 동안은 두 단추를 끄고 "<provider> 로그인 화면으로 이동합니다"를 `role="status"`로 보인다. | 로그인 흐름의 동작을 바꾸지 않고 자리만 옮긴다. 시안의 "이동하지 않습니다"는 시안용 흉내라 쓰지 않는다. |
| L6 | `?login=error`로 돌아온 실패 문장이 있으면 랜딩을 열 때 로그인 창을 열어 둔 채로 시작하고, 창 안에 실패 문장을 `role="status"`로 보인다. 한 번 보인 문장은 지금처럼 지운다. | 실패하고 돌아온 사람의 다음 행동은 다시 로그인이다. 문장이 다시 누를 단추 옆에 있어야 한다. 창이 닫혀 있으면 실패 문장이 보이지 않는다. |
| L7 | 랜딩에는 상단 단추 말고 다른 로그인 단추를 두지 않는다. 상단 막대는 스크롤하는 동안 늘 보인다. | 사용자의 2번 말이다. |

### 스크롤 이야기

| # | 결정 | 이유 |
|---|---|---|
| L8 | 랜딩의 바깥 요소가 `h-dvh overflow-y-auto` 스크롤 컨테이너다. 스크롤 진행률은 고정 구간 안의 위치로 JS가 계산해 CSS 변수(`--p`, 0~1)로 넘기고, `requestAnimationFrame`으로 한 프레임에 한 번만 쓴다. 스크롤 수신기는 passive다. 차트 선의 `stroke-dashoffset`, 진행 막대의 `scaleX`, 네 장의 투명도가 이 변수를 읽는다. | `body`가 `overflow: hidden`이라 페이지 스크롤이 없다. CSS 스크롤 구동 애니메이션(`animation-timeline`)은 브라우저 지원이 고르지 않다. 시안이 같은 방식이다. |
| L9 | 지금 보이는 장의 번호(1~4)를 이야기 구간의 `data-step` 속성으로 내놓는다. | e2e가 픽셀이나 투명도 대신 앱이 내놓는 상태를 기다리게 한다(`docs/e2e-tests.md`). |
| L10 | `prefers-reduced-motion: reduce`이면 고정 구간과 스크롤 구동을 끈다. 네 장을 문서 흐름에 차례로 놓아 모두 보이게 하고, 차트 선은 처음부터 다 그려 두고, 진행 막대와 "스크롤" 안내는 숨긴다. | 움직임을 줄인 사람에게 스크롤로 바뀌는 큰 화면은 그대로 움직임이다. 내용은 하나도 잃지 않는다. |
| L11 | 휴대폰 폭에서도 같은 구성이다. 큰 제목은 화면 폭에 맞춰 줄고 가로 스크롤이 생기지 않는다. 로그인 창은 좌우 16px 여백 안에 들어온다. | 요청의 6번이다. 커넥터는 PC에서 돌지만 같은 PC의 좁은 창도 휴대폰 폭이다. |
| L12 | 첫 장의 본문은 "키움 REST API로 도는 개인 차트 워크스페이스."까지만 쓴다. 시안의 "스크롤하면 차트가 그려집니다"는 화면 아래의 "스크롤" 안내가 맡고, 움직임을 줄이면 둘 다 없다. 나머지 문구는 시안 그대로다. | 움직임을 줄인 화면에서 차트는 스크롤로 그려지지 않는다. |
| L13 | 큰 제목과 본문 크기는 `tokens.css`에 새 글자 크기 토큰으로 더하고 `index.css`의 Tailwind 연결에 잇는다. 글꼴은 Pretendard 하나를 쓰고 시안의 Noto Sans KR·Space Grotesk는 들이지 않는다. 로고는 시안의 라임 사각형 V 표시를 토큰 색으로 그린다. `docs/design-system.md`에 랜딩 절을 더한다. | 토큰 밖의 크기를 막아 둔 규칙을 지킨다. 외부 글꼴을 들이면 오프라인 커넥터에서 불러오지 못한다. |
| L14 | 용어집에 "랜딩"을 더한다. 계정 모드에서 로그아웃 상태일 때 보이는 첫 화면이다. | 앞으로 작업과 리뷰가 같은 이름을 쓴다. |

### 운영 전에 고칠 것 (로그인 리뷰의 여섯 항목)

| # | 항목 | 처리 | 이유 |
|---|---|---|---|
| O1 | 실제 Google·네이버로 돌려 본 적이 없고, 앱 등록·호스팅·도메인·TLS·배포 방식이 없다 | 사람이 할 일은 아래 "사용자가 정해야 하는 결정"과 "사용자 할 일"에 적는다. 코드 쪽으로는 운영 문서(`docs/account-server-operations.md`)를 쓰고(`acct-ops-docs`), 계정 서버·커넥터·가짜 IdP를 함께 띄워 실제 브라우저로 랜딩에서 로그인하는 확인을 `verify-vally`에 더한다(`login-verify`). | 실제 IdP 없이도 랜딩 단추 → 커넥터 → 계정 서버 → IdP 자리 → `/auth/complete` → 로그인 상태까지 진짜 프로세스로 확인할 수 있어야 "백엔드와 연동"을 보일 수 있다. e2e는 응답 고정값이라 백엔드를 거치지 않는다(ADR 0016). |
| O2 | 계정 서버에 요청 횟수 제한이 없고, 인증 없는 `start`가 호출마다 `pending_logins` 행을 더한다 | 넣는다(`acct-login-harden`). 아직 만료되지 않은 대기 로그인 수에 한도(기본 10,000)를 두고, 넘으면 행을 더하지 않고 IdP로 보내지 않고 503 HTML 안내와 `Retry-After`를 낸다. 한도는 동시 `start`에서도 넘지 않는다. IP별 제한은 계정 서버가 아니라 앞단 리버스 프록시가 맡고 운영 문서에 설정 예를 적는다. | DB가 끝없이 자라는 것을 코드로 막는다. 계정 서버는 프록시 뒤에서 진짜 클라이언트 IP를 알려면 전달 헤더를 믿어야 하는데, 그 신뢰 설정은 배포 방식(사용자 결정 1)에 달려 있다. 전체 한도만으로는 공격자가 한도를 채워 로그인을 잠시 막을 수 있으므로 IP별 제한을 프록시에 둔다. |
| O3 | 같은 브라우저에서 로그인 두 개를 동시에 시작하면 쿠키 이름이 같아 앞 것이 실패한다 | 넣는다(`acct-login-harden`). 쿠키 이름에 그 로그인의 IdP `state`를 붙이고(`__Host-vally_login_<state>`, 루프백 http는 `vally_login_<state>`), callback은 질의의 `state`로 자기 쿠키를 찾고 그 쿠키만 지운다. | 랜딩을 두 탭에서 열고 차례로 누르면 앞 탭은 계정 서버의 실패 페이지에 멈춘다. 고치는 범위가 `app.rs` 몇 줄이다. 쿠키는 10분 뒤 사라진다. |
| O4 | Google 로그인에 `prompt=select_account`가 없다 | 넣는다(`acct-login-harden`). Google authorize 주소에 `prompt=select_account`를 더한다. 네이버는 계정 고르기 매개변수가 없어 그대로 둔다. | 계정 바꾸기 확인 화면(D25)이 있는데 다른 Google 계정으로 들어갈 길이 브라우저 로그아웃뿐이다. O6의 위험도 사용자가 보는 한 단계로 줄어든다. |
| O5 | 다른 기기의 토큰을 끊을 방법이 없다(계정 삭제뿐) | 이번 범위 밖. 사용자 결정 4로 둔다. | 계정 서버 API, 커넥터 라우트, 계정 메뉴 화면까지 세 층의 새 기능이고 랜딩과 관계가 없다. 그동안의 길은 그 PC에서 로그아웃하거나 계정을 지우는 것이다. |
| O6 | 같은 PC의 악성 프로그램이 자기 `code_challenge`로 만든 시작 주소로 코드를 받을 수 있는 루프백 방식의 한계가 ADR 0023에 없다 | 넣는다(`acct-ops-docs`). ADR 0023 로그인 절에 받아들인 한계로 적는다. 같은 사용자로 도는 프로그램은 상태 파일(`account.json`, 600)도 직접 읽을 수 있으므로 이 길이 새 능력을 주지 않는다는 것, Google은 계정 고르기 화면이 한 단계 더 보인다는 것을 함께 적는다. | 코드로 막을 수 없는 한계이고, 적어 두지 않으면 리뷰마다 다시 나온다. |

### 작업 방식

| # | 결정 | 이유 |
|---|---|---|
| L15 | 기존 e2e의 "로그인 화면이 보인다" 단언(`heading "로그인"`)은 랜딩 표시로 바꾼다. 로그인 단추를 누르는 시험은 먼저 로그인 창을 연다. 시험이 확인하던 동작(셋업을 읽지 않음, 시작 요청 본문, 실패 문장과 주소창 정리, 단추 다시 켜기, 화면 안에 들어옴)은 하나도 빼지 않는다. | 화면 구조가 바뀌어 찾는 방법만 바뀐다. 검증을 약하게 하지 않는다. |
| L16 | 새 크레이트나 새 병합 검사 항목을 만들지 않는다. `login-verify`가 더하는 가짜 IdP 실행 파일은 `fake-idp` 기능이 있어야 빌드된다(`required-features`). | 배포 빌드에 가짜 IdP가 들어가지 않는다. 기존 `account-server-test`가 계정 서버 변경을 검사한다. |

## 작업과 순서

| 작업 | 내용 | 방식 | 방식의 이유 | 뒤에 |
|---|---|---|---|---|
| `landing-s1` | 랜딩 화면, 상단 막대의 로그인 창, 스크롤 이야기, 움직임 줄이기·휴대폰 폭, 기존 e2e 맞추기와 새 랜딩 e2e, 토큰·디자인 문서·용어집 | `poteto` | 로그인 흐름의 입구를 바꾸고 여러 부품에 걸친 새 화면이다 | 없음 |
| `acct-login-harden` | 계정 서버의 대기 로그인 한도, 로그인별 쿠키 이름, Google `prompt=select_account` | `poteto` | 인증·보안 코드와 동시 `start`의 한도 | 없음 |
| `login-verify` | 가짜 IdP 실행 파일, `verify-vally`의 계정 모드(계정 서버·가짜 IdP·계정 모드 커넥터), 랜딩에서 실제 로그인하는 기능 파일 | `poteto` | 여러 프로세스를 띄우고 정리하며 인증 흐름 전체를 지난다 | `landing-s1`, `acct-login-harden` |
| `acct-ops-docs` | ADR 0023의 루프백 한계, 계정 서버 운영 문서 | `basic` | 문서만 고친다 | `acct-login-harden`, `login-verify` |

병렬: 처음에 `landing-s1`과 `acct-login-harden`이 함께 돈다. 둘이 끝나면 `login-verify`, 그 뒤에 `acct-ops-docs`가 돈다.

순차로 둔 이유:

- `login-verify`는 `landing-s1`의 랜딩과 로그인 창을 브라우저로 누르고, `acct-login-harden`이 바꾼 쿠키 이름과 Google 주소를 지난 계정 서버를 띄운다.
- `acct-ops-docs`는 `acct-login-harden`의 한도·쿠키 동작과 `login-verify`의 확인 명령을 문서에 그대로 적는다. 먼저 쓰면 없는 동작을 적게 된다.

겹치는 파일: `landing-s1`과 `acct-login-harden`은 겹치는 파일이 없다. `login-verify`와 `acct-login-harden`은 둘 다 `crates/account-server/`를 고치지만 순차다.

## 다른 플랜과 겹치는 곳

`collector-build` 플랜이 돌고 있다. 그 가운데 `web-collector-board`(대기 중)는 웹에 수집 현황판을 더하며 `App.tsx`나 시스템 설정 메뉴에 손댈 수 있다. `landing-s1`은 `App.tsx`에서 한 줄만 바꾸고 PR 전에 최신 `main`으로 맞춘다. `connector-collector-api`(대기 중)는 계정 서버를 고치지 않는다고 지시서에 적혀 있다. 그 밖에 이 플랜의 파일을 고치는 열린 PR은 없다.

## 범위 밖

- 공개 웹사이트(커넥터 밖의 소개 페이지). L1의 이유다.
- 다른 기기 토큰 끊기(O5).
- 실제 배포 실행: 서버 마련, 도메인, TLS 인증서, 리버스 프록시 설치, 백업 작업 등록, 커넥터 설치본과 자동 업데이트. 운영 문서는 절차와 예만 적는다.
- Google·네이버 앱 등록과 실제 client id·secret 넣기. 사람만 할 수 있다.
- 실제 Google·네이버·키움에 접속하는 시험이나 확인.
- 로그인 창 밖의 계정 화면(계정 메뉴, 계정 바꾸기 확인 화면, 마법사)의 디자인 변경.
- 랜딩의 다국어, 분석 도구, 외부 글꼴.

## 사용자가 정해야 하는 결정

구현을 막는 결정은 없다. 모든 작업은 위의 권장안으로 시작한다. 실제로 다른 사람이 로그인하게 하려면 아래가 정해져야 한다.

1. **계정 서버를 어디에 띄울지**: 호스팅과 도메인. 권장은 작은 VM 하나에 TLS 리버스 프록시(예: Caddy)를 두고, 계정 서버는 `127.0.0.1:8090`에 묶고, SQLite를 매일 파일로 백업하는 것이다. 정해지면 `VALLY_ACCOUNT_PUBLIC_URL`이 `https://<도메인>`이 된다.
2. **IdP 앱 등록**: Google Cloud에서 OAuth 클라이언트(웹 애플리케이션)를, 네이버 개발자센터에서 애플리케이션을 만들고 callback 주소 `https://<도메인>/v1/auth/google/callback`, `https://<도메인>/v1/auth/naver/callback`을 등록한다. 다른 사람이 로그인하려면 Google OAuth 동의 화면 게시와 네이버 검수가 필요할 수 있다(실제 콘솔에서 확인 필요).
3. **IP별 요청 제한 값**: 권장은 리버스 프록시에서 `/v1/auth/*/start`를 IP당 분당 10회 정도로 제한하는 것이다. 계정 서버 안의 전체 한도(10,000)는 코드에 들어간다(O2).
4. **다른 기기 토큰 끊기를 다음에 만들지**(O5): 만들면 계정 서버 API, 커넥터 라우트, 계정 메뉴의 "다른 PC 모두 로그아웃" 단추가 한 플랜이 된다.
5. **커넥터를 사람들에게 어떻게 줄지**: 지금은 소스 빌드뿐이다. 배포본에 기본 계정 서버 주소를 넣을지, OS별 설치본을 만들지는 별도 플랜이다.

검증을 약하게 하는 작업은 없다. 검사 단계 삭제, 시간 제한 증가, `chute.toml`의 `paths` 축소를 하지 않는다. 기존 e2e 단언은 찾는 방법만 바뀐다(L15).

## 사용자 할 일 (실제 운영을 시작하는 순서)

1. 결정 1대로 서버와 도메인을 마련하고 TLS 리버스 프록시를 세운다.
2. 결정 2대로 Google·네이버 앱을 만들고 callback 주소를 등록한다.
3. 계정 서버의 env 파일(권한 600)에 공개 주소, Google·네이버 client id·secret을 넣고 `vally-account`를 띄운다. 비밀값은 저장소·이슈·PR에 적지 않는다. 절차는 `acct-ops-docs`가 쓰는 `docs/account-server-operations.md`를 따른다.
4. 각 PC의 커넥터에 `VALLY_ACCOUNT_SERVER_URL=https://<도메인>`을 넣고 띄운다.
5. 랜딩에서 Google과 네이버로 한 번씩 직접 로그인해 마법사가 열리는지 본다. 이것이 실제 IdP로 처음 도는 확인이다.
