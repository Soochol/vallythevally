# 키움 대기열 속도: 공용 260ms 간격을 TR별 간격과 호출 제한 재시도로 바꾸기

작성일 2026-11-19. 승인 시점의 기록이며 구현 중 바뀐 것은 반영하지 않는다.

## 사용자가 풀려는 문제

종목을 바꾸면 차트·호가주문창이 1.6~2.3초 뒤에야 다 찬다. 주문 한 건도 키움 응답이 빨라도 0.78초 아래로 못 내려간다. 두 조사(switch-latency, order-latency)는 같은 원인을 꼽았다. 키움 응답(실서버 6~70ms)이 아니라 서버 키움 대기열의 **260ms 공용 전송 간격**(`crates/server/src/kiwoom/rest.rs` `SEND_SPACING`)이 모든 TR을 한 줄로 세운다. 전환 한 번에 TR 7~9건이 나가므로 `건수 × 260ms`가 걸린다.

사용자 요청(원문): "이걸 제거하고, 호출 제한 걸리면 어떻게 되지, 기다리라고 나오지 않을까? 그럼 재시도 하면 되잖아. 너가 제한한것도 적용 하고"

## 확정된 결정

1. 공용 260ms 간격을 없애고 키움이 정한 단위(TR)마다 간격을 둔다. 간격은 TR마다 250ms(초당 4회, 한도 5회의 80%, hoga-ops와 같은 여유)다. 다른 TR은 기다리지 않고 바로 나간다. 아래 "사용자가 정해야 하는 결정" 1에서 A안을 고른다는 전제다.
2. 호출 제한(`RateLimit`)을 받으면 **그 TR만** 1초 쉬고 같은 요청을 다시 보낸다. 다른 TR은 계속 나간다. 응답의 `유량=N`이 5보다 작으면 그 TR의 간격을 N에 맞춰 늘린다(서버가 켜져 있는 동안).
3. 같은 요청이 세 번 호출 제한을 받으면 지금처럼 실패로 돌려주고 공용 관문을 30초 닫는다(ADR 0009 반복 예산 유지). TR별 간격이 맞으면 일어나지 않아야 하고, 일어나면 우리 가정(여러 TR 합계 한도 없음)이 틀렸다는 신호라 멈추는 쪽이 안전하다.
4. 주문 쓰기(`kt10000`~`kt10003`)는 네 TR을 **한 묶음**으로 묶어 초당 4회다. 공식 문구가 "주문 TR 초당 5회"이고 주문 TR끼리 독립인지는 재지 않았다. 주문이 여전히 조회보다 앞에 선다.
5. 조사 보고서의 줄이는 방법 중 a(취소된 대기 요청 빼기)와 b(`ka10095` 한 번만)를 넣는다. f(실시간 구독으로 대체)는 범위 밖이다.

## 스스로 정한 결정과 이유

1. **c·d·e는 따로 작업을 두지 않는다.**
   - c(화면에 먼저 필요한 것을 앞으로)와 e(계좌 poll을 낮은 우선순위로): 전환 때 나가는 TR(`ka10081`·`ka10080`·`ka10004`·`ka10095`·`ka10003`·`ka10001`·`kt00011`)과 계좌 poll(`kt00018`·`kt00007`·`ka10075`)은 서로 다른 TR이다. TR별 간격에서는 서로 기다리지 않으므로 순서 칸을 더해도 줄어드는 시간이 없다. 같은 TR 안의 순서는 지금 우선순위(주문 → 화면 → 복구 → 배경)가 이미 정한다. 사용자가 결정 1에서 C안을 고르면 c·e가 다시 효과가 있으니 그때 작업을 더한다.
   - d(`ka10001` 상·하한가 당일 캐시): 이미 들어가 있다. 기본 정보 조회(`http.rs` `fundamentals`)가 받은 상·하한가를 주문 쪽 기억(`trading/memory.rs` `PriceBands`, #696)에 넣고, 주문 확인(`check_price_band`)은 그 날 기억이 있으면 `ka10001`을 부르지 않는다. 전환 때의 `ka10001`은 정보란 2쪽(시가총액·PER 등, plan-order-panels2의 `order-info-pages`)이 계속 쓰고, 새 종목이라 캐시로 없앨 수 없다. TR별 간격에서는 다른 TR과 함께 나가 기다리지 않는다.
2. **a를 공용 간격 작업 뒤에 따로 둔다.** 두 작업 모두 `rest.rs`의 같은 선택 함수(`next_step`)를 고친다. 간격이 없어져도 빠르게 종목을 넘기면 같은 TR(예: 종목마다 `ka10081`)이 초당 4회로 줄을 선다. 포기한 종목의 요청을 빼야 마지막 종목이 바로 나간다.
3. **시험용 간격 손잡이는 지금 뜻 그대로 둔다.** `KiwoomRest::with_send_spacing`·`build(spacing)`·`KIWOOM_SEND_SPACING_MILLIS`는 지금처럼 "모든 TR 사이의 최소 간격"이고 TR별 간격은 끈다. 이 손잡이로 "대기열에 서 있는 요청"을 만드는 시험(`trading/tests.rs`, `tests/kiwoom_link.rs`, `tests/screener_update.rs`)이 고치지 않고 그대로 돈다. 그래서 공용 간격 작업이 `trading/**`·`http.rs`를 건드리지 않고, 같은 시각의 plan-order-panels2 작업과 겹치지 않는다. 바뀌기 전과 뒤를 같은 시험에서 잴 수도 있다(손잡이 260ms = 지금, 기본값 = 새 방식).
4. **주문 1700 재시도는 대기열 안에서 한다.** 대기열이 같은 명령을 다시 보내고, 주문 쪽 판정(`orders.rs` `settle`)과 저널은 그대로다. 끝내 429면 지금처럼 확정 거절이다. 다시 보내기 전에 주문 사용 확인(`admit`)을 다시 지난다. ADR 0029("한 번만 보낸다")는 같은 시각 `order-account-digits`가 고치므로 이 플랜은 손대지 않고, 새 ADR에 예외(429/1700은 키움이 받지 않은 요청이라 다시 보낸다)를 적는다.
5. **순서: plan-order-panels2가 먼저다.** `order-info-pages`가 정보란의 `/api/quotes` 5초 조회(`ladder-quote`)를 새 당일 요약 조회로 바꾼다. b는 그 결과 위에서 두 훅을 하나로 합쳐야 하므로 그 뒤에 한다. 공용 간격·a 작업은 plan-order-panels2와 파일이 겹치지 않아 병렬이다.
6. **b 작업(`queue-one-quote`)은 `tasks.json`에 넣지 않는다.** `after`는 이 탭 계획에 올라간 작업만 가리킬 수 있는데 plan-order-panels2는 아직 적재 전이다. 지시서는 써 두었고, 오케스트레이터가 plan-order-panels2를 적재한 뒤 `plan add`로 `--after order-info-pages`를 달아 더한다(아래 "작업" 표의 명령).
7. 측정은 합성 transport와 tokio 멈춘 시계로 한다. 실서버 키움을 제한까지 두드리지 않는다.

## 사용자가 정해야 하는 결정

### 1. 전송 방식 (권장 A)

| | A. TR마다 초당 4회 + 제한 오면 그 TR만 1초 쉬고 재시도 (권장) | B. 간격 0 + 제한 오면 재시도 (요청 원안 그대로) | C. 지금 간격(초당 4회 합계) 유지 + 순서만 조정(c·e) |
|---|---|---|---|
| 종목 전환 | 약 0.1초 | 제한이 안 오면 A와 같음 | 차트·호가 0.3~1.0초 빨라짐, 마지막은 그대로 1.6~2.3초 |
| 주문 1건 | 키움 응답 × 3 안팎 | 같음 | 0.78초 그대로 |
| 제한 응답 | 거의 안 옴(한도의 80%) | 같은 TR이 이어지는 곳(과거 봉 페이지 넘기기, 스크리너 일봉 수천 건)에서 매번 옴 → 1초씩 쉼, 세 번이면 조회 전체 30초 멈춤 | 안 옴 |
| 위험 | 공식 문구 "계좌별 초당 5회"가 TR 합계라는 뜻이면 한 번에 여러 TR을 보낼 때 제한이 온다. 그러면 그 TR만 1초 뒤 다시 나가고(최악 1초 늦음), 반복되면 30초 멈춤으로 드러난다 | A의 위험 + 제한 응답 반복. 제재 사례는 못 찾았지만 확인한 것도 아님 | 없음 |

### 2. 주문 쓰기가 제한 응답(429/1700)을 받으면 (권장 가)

- **가. 1초 뒤 같은 주문을 최대 두 번 더 보낸다(권장).** 지금도 429는 "키움이 받지 않음"(확정 거절)으로 판정하므로 다시 보내도 중복 주문이 되지 않는다는 판정과 맞다. 다른 실패(응답 없음, 5xx, 읽을 수 없는 응답)는 지금처럼 절대 다시 보내지 않는다.
- **나. 다시 보내지 않는다.** 지금처럼 바로 "키움이 거절"을 보이고 사용자가 다시 누른다.

A안에서 주문은 묶음 초당 4회라 이 응답은 드물다.
