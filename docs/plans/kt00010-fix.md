# 키움 업무 거절 `[2000]`이 조회 경로를 재시작 전까지 멈추는 문제

작성일: 2026-11-19. 승인 시점의 기록이며 구현 중 바뀐 것은 반영하지 않는다.

기준: `origin/main` a144ef93. 조사 보고는 `/home/dev/.claude/orch/reports/kt00010-root/kt00010-root.md`(읽기 전용 참고, 저장소 밖)이고, 이 플랜은 그 보고의 개선안 3.1·3.2·3.3("PR 1")을 맡는다.

## 사용자가 풀려는 문제

앱 상태 막대에 다음 문구가 떴다.

> 키움 조회 멈춤: 키움이 알 수 없는 실패를 돌려줬습니다(kt00010, HTTP 200, return_code 20, 상세 [2000]). 운영자가 확인하고 서버를 다시 켤 때까지 이 경로로 보내지 않습니다

사용자는 원인 조사를 시켰고("근본 원인까지 찾아서 개선안까지 도출하도록 시켜줘"), 조사 보고를 본 뒤 "kt00010 PR 1 진행해줘"라고 했다.

조사로 확인한 것:

- `[2000]`은 키움 계좌 업무 시스템의 거절을 감싸는 공통 바깥 코드다. 실제 사유는 `[2000](571489:장이 열리지 않는 날입니다.)`처럼 괄호 안 6자리로 온다. 휴장 전용 코드가 아니다.
- 서버 코드표(`crates/server/src/kiwoom/error.rs`의 `CODE_TABLE`)에 `[2000]`이 없어 `Unknown`이 되고, `Unknown`은 그 TR 경로(kt00010 전체)를 서버를 다시 켤 때까지 멈춘다. 정상적인 업무 거절 하나가 매수·매도·모든 종목의 kt00010을 막고, 브라우저에는 `manualActionRequired=true`로 "키움 조회 멈춤"이 뜬다.
- 서버는 `[` 뒤 네 자리만 읽어서 안쪽 6자리 사유가 어디에도 남지 않았다.
- 호가주문창은 열릴 때마다 kt00010을 매도(`trde_tp=1`)와 매수(`trde_tp=2`)로 하나씩 보낸다. 보유하지 않은 종목의 매도 쪽 조회는 571455로 거절된다는 외부 실측이 있다(가장 유력한 원인, 추정).

## 확정된 결정 (사용자·요청)

- 범위는 보고서의 3.1 + 3.2 + 3.3이다.
  - 3.1: `[2000]`을 새 범주 업무 거절(`BusinessRejected`)로 분류한다. 조회 단계 정책은 재시도·경로 정지 없이 그 요청만 실패다. 브라우저에는 `manualActionRequired=false`, 문구는 "멈춤"이 아니라 거절 사유다. "우리 코드의 버그" 로그를 남기지 않는다.
  - 3.2: `[2000](NNNNNN:…)`의 안쪽 6자리를 숫자로만 읽어 실패 증거와 `키움 조회` 로그 줄에 남긴다. `return_msg` 원문은 담지 않는다(ADR 0009·`Note`의 원문 비보관 원칙). 알려진 사유 표(571489, 571455, 508975, 503721, 501307)는 문구·로그용이다.
  - 3.3: 호가주문창이 매도 쪽 kt00010을 보내지 않는다. 매도 가능 수량은 이미 받는 kt00018의 `sellableQuantity`(`trde_able_qty`)를 쓴다. 매수 쪽은 그대로 kt00010이다(ADR 0029).
- 범위 밖(사용자 승인 전): 3.4 코드표에 없는 코드의 기본 정책 변경(ADR 0009 "알 수 없음" 개정), 3.5 재시작 없이 경로를 푸는 수단과 상태 막대 문구의 TR 이름화. ADR 0009의 "목록에 없는 코드 = 알 수 없음" 원칙은 바꾸지 않는다.

## 스스로 정한 결정과 이유

1. **작업을 서버(3.1+3.2)와 웹(3.3) 둘로 나누고 병렬로 둔다.** 두 작업의 `paths`가 같은 파일에 닿지 않는다. 서버 작업이 `web/src/api/http.ts`의 사유 목록과 생성 타입 `ApiErrorReason.ts`를 고치지만, 웹 작업은 `web/src/features/order/`와 주문창 e2e만 고친다. 웹 작업은 새 사유 이름에 기대지 않는다: 매도 쪽 조회를 없애는 일과 매수 가능 조회 실패 문구를 보이는 일은 `manualActionRequired`와 `message`만 쓴다. 3.3만 먼저 들어가도 매수 쪽에 업무 거절이 오면 여전히 경로가 멈추지만(보고서 3.3 주의), 둘 다 이 플랜에서 병합되므로 순서를 강제하지 않는다. 사용자가 "한 PR이어도 되고, 파일이 겹치지 않으면 나눠 병렬로 해도 된다"고 플래너에게 맡겼다.
2. **새 범주 이름은 `Category::BusinessRejected`, 브라우저 사유는 `ApiErrorReason::BusinessRejected`(`business_rejected`)다.** 보고서의 대안 (가) `InvalidRequest`로 넣기는 휴장·미보유 같은 정상 거절을 "우리 코드의 버그"와 `Internal`로 보이게 하고, (나) `MarketClosed`는 바깥 코드 2000이 휴장 전용이 아니라 이름이 틀린다. 둘 다 고르지 않는다.
3. **`CODE_TABLE`에는 `(Rest(2000), Known(BusinessRejected, Reported))`로 넣는다.** 근거는 hoga-ops·cluefin 실측과 이번 서버 로그다. 공식 37개 표에는 없으므로 `Official`이 아니다. 코드표에 실측 코드를 더하는 것은 ADR 0009 "목록: 공식 REST 37개와 실측 추가분" 안의 일이다.
4. **ADR 0009에 범주 하나를 더한다.** ADR 0009의 "범주와 정책"은 닫힌 범주 목록이다. 새 범주는 그 목록을 바꾸므로 같은 ADR에 개정일(2026-11-19)과 함께 "업무 거절([2000]): 조회 단계는 재시도·정지 없이 그 요청만 실패, 발급 단계는 경로 멈춤, 안쪽 6자리 사유는 숫자로만 남긴다" 항목을 더한다. "알 수 없음" 문단은 바꾸지 않는다.
5. **발급 단계(`Phase::Issue`)에서 온 업무 거절은 지금처럼 `Path`다.** 발급에 2000이 올 근거가 없고, 발급 경로를 반복하지 않는 기존 원칙을 따른다.
6. **안쪽 사유는 `[NNNN]` 바로 뒤 `(` + 정확히 6자리 ASCII 숫자 + `:` 또는 `)`일 때만 읽는다.** 다른 모양이면 사유 없음이다. 표에 없는 6자리도 숫자로 남기고 같은 업무 거절로 다룬다(정책은 사유와 무관). 알려진 사유 문구는 우리가 쓴 고정 문구다. 키움 원문이 아니므로 원문 비보관 원칙을 지킨다.
7. **주문 쓰기(kt10000~3)의 업무 거절은 확정 거절이다.** `trading/orders.rs`의 `kiwoom_said_no`는 지금 `Unknown`을 HTTP 200 + 비0 `return_code`에서 확정 거절로 본다. 쓰기에 `[2000]`이 오면 이제 `BusinessRejected`가 되므로, 이 목록에 넣지 않으면 확정 거절이 "결과 불명"으로 바뀌어 주문 칸이 막힌다. 그래서 같은 목록에 더한다.
8. **`키움 조회` 로그 줄에는 사유 숫자만 더하고 요청 본문 값(`trde_tp`, 종목)은 더하지 않는다.** 3.3 뒤에는 kt00010이 매수 쪽만 나가므로 어느 쪽인지 가릴 필요가 줄었고, 로그 줄 모양을 TR마다 다르게 만들지 않는다.
9. **매도 가능 수량은 잔고를 받기 전이면 `null`(검사 안 함), 받았는데 그 종목이 없으면 0이다.** 서버도 매도 주문 때 kt00018 잔고의 `sellable_quantity`로 검사하고 없으면 0으로 본다(`trading/orders.rs`의 `SellOverSellable`). 화면이 같은 값을 쓴다. `/api/trading/orderable` 경로 자체는 남긴다(서버 매수 검사가 같은 함수를 쓴다).
10. **매수 가능 조회가 실패하면 주문창 "매수 가능" 칸은 지금처럼 "-"를 보이고, 서버가 준 실패 문장을 그 칸의 툴팁(`title`)으로 보인다.** "멈춤"이 아니라 거절 사유를 화면에 두라는 요청을 가장 작은 화면 변경으로 맞춘다. 새 줄이나 알림은 더하지 않는다.
11. **`rankings/cache.rs`의 `key_was_refused`와 기존 "표에 없는 상세" 시험(`rest.rs`의 `unknown_and_protocol_failures_stop_their_path_until_restart`)은 바꾸지 않는다.** 둘 다 3.4(알 수 없음 정책)와 묶인 동작이다.

## 작업

| 작업 | 범위 | 방식 | 이유 |
|---|---|---|---|
| `kt00010-reject` | 서버 3.1+3.2, 브라우저 계약의 새 사유, ADR 0009 | `poteto` | 경로 정지 정책(대기열 상태)과 주문 쓰기 판정(`kiwoom_said_no`)을 바꾸고, 오류 모듈·대기열·거래·계약에 걸친다 |
| `order-sell-qty` | 웹 3.3과 매수 가능 실패 툴팁, 주문창 e2e | `basic` | 화면 한 곳의 작은 수정과 시험이다 |

두 작업은 병렬이다. 순차로 둔 작업은 없다(결정 1).

## 사용자가 정해야 하는 결정

- 검증을 약하게 하는 작업은 없다.
- 3.4(코드표에 없는 코드를 시간 제한 정지로 바꾸는 ADR 0009 개정)와 3.5(재시작 없이 경로 해제, 상태 막대 TR 이름화)를 다음 플랜으로 할지. 이 플랜 뒤에도 `[2000]`이 아닌 처음 보는 코드는 지금처럼 그 경로를 재시작 전까지 멈춘다.
- 배포 뒤 주문창을 한 번 열면 `키움 조회` 로그 줄에 안쪽 사유가 남는다. 그 숫자로 원인(571455 미보유 매도 / 571489 장외 / 503721 계좌 종류)을 확정할지 사용자가 로그를 확인한다.
