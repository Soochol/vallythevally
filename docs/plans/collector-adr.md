# 수집기 확대 ADR(PR #435) 갱신 플랜

작성일: 2026-11-17. 승인 시점의 기록이며 구현 중 바뀐 것은 반영하지 않는다.

## 풀려는 문제

PR #435는 수집기를 키 넷·약 760종목으로 넓히는 ADR을 `0023`으로 냈다. 그 사이 main에 `0023-connector-and-account-server.md`와 `0024-setup-storage-and-sync.md`가 먼저 들어가 번호가 겹친다. 사용자는 이 ADR의 큰 그림(키마다 프로세스 하나)이 맞다고 보았고, 전종목을 모은다고 할 때 필요한 전략과 구성을 더하라고 했다.

- 어떤 종목이 있는지 아는 법(종목 목록)
- 키마다 몇 종목을 맡길지(용량과 할당)
- 데몬 프로세스 여러 개로 할지, 수집 앱을 만들지
- 수집이 얼마나 됐는지 보는 법(커버리지와 상태 화면). 상태 화면은 로그인한 허용 계정만 보게 한다.

함께 store-bench 실험 결론을 "아직 정하지 않은 것"에 채우고, 제3자 제공 금지 관련 문장을 ADR에서 뺀다.

## 확정된 결정 (사용자와 정함)

- ADR 번호를 `0025`로 바꾸고 파일명은 `0025-collector-stores-closed-days-for-the-app.md`다. ADR 본문, `GLOSSARY.md`, ADR 0003·0022, `docs/collector-rest-jobs.md`의 링크와 "ADR 0023" 언급을 0025로 고친다. `GLOSSARY.md` 충돌은 main 기준으로 푼다.
- store-bench 결론:
  - 정리는 Parquet에 바로 쓰고 모든 FID를 저장한다. 종목 해시로 64파일, 종목·시각 정렬, delta, zstd 3, 묶음 3만 행.
  - 구간 파일은 미리 만들지 않고 요청 때 Parquet에서 만든다(brotli q5).
  - 원문은 zstd 9로 받고 2~3주 보관한다. 지우는 일은 사람이 한다. 하루치를 실측하기 전의 가정이다.
- 구성은 수집 앱 하나(바이너리 `collector`, 하위 명령 `universe`·`plan`·`collect --key`·`finalize`·`status`)와 키마다 프로세스 하나다. systemd 템플릿과 타이머가 띄우고 다시 띄운다. 상주 감독 데몬은 두지 않는다. 공유하는 설정·상태는 키 목록 설정(이름·용량·활성·앱키 해시), `universe/<날짜>`, `plan/<날짜>`, `status/<키>.json`이다.
- 종목 목록: 마감 뒤 한 키가 `ka10099`로 시장별 전 종목을 받아 `universe/<날짜>`에 쓰고, 전날과의 차이(신규·폐지)를 남긴다.
- 할당: 키 목록 설정을 보고 나눈다. 전날 원문의 종목별 메시지 수(부하)가 고르게 되도록 나눈다. 시장 단위 타입과 REST 작업도 같은 계획이 나눈다. 용량을 넘는 종목은 계획에 "제외"로 남긴다.
- 커버리지: `finalize`가 종목별로 계획·등록 성공·실제 수신·끊긴 구간·용량 제외를 집계해 `complete.json`에 담는다.
- 수집 상태 화면: 수집 앱에는 UI가 없다. 상태 화면은 커넥터에 페이지로 둔다. 수집기 상태 폴더가 설정된 커넥터에서만 켜지고, 설정이 없으면 라우트와 메뉴가 없다. 선택으로, 커넥터 설정의 허용 계정(`provider:subject`)으로 로그인했을 때만 보인다. 판단은 커넥터가 한다. 계정 서버는 판단하지 않는다.
- 뺄 것: "개인용 범위는 그대로다…" 항목. 키움 약관 제5조③ 관련 문장은 넣지 않는다.

## 스스로 정한 결정과 이유

1. **기존 PR #435의 브랜치를 이어서 고친다(사용자 지시).** 작업자는 orch가 만든 작업 worktree에서 `origin/docs/collector-expansion-adr`(05b6283)로 시작한다. 최신 main을 들여오고(rebase든 merge든 작업자가 고른다) 같은 브랜치에 push해 PR #435를 갱신한다. 새 PR은 만들지 않는다. rebase했을 때만 `--force-with-lease=docs/collector-expansion-adr:05b6283…`로 강제 push한다. 맨 `--force`는 쓰지 않는다.
2. **용량 결정 전까지 무엇을 "제외"할지 정하는 임시 순서.** 키를 늘릴지 우선순위로 자를지는 사용자가 정한다. 그 전에도 계획은 같은 입력에서 같은 결과를 내야 한다. 그래서 기존 초안의 순서(관심종목 먼저, 나머지는 전 관측일 거래대금 순)로 자르고, ADR에 이 순서가 임시라고 적는다.
3. **어디에 무엇을 넣을지는 사용자 결정 대기로 적는다.** 넣을 종목 종류(보통주·우선주·ETF·ETN·스팩·거래정지·관리종목)와 용량 대응(키 증설 / 우선순위 절단)은 ADR의 "아직 정하지 않은 것"에 사용자 결정 대기로 둔다. 200자리가 앱키마다인지 계좌마다인지를 먼저 재야 한다고 적는다.
4. **새 용어.** "운영자"는 GLOSSARY가 피하는 말이다. 상태 화면을 볼 수 있는 계정은 새 용어(예: "수집 관리 계정")로 GLOSSARY에 더한다. 종목 목록도 용어로 더하고, `수집 계획`의 _Avoid_에 있는 "유니버스"와 어긋나지 않게 한다. 파일 경로 `universe/`는 코드 식별자라 그대로 둔다. 정확한 낱말은 작업자가 GLOSSARY의 기존 용어와 맞춰 고른다.
5. **store-bench 근거 문서.** 실험 결과 문서는 아직 저장소에 없다(다른 세션의 커밋 전 worktree). ADR에는 링크 대신 수치를 적고 "실험 결과 문서는 별도 PR"이라고 적는다. 그 worktree는 건드리지 않는다.
6. **작업 하나.** 고칠 파일 다섯이 모두 한 ADR의 번호와 내용에 묶여 있어 나누면 서로의 결과를 쓴다. PR 하나로 둔다.

## 사용자가 정해야 하는 결정

1. **orch로 병합하는 길.** orch의 작업 브랜치는 항상 `orch/<플랜>/<작업>`이다. `land`와 `done`은 그 브랜치의 PR을 찾는데 PR #435의 브랜치는 `docs/collector-expansion-adr`라 찾지 못한다. 오케스트레이터 터미널의 훅은 `chute submit`을 직접 부르는 것도 막는다. 그래서 작업자가 `merge-ready`(PR 435, HEAD)를 보고한 뒤 PR #435를 chute에 올리는 길은 셋 가운데 사용자가 고른다.
   - (가) 사용자가 직접 `chute submit 435 --head <보고된 HEAD>`를 실행한다(권장).
   - (나) 오케스트레이터가 사용자 승인을 받아 훅 밖에서 submit한다.
   - (다) orch에 기존 PR 브랜치를 작업 브랜치로 지정하는 기능을 더한다(별도 작업).

   병합된 뒤 작업 정리는 `done collector-adr --discard`로 한다. 작업 브랜치에는 PR이 없어서 `--discard` 없이는 "병합 안 됨"으로 멈춘다.
2. 넣을 종목 종류와 용량 대응(키 증설 / 우선순위 절단)은 이 플랜에서 정하지 않는다. ADR에 결정 대기로 남는다.

검증을 약하게 하는 변경(검증 단계 삭제, 시간 제한 증가, `paths` 축소)은 없다.
