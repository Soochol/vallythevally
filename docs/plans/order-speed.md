# 주문·취소 속도

작성일: 2026-11-19. 승인 시점의 기록이며 구현 중 바뀐 것은 반영하지 않는다.

## 사용자가 풀려는 문제

사용자 요청(원문):

> 그리고 내가 더블클릭으로 주문을 넣으면 그 찰나가 왜이렇게 길어? 주문이라 엄청 속도가 중요한데 .

> (조사 뒤) a b f로 하고 b에서 거절나면 알려주면 되잖아.

> 취소할때도 빨리 취소가 되어야 해, 이것도 체크 필요

호가 칸을 더블클릭해 주문하거나 칩을 취소할 때 화면에 결과가 늦게 뜬다. 조사(order-latency 보고서) 결과 원인은 브라우저가 아니라 서버다. 키움 쓰기 앞에서 서버가 키움 조회를 직렬로 2~3번 하고, 모든 키움 전송 사이에 260ms 간격이 있다. 화면의 주문 칩은 응답 뒤 미체결을 다시 조회해야 나타난다.

## 지금 걸리는 시간

주문(조사 보고서의 합성 transport 측정, 키움 응답 지연 0, 실서버 간격 260ms):

| 동작 | 쓰기 앞 키움 조회 | HTTP 총 시간 |
|---|---|---|
| 매수 | `ka10001`(상·하한가) → `kt00010`(매수 가능 금액) → `kt10000` | 784ms |
| 매도 | `ka10001` → `kt00018`(잔고) → `kt10001` | 783ms |

마지막 계좌 확인이 60초 지났으면 `ka00001`이 하나 더 붙는다. 호가주문창이 열려 있으면 15초 잔고 폴링이 이 확인을 미리 해 두므로 주문 경로에서는 거의 붙지 않는다.

취소·정정(코드로 센 키움 전송 수. 측정은 첫 작업의 성공 조건이다. 간격 260ms 기준 대략 `전송 수 × 260ms`):

| 동작 | 지금 키움 전송 | 대략 |
|---|---|---|
| 취소 한 건 | `ka10075`(미체결) → `kt10003` = 2 | 0.5초 |
| 같은 가격 N건 일괄 취소 | 대상 고르기 `ka10075` 1 + 건마다 다시 `ka10075` + `kt10003` = 2N+1 | N=3이면 1.8초 |
| "매수/매도/전체 모두 취소"(가격 K개, 주문 N건) | 가격마다 일괄 취소 = 2N+K | 3가격 3건이면 2.3초 |
| 정정 N건(칩 끌어 다른 가격) | 건마다 `ka10075` + `ka10001` + `kt10002` = 3N | 2건이면 1.6초 |

일괄 취소가 건마다 미체결을 다시 조회하는 것은 `cancel_batch_detached`가 이미 고른 대상을 `execute → vet → resolve_target`에서 한 번 더 찾기 때문이다(`crates/server/src/trading/orders.rs`).

## 확정된 결정

1. **A. 상·하한가 확인을 주문 경로 밖으로.** 서버가 종목별 상·하한가를 그날(KST 날짜) 동안 기억한다. 호가주문창을 열 때 화면이 부르는 종목 기본 정보 조회(`/api/symbols/{code}/fundamentals`, `ka10001`)와 주문 경로의 조회가 기억을 채운다. 기억이 없거나 날짜가 바뀌었을 때만 주문 경로에서 `ka10001`을 부른다. 상·하한가를 받지 못하면 지금처럼 `limits_unavailable`로 주문을 닫는다.
2. **B. 매수 가능 금액·매도 가능 수량 확인을 주문 경로에서 뺀다.** 최근 값으로 대신한다(아래 스스로 정한 결정 2). 키움이 잔고·수량 부족으로 거절하면 무엇 때문인지 상태줄에 분명히 보인다.
3. **F. 응답 즉시 화면에 그린다.** 더블클릭하면 그 칸에 곧바로 "보내는 중"을 보이고, 접수 응답(주문번호)을 받으면 미체결 재조회를 기다리지 않고 칩을 그린 뒤 재조회로 맞춘다. 거절·결과 불명이면 되돌린다. 취소도 같다. 누르면 칩이 곧바로 "취소 중"이 되고, 접수 응답을 받으면 칩을 지운다. 거절·결과 불명이면 칩을 되살린다.
4. **취소·정정 경로도 줄인다.** 취소·정정할 주문을 최근 미체결 값에서 찾고, 일괄 취소는 처음 고른 대상을 그대로 쓴다(아래 스스로 정한 결정 3, 4).
5. **하지 않는 것**: 계좌 재확인(`ka00001`, 60초)을 주문 경로 밖으로 빼기(C), 260ms 간격 줄이기(E).

바뀐 뒤 예상(측정은 각 작업의 성공 조건):

| 동작 | 바뀐 뒤 키움 전송 | 대략 |
|---|---|---|
| 매수·매도 | 쓰기 1 | 0.26초 (지금 0.78초) |
| 취소 한 건 | `kt10003` 1 | 0.26초 |
| 같은 가격 N건 | `ka10075` 1 + `kt10003` N = N+1 | N=3이면 1.0초 |
| 모두 취소(가격 K개) | N+K | 3가격 3건이면 1.6초 |
| 정정 N건 | `kt10002` N | 2건이면 0.5초 |

화면에서는 위 시간을 기다리지 않고 누르는 즉시 "보내는 중/취소 중"이 보인다.

## 스스로 정한 결정과 이유

1. **상·하한가 기억이 범위 밖이라고 하면 한 번 새로 조회한 뒤 거절한다.** 장 시작 전에 받은 값이 전날 값일 수 있어서다. 새 값으로도 범위 밖이면 `out_of_limit`. 기억한 값으로 범위 안인데 실제로 밖이면 키움이 거절한다(그 거절은 결정 5처럼 보인다).
2. **B는 "빼기" 대신 "20초 안의 최근 값으로 확인"으로 한다.** 서버 확인을 완전히 빼면 키움이 계좌 증거금률로 받아 줄 수 있다. 증거금률이 100%가 아닌 계좌에서는 현금보다 큰 매수가 접수돼 미수가 생길 수 있다. 지금 서버는 증거금 100% 값(ADR 0029)으로 이것을 막는다. 그래서 확인은 남기되 키움을 다시 부르지 않는다.
   - 최근 값은 호가주문창이 15초마다 부르는 매수 가능 금액·잔고 조회와 주문 경로의 조회가 채운다. 20초가 지났거나 값이 없으면 지금처럼 조회한다.
   - 이 서버로 넣은 주문이 접수되면 그 금액·수량만큼 최근 값에서 뺀다. 연달아 넣는 주문도 조회 없이 확인한다.
   - 남는 틈: 다른 앱(영웅문 등)에서 같은 계좌로 주문한 뒤 20초 안에 여기서 주문하면 서버가 모르고 보낸다. 그때는 키움이 판단한다. 사용자가 정할 것 1.
3. **취소·정정은 최근 미체결 값(10초 안)에서 대상 주문을 찾는다.** 호가주문창이 5초마다 미체결을 조회하고 쓰기 뒤·계좌 이벤트 뒤에도 다시 조회하므로 값이 거의 늘 새것이다. 목록에 없거나(막 넣은 주문) 10초가 지났으면 지금처럼 조회한다. 이 서버의 쓰기가 접수되거나 키움 계좌 이벤트가 오면 기억을 버린다. 남는 틈은 그 사이 일부 체결로 잔량이 줄었는데 이벤트가 아직 안 온 경우다. 이때 보내는 수량이 실제 잔량보다 크고, 그 결과는 키움이 정한다(취소·정정은 원주문 범위를 넘어 체결을 늘릴 수 없다). 거절이면 결정 5처럼 보인다.
4. **일괄 취소는 대상을 고를 때 한 번만 미체결을 새로 조회하고, 건마다 다시 찾지 않는다.** 대상 고르기는 최근 값을 쓰지 않는다. "모두 취소"가 막 들어온 주문을 빠뜨리면 안 되기 때문이다.
5. **키움 거절 사유는 ADR 0009대로 6자리 숫자와 우리가 쓴 고정 문구로 보인다.** 키움 원문은 저장하지 않는다. 명령 저널에 사유 숫자를 남겨 같은 `command_id`를 다시 받아도 같은 문구가 나온다. 알려진 사유(571455 매도할 잔고 부족 등)는 문구로, 모르는 사유는 "키움이 주문을 거절했습니다(사유 NNNNNN)"으로 보인다. 매수 가능 금액 부족의 사유 숫자는 아직 모른다. 처음 보이면 숫자를 알려 주면 표에 문구를 더한다.
6. **화면 즉시 표시는 서버 변경과 따로 한다.** 서버가 빨라져도 미체결 재조회를 한 번 더 기다리는 것은 그대로라서 둘 다 필요하다. 서로 다른 파일이라 병렬로 할 수 있다.

## 작업과 순서

| 작업 | 내용 | 순서 | 방식과 이유 |
|---|---|---|---|
| `order-vet-fast` | 서버: A, B, 취소·정정 대상 찾기, 일괄 취소 재조회 제거, 합성 측정 | 바로 시작 | `poteto`: 주문 쓰기 앞의 안전 확인(main에 무엇이 나가는지)과 동시 접근하는 기억을 바꾼다 |
| `order-reject-reason` | 서버·웹: 키움 거절 사유를 저널에 남기고 상태줄에 보이기 | `order-vet-fast`, `book-venue-server` 뒤 | `poteto`: 저널 DB 이관(상태 저장)이다 |
| `order-optimistic` | 웹: 보내는 중·접수 칩 즉시 표시, 취소 중·취소됨 즉시 표시, 되돌리기 | `drag-cancel` 뒤 | `poteto`: 주문 상태를 화면에서 앞서 그리고 되돌리는 새 설계이고 실제 주문 취소 화면이다 |

순차로 둔 이유:

- `order-reject-reason`은 `order-vet-fast`가 다시 짜는 `orders.rs`의 `vet`·`execute` 옆 `settle`과 저널 호출을 고치고, B의 결과(키움 거절)를 보이는 일이라 그 뒤다. `crates/server/src/api.rs`와 `web/src/api/generated/**`를 같은 탭의 `book-venue-server`가 고치므로 그 뒤다.
- `order-optimistic`은 `drag-cancel`이 고치는 `OrderLadder.tsx`·`orderRules.ts`·`order-window.css`의 칩 그리기를 다시 만진다. 그래서 그 뒤다. `OrderWindow.tsx`와 기존 `win-order.spec.ts`·`e2e/order-window.ts`는 `book-venue-web`도 고치므로 이 작업은 고치지 않는다(새 spec 파일을 쓴다). `statusText.ts`는 `order-reject-reason`과 각자 몇 줄 더하는 관계라 둘 다 `shared`로 둔다.
- `order-vet-fast`는 같은 탭의 다른 작업과 겹치는 파일이 없다.

## 범위 밖

- 계좌 재확인(C), 260ms 간격 변경(E), 연속 클릭 직렬(`useOrderWrites`의 `tail`, 서버 계좌 잠금) 약화(G), 조회 병렬화(D).
- 여러 가격 "모두 취소"를 한 번의 미체결 조회로 묶는 서버 API(사용자가 정할 것 2).
- 취소 수량을 "0(잔량 전부)"으로 보내기. 공개 글에만 근거가 있고 실제 키움으로 확인할 수 없다.
- 실제 키움 호출·실제 주문. 모든 확인은 합성 transport와 브라우저 가짜 응답으로 한다. 실제 체감은 병합 뒤 사용자가 소량으로 확인한다.

## 사용자가 정해야 하는 결정

1. **매수 가능 금액·매도 가능 수량을 얼마나 오래된 값까지 믿을까?** 기본 20초로 구현한다.
   - 20초(권장): 주문 앞 조회가 없어진다. 다른 앱에서 방금 주문한 경우만 서버가 놓친다.
   - 0초(지금처럼 매번 조회): 매수·매도가 0.26초 느려진다.
   - 아예 확인 안 하고 키움에 맡기기(요청 원문 그대로): 증거금률 100%가 아닌 계좌면 미수가 생길 수 있다. 계좌가 100% 증거금으로 설정돼 있다면 이 선택도 안전하다.
2. **"모두 취소"를 더 빠르게 할까?** 지금 플랜은 가격마다 미체결을 한 번씩 조회한다(가격 3개면 0.5초 더). 한 번으로 묶으려면 서버에 방향 단위 일괄 취소를 새로 만들어야 한다. 기본은 하지 않는다. 원하면 다음 플랜으로 한다.
