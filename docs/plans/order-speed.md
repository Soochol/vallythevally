# 주문·취소 속도

작성일: 2026-11-19. 승인 시점의 기록이며 구현 중 바뀐 것은 반영하지 않는다.

## 사용자가 풀려는 문제

사용자 요청(원문):

> 그리고 내가 더블클릭으로 주문을 넣으면 그 찰나가 왜이렇게 길어? 주문이라 엄청 속도가 중요한데 .

> (조사 뒤) a b f로 하고 b에서 거절나면 알려주면 되잖아.

> 취소할때도 빨리 취소가 되어야 해, 이것도 체크 필요

> (플랜 검토 뒤) 일단 주문 빠르게 하는것만 진행하고 미수 이건 별도 세션으로 하자.

호가 칸을 더블클릭해 주문하거나 칩을 취소할 때 화면에 결과가 늦게 뜬다. 조사(order-latency 보고서) 결과 원인은 브라우저가 아니라 서버다. 키움 쓰기 앞에서 서버가 키움 조회를 직렬로 2~3번 하고, 모든 키움 전송 사이에 260ms 간격이 있다. 화면의 주문 칩은 응답 뒤 미체결을 다시 조회해야 나타난다.

## 지금 걸리는 시간

주문(조사 보고서의 합성 transport 측정, 키움 응답 지연 0, 실서버 간격 260ms):

| 동작 | 쓰기 앞 키움 조회 | HTTP 총 시간 |
|---|---|---|
| 매수 | `ka10001`(상·하한가) → `kt00010`(매수 가능 금액) → `kt10000` | 784ms |
| 매도 | `ka10001` → `kt00018`(잔고) → `kt10001` | 783ms |

마지막 계좌 확인이 60초 지났으면 `ka00001`이 하나 더 붙는다. 호가주문창이 열려 있으면 15초 잔고 폴링이 이 확인을 미리 해 두므로 주문 경로에서는 거의 붙지 않는다.

취소·정정(코드로 센 키움 전송 수. 측정은 서버 작업의 성공 조건이다. 간격 260ms 기준 대략 `전송 수 × 260ms`):

| 동작 | 지금 키움 전송 | 대략 |
|---|---|---|
| 취소 한 건 | `ka10075`(미체결) → `kt10003` = 2 | 0.5초 |
| 같은 가격 N건 일괄 취소 | 대상 고르기 `ka10075` 1 + 건마다 다시 `ka10075` + `kt10003` = 2N+1 | N=3이면 1.8초 |
| "매수/매도/전체 모두 취소"(가격 K개, 주문 N건) | 가격마다 일괄 취소 = 2N+K | 3가격 3건이면 2.3초 |
| 정정 N건(칩 끌어 다른 가격) | 건마다 `ka10075` + `ka10001` + `kt10002` = 3N | 2건이면 1.6초 |

일괄 취소가 건마다 미체결을 다시 조회하는 것은 `cancel_batch_detached`가 이미 고른 대상을 `execute → vet → resolve_target`에서 한 번 더 찾기 때문이다(`crates/server/src/trading/orders.rs`).

## 확정된 결정

1. **A. 상·하한가 확인을 주문 경로 밖으로.** 서버가 종목별 상·하한가를 그날(KST 날짜) 동안 기억한다. 호가주문창을 열 때 화면이 부르는 종목 기본 정보 조회(`/api/symbols/{code}/fundamentals`, `ka10001`)와 주문 경로의 조회가 기억을 채운다. 기억이 없거나 날짜가 바뀌었을 때만 주문 경로에서 `ka10001`을 부른다. 상·하한가를 받지 못하면 지금처럼 `limits_unavailable`로 주문을 닫는다.
2. **취소·정정 앞 조회를 줄인다.** 취소·정정할 주문을 최근 미체결 값에서 찾고, 일괄 취소는 처음 고른 대상을 그대로 쓴다(아래 스스로 정한 결정 2, 3).
3. **F. 누르는 즉시 화면에 그린다.** 더블클릭하면 그 칸에 곧바로 "보내는 중"을 보이고, 접수 응답(주문번호)을 받으면 미체결 재조회를 기다리지 않고 칩을 그린 뒤 재조회로 맞춘다. 거절·결과 불명이면 되돌린다. 취소도 같다. 누르면 칩이 곧바로 "취소 중"이 되고, 접수 응답을 받으면 칩을 지운다. 거절·결과 불명이면 칩을 되살린다.
4. **B(매수 가능 금액·매도 가능 수량 사전 확인 바꾸기)는 이 플랜에서 뺀다.** 그 확인은 지금처럼 주문 경로에서 매번 조회한다. 이 확인은 증거금 100% 값으로 미수를 막는다(ADR 0029). 미수·증거금과 함께 별도 세션에서 다룬다. B의 거절을 알리려던 키움 거절 사유 표시 작업도 함께 뺀다.
5. **하지 않는 것**: 계좌 재확인(`ka00001`, 60초)을 주문 경로 밖으로 빼기(C), 260ms 간격 줄이기(E), 여러 가격 "모두 취소"를 미체결 조회 한 번으로 묶는 서버 API.

바뀐 뒤 예상(측정은 각 작업의 성공 조건):

| 동작 | 바뀐 뒤 키움 전송 | 대략 |
|---|---|---|
| 매수 | `kt00010` → `kt10000` = 2 | 0.52초 (지금 0.78초) |
| 매도 | `kt00018` → `kt10001` = 2 | 0.52초 (지금 0.78초) |
| 취소 한 건 | `kt10003` 1 | 0.26초 |
| 같은 가격 N건 | `ka10075` 1 + `kt10003` N = N+1 | N=3이면 1.0초 |
| 모두 취소(가격 K개) | N+K | 3가격 3건이면 1.6초 |
| 정정 N건 | `kt10002` N | 2건이면 0.5초 |

화면에서는 위 시간을 기다리지 않고 누르는 즉시 "보내는 중/취소 중/정정 중"이 보인다.

## 스스로 정한 결정과 이유

1. **상·하한가 기억으로 범위 밖이면 한 번 새로 조회한 뒤 거절한다.** 장 시작 전에 받은 값이 전날 값일 수 있어서다. 새 값으로도 범위 밖이면 `out_of_limit`. 기억한 값으로 범위 안인데 실제로 밖이면 키움이 거절한다.
2. **취소·정정은 최근 미체결 값(10초 안)에서 대상 주문을 찾는다.** 호가주문창이 5초마다 미체결을 조회하고 쓰기 뒤·계좌 이벤트 뒤에도 다시 조회하므로 값이 거의 늘 새것이다. 목록에 없거나(막 넣은 주문) 10초가 지났으면 지금처럼 조회한다. 이 서버의 쓰기가 접수·결과 불명이 되거나 키움 계좌 이벤트가 오면 기억을 버린다. 남는 틈은 그 사이 일부 체결로 잔량이 줄었는데 이벤트가 아직 안 온 경우다. 이때 보내는 수량이 실제 잔량보다 크고, 결과는 키움이 정한다. 취소·정정은 원주문 범위를 넘어 체결을 늘릴 수 없다. 거절이면 지금 문구("키움이 주문을 거절했습니다")로 보인다.
3. **일괄 취소는 대상을 고를 때 한 번만 미체결을 새로 조회하고, 건마다 다시 찾지 않는다.** 대상 고르기는 최근 값을 쓰지 않는다. "모두 취소"가 막 들어온 주문을 빠뜨리면 안 되기 때문이다.
4. **화면 즉시 표시는 서버 변경과 따로 한다.** 서버가 빨라져도 미체결 재조회를 한 번 더 기다리는 것은 그대로라서 둘 다 필요하다. 서로 다른 파일이라 병렬로 할 수 있다.
5. **키움 거절 사유 표시는 취소·정정 속도에 필요하지 않아 남기지 않는다.** 결정 2의 틈으로 생기는 거절은 드물고 지금 문구로도 거절임은 보인다.

## 작업과 순서

| 작업 | 내용 | 순서 | 방식과 이유 |
|---|---|---|---|
| `order-vet-fast` | 서버: A, 취소·정정 대상 찾기, 일괄 취소 재조회 제거, 합성 측정 | 바로 시작 | `poteto`: 주문 쓰기 앞의 안전 확인과 동시에 접근하는 기억을 바꾼다 |
| `order-optimistic` | 웹: 보내는 중·접수 칩 즉시 표시, 취소 중·취소됨·정정 중 즉시 표시, 되돌리기 | `drag-cancel` 뒤 | `poteto`: 주문 상태를 화면에서 앞서 그리고 되돌리는 새 설계이고 실제 주문 취소 화면이다 |

순서를 둔 이유:

- `order-optimistic`은 `drag-cancel`이 고치는 `OrderLadder.tsx`·`orderRules.ts`·`order-window.css`의 칩 그리기를 다시 만진다. 그래서 그 뒤다. `OrderWindow.tsx`와 기존 `win-order.spec.ts`·`e2e/order-window.ts`는 `book-venue-web`도 고치므로 이 작업은 고치지 않는다(새 spec 파일을 쓴다).
- `order-vet-fast`는 같은 탭의 다른 작업과 겹치는 파일이 없다. 두 작업은 병렬이다.

## 범위 밖

- B와 키움 거절 사유 표시(별도 세션), C, E, 연속 클릭 직렬(`useOrderWrites`의 `tail`, 서버 계좌 잠금) 약화(G), 조회 병렬화(D), "모두 취소" 묶기 API.
- 취소 수량을 "0(잔량 전부)"으로 보내기. 공개 글에만 근거가 있고 실제 키움으로 확인할 수 없다.
- 실제 키움 호출·실제 주문. 모든 확인은 합성 transport와 브라우저 가짜 응답으로 한다. 실제 체감은 병합 뒤 사용자가 소량으로 확인한다.
