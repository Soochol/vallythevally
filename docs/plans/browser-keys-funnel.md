# Funnel 공개 첫 단계 플랜: 공개 리스너, 브라우저 로그인, 브라우저 키 보관

작성일 2026-11-22. 승인 시점의 기록이며 구현 중 바뀐 것은 반영하지 않는다.

코드 사실의 기준 시점은 `origin/main` `c795199b`(#767) 하나다. 독립 검토(`plan-review`, 성능·보안 두 검토자)의 지적을 반영했다. 사용자는 성능을 가장 중요하게 본다.

## 사용자가 풀려는 문제

사용자는 이 도구를 여러 사람이 웹 화면만 열어 쓰는 서비스로 열려 한다. 공개 방법은 Tailscale Funnel이다. 지금 서버 PC의 `tailscale serve`(ADR 0036)를 바탕으로 무료 요금제로 시작한다. 구조는 PR #754의 ADR 0038 초안에 있다. 사용자 키움 키는 각자 브라우저에만 두고, 수집은 운영 서버 한 곳에서 한다.

사용자의 말: "좋아. funnel 하는걸로 하고 /orch 으로 플래닝해줘."

지금 코드로는 다음이 막는다.

- 로그인은 루프백 흐름뿐이다. 계정 서버(`crates/account-server`)가 일회용 코드를 `http://127.0.0.1:<포트>/auth/complete`로 보내고(`app.rs`의 `connector_url`), 커넥터가 그것을 커넥터 토큰으로 바꾼다. 원격 브라우저에서는 끝나지 않고, 계정 서버에는 브라우저 세션이 없다.
- `vally-server`에는 사람을 가리는 계층이 없다. 루프백이나 설정한 tailnet 이름으로 오면 모든 라우트에 닿는다. 쓰기 가드(`write_guard.rs`)는 Host·Origin·Content-Type 형식만 본다. 가드가 걸리지 않는 곳은 다음과 같다.
  - 사용자 자료 `PUT`
  - `POST` 아홉: 스크리너 갱신·취소·실행, 순위, 재무 갱신·멈춤·다시 시작·소스·지표(`financials/routes.rs:14`)
  - `/api/ws`
  - 모든 읽기
- 같은 프로세스에 운영자의 실전 키와 주문 라우트가 있다. 그대로 Funnel로 열면 인터넷의 누구나 운영자 계좌에 닿는다.
- 응답에 CSP 같은 보안 헤더가 없다. 압축은 `CompressionLayer::new()`(`http.rs:73`)의 brotli 기본 품질로 요청마다 한다.
- 사용자 자료는 한 사람의 로컬 SQLite(`data/vally.db`)다. 히트맵 보드(`heatmap_board`)도 그 DB의 테마 하나를 읽는다.

## 확정된 결정

사용자가 정했다(2026-11-22).

1. 여러 사람이 쓰는 서비스로 연다. 사용자가 프로그램을 설치하는 방식(ADR 0023의 커넥터 설치)은 쓰지 않는다.
2. **역할 나누기.** 공용 자료는 운영 서버가 운영자 키(수집 키 포함)로 받고 캐시해서 로그인한 모든 사용자에게 준다. 종목 목록, 일봉 저장소, 스크리너, 재무, ETF, 순위, 시장 개요, 히트맵이 여기에 든다. 브라우저가 사용자 키로 하는 일은 셋뿐이다.
   - 내가 보는 종목의 실시간(WebSocket 체결·호가)
   - 계좌 실시간(WebSocket `00`·`04`)
   - 토큰, 계좌 조회, 주문(REST)
3. 사용자 키움 키는 브라우저에서 입력해 브라우저에만 저장한다. 서버로 보내지 않는다.
4. **키 보호의 기본은 브라우저가 알아서 잠그는 것이다.** 꺼낼 수 없는(`extractable: false`) AES-GCM 키를 IndexedDB에 두고, 키움 키와 토큰을 그 키로 암호화한다. 사용자 입력은 없다. 원하는 사용자만 잠금 비밀번호나 패스키(WebAuthn PRF)를 켠다. 어느 방식이든 키는 서버로 가지 않는다.
5. 수집기는 운영 서버 한 곳에서만 돌린다.
6. 공개 방법은 Tailscale Funnel이다. 무료 요금제로 시작하고 나중에 자기 도메인으로 옮길 수 있다.
7. Google·Naver 로그인, `(provider, subject)` 계정 식별, 셋업 범위는 ADR 0023 그대로다.
8. PR #754(ADR 0038)는 먼저 병합하지 않는다. `adr-public`이 흡수해 2번 역할 나누기로 고친 판을 쓴다. #754는 오케스트레이터가 닫는다.
9. 가입 상한은 100, 공개 포트는 8443이다(호스트 이름은 사용자 결정 3). 키움 규칙은 Rust 코어를 WASM으로 쓴다. 첫 단계 뒤 다음 단계를 플랜으로 만든다.
10. 실제 Funnel 켜기, IdP 앱 등록, 배포(운영 단계 P1·P2·P4)는 나중에 따로 승인한다(ask #8을 이어받는다).
11. 히트맵 기능은 이 플랜이 새로 짜지 않는다. 공개 리스너에 히트맵 읽기 라우트를 넣고, 공개 경로에 필요한 최소 변경만 한다.
12. 한도는 모두 설정으로 두고 기본값을 문서에 적는다. 조정 근거(429·503 횟수, 대기 시간, 캐시 적중)를 경로별로 센다. 요청 제한은 계정 단위이고, 공개 리스너 전체 상한을 하나 둔다.
13. 스크리너는 공용 스냅샷 방식으로 바꾼다. 장중 30초마다 한 번 받아 모두가 같이 쓰고, 운영자 리스너도 같은 방식으로 맞춘다(아래 "스크리너 공용 스냅샷"). 분봉 스크리너는 나중에 한다.
14. 한 프로세스의 위험을 알려진 위험으로 적고, 첫 단계에서 줄인다. 쿠키·출처 공유를 분석하고 별도 호스트 이름 안을 검토한다. 히트맵 보드가 스냅샷을 쓰는 안도 검토한다.
15. 독립 검토의 지적을 반영한다. 공개 히트맵 흐름은 빼지 않고, 종목 수·TR 수로 제한한다. 압축 품질을 낮춘다(오케스트레이터가 정한 처리, 2026-11-22).

## 이번 플랜의 범위

공개 서버의 뼈대와 브라우저 키 보관까지가 첫 단계다. 첫 단계가 끝나면 다음이 된다.

- 운영 서버가 운영자용 주소와 따로 연 **공개 리스너**에서, 로그인한 사용자에게 공용 자료와 계정별 셋업을 준다. 운영자 라우트는 공개 리스너에 없다. 공개 부하가 운영자 화면을 밀어내는 크기에는 계산한 상한이 있다(D10).
- 브라우저가 공개 주소에서 Google·Naver로 직접 로그인한다.
- 브라우저가 키움 키를 암호화해 저장하고, 엄격한 CSP 아래에서 돈다.
- 지금 서버 PC의 로컬 전용 운영과 수집은 그대로 돈다.

브라우저 키움 엔진(실시간, 계좌 실시간, 토큰·계좌·주문)은 다음 단계다. 그 일은 `crates/server/src/kiwoom/`, `trading/`, `market/`을 꺼내 쓰는데, 다른 탭의 다중 증권사 플랜이 바로 그 파일들을 다시 짜고 있다. 지금 실행 중인 것은 `market-port-rest`이고, `market-port-stream`·`kis-*`·`source-select-*`·`kis-orders`는 대기 중이다.

| D4 | 계정 기능은 `account-server` 크레이트를 라이브러리로 써서 공개 리스너 프로세스 안에 붙인다. `server`가 `account-server`에 의존하고, 그 반대는 없다. 별도 `vally-account` 실행과 커넥터 루프백 흐름은 지우지 않는다. | 세션 확인이 함수 호출이 된다. ADR 0023의 의존 방향 규칙도 그대로 지켜진다. |
| D5 | 공개 리스너는 **모든 요청**의 Host가 `VALLY_PUBLIC_ORIGIN`의 호스트(포트 포함)와 정확히 같은지 확인한다. Origin이 있으면 그 출처와 같아야 한다. `GET`·`HEAD`·`OPTIONS`가 아닌 요청은 Origin이 반드시 있어야 하고, 본문은 `Content-Type: application/json`이어야 한다. | 인터넷에 열리면 읽기도 보호 대상이다. 브라우저는 `fetch`의 `POST`·`PUT`·`DELETE`에 늘 Origin을 붙인다. Funnel이 Host를 어떤 모양으로 넘기는지는 P4에서 확인한다. |
| D6 | 공개 리스너의 `/api/*`는 서버 모드 조회를 빼고 모두 세션이 있어야 한다. 세션이 없으면 `401`이고, 본문은 지금 오류 모양 그대로 `{"error":{"code":"signed_out","message":…}}`이다. `api.rs`의 `ApiErrorCode`에 값 하나를 더하는 최소 변경을 한다. 화면 파일과 로그인 시작은 세션 없이 받는다. | 웹의 오류 해석(`web/src/api/http.ts:103`)이 이 모양만 읽는다(검토 R11). |
| D7 | **요청 제한은 계정 단위다.** 계정마다 토큰 버킷 하나를 두고, 같은 계정의 세션 여럿이 한 버킷을 쓴다. 메모리만 읽는 경로(종목 하나 조회, 종목 검색, 스크리너 상태, 서버 모드)는 한 번에 0.1을 쓴다. **로그인한 요청 전체에 버킷 하나**, **익명 요청에 따로 버킷 하나**를 둔다. 익명 요청은 화면 파일을 빼고 로그인 시작, callback, 세션 조회, 401 응답이다. 로그인 시작에는 버킷이 하나 더 있고, 기존 대기 로그인 한도도 그대로다. 넘으면 `429`와 `Retry-After`를 내고, 본문 `error.retryAt`에 다시 시도할 시각을 싣는다. 시계는 주입한다. IP별 제한은 이번에 하지 않는다. | 세션 단위로 세면 세션을 여러 개 만들어 한도를 늘릴 수 있다. 지도 화면은 종목마다 `/api/symbols/{code}`를 부른다(`queries.ts:61-66`). 그래서 종목이 100개를 넘으면, 메모리 경로에 가중치가 없을 때 한 사람이 혼자 429를 맞는다(검토 P6). 익명 요청을 계정 한도 밖에 두면, 익명 요청만으로 전체 자원을 채울 수 있다(R5). 웹은 `Retry-After` 헤더가 아니라 본문의 `retryAt`만 읽는다(`http.ts:92-95`, P8). IP는 Funnel이 넘기는지 확인하지 않았고, 확인하지 않은 헤더를 믿으면 위조된다. |
| D7a | **모든 한도는 설정(env)이다.** 다시 빌드하지 않고 바꾼다. 이름과 기본값은 `public-listener` 지시서의 표에 있고, `docs/public-operations.md`의 한 표에 같이 둔다. 설정 해석은 `crates/server/src/public/` 안에 두고, `config.rs`에는 부르는 몇 줄만 더한다. | 기본값은 첫 값이다. 바꿀 근거는 D7b가 남긴다. `config.rs`는 다른 탭의 작업도 고친다. |
| D7b | **조정 근거를 센다.** | 한도를 바꿀 근거가 남아야 "운영하면서 조정"이 된다. 지금 대기열 사용량에는 운영자 화면과 샘플러의 호출이 섞여 있다. 그래서 공개 요청이 직접 낸 TR 수와 운영자 쪽 지연을 따로 센다(검토 P10). 계정별 상위 목록은 악성 계정을 찾는 데 쓴다(D16, S3). |
|  | (1) 공개 리스너는 경로 묶음별로 다음을 센다: 응답 수, `429`와 `503` 횟수, 동시 한도에서 기다린 시간(합계와 최대), 공개 요청이 직접 낸 TR 수. 흐름·보드·순위·시장 개요는 공개 경로가 TR 예산을 쓰므로 정확히 세고, 나머지는 대기열 사용량으로 추정한다. | |
|  | (2) 캐시 적중을 센다: 보드, 흐름, 시장 개요 응답 캐시, 스크리너 상태 캐시. 스크리너 결과 재사용은 스냅샷 플랜이 센다. | |
|  | (3) 운영자 리스너는 자기의 키움 경로 응답 시간(분마다 p50과 최대)을 센다. | |
|  | (4) 요청 수 상위 계정 10개를 센다. | |
|  | 이 값들은 운영자 리스너 전용 `GET /api/public-usage`와 분 단위 로그 한 줄로 낸다. | |
| D8 | 수집 현황(`/api/collector/*`)은 공개 리스너에서 **요청한 세션의 계정**이 `VALLY_COLLECTOR_ADMINS`에 있어야 보인다. 운영자 리스너의 판정은 그대로다. | 지금 판정은 서버에 저장된 커넥터 계정으로 한다. 그래서 공개하면 누구나 같은 판정을 받는다. |

### 공용 자료를 여러 사용자에게 줄 때의 부담

| # | 결정 | 이유 |

| D9 | **계정별 셋업.** 공개 리스너의 사용자 자료 라우트(관심종목, 조건식, 히트맵 테마, 화면 상태, 레이아웃, 드로잉)는 지금과 **같은 경로, 같은 JSON**으로 받는다. 저장은 계정 서버 저장소의 그 계정 셋업 문서에 한다. revision 규칙, 삭제 표시, 크기 한도는 ADR 0024와 `crates/setup` 그대로다. 히트맵 보드와 흐름은 공개 리스너에서 **세션 계정의 히트맵 테마 문서**를 쓴다. 보드는 그 문서의 테마로 계산한다. 흐름의 `symbols`는 그 문서에 있는 종목만 받는다. 없는 종목은 지금 `over_limit`처럼 응답에 따로 돌려준다. 두 모듈에는 공개 경로가 쓸 진입 함수 하나씩을 더하는 최소 변경만 한다. 운영자 경로의 동작은 바꾸지 않는다. | 보드가 운영자 DB의 테마를 읽으면 모든 사용자가 운영자 테마를 본다. 흐름이 임의의 종목 60개를 받으면 종목 조합을 바꿔 가며 캐시를 피해 키움 슬롯을 독점할 수 있다(검토 S1). 테마 문서로 묶으면 계정이 부를 수 있는 종목이 테마 저장 한도(100×60) 안으로 정해진다. |
| D10 | **운영자 키 호출 보호.** 목표: 공개 부하가 운영자 화면의 같은 TR 요청을 늦추는 크기에 계산한 상한을 둔다. 아래 (1)~(9)를 둔다. | 검토 P1: 지금 계획대로면 공개 흐름 두 건(60종목씩)이 운영자 분봉 요청을 최대 약 24초 밀어낸다(120 ÷ 5/s). 요청 수로 묶으면 한 요청이 TR을 0~62회 부르므로 보호가 되지 않는다(P3). 묶음을 나누지 않으면, 무거운 흐름 하나 때문에 가벼운 시장 개요 카드까지 모두 503이 된다(P3). 계정당 동시 한도가 없으면 한 계정이 슬롯을 독점한다(S1). 흐름은 서버 캐시 45초가 웹 갱신 60초보다 짧아서 매 갱신이 전부 미스였다. 분 단위로 맞추면 공개 사용자 수와 상관없이 종목마다 분당 1회로 준다. `Gated`가 대기열 공용 관문을 통해 운영자 조회로 번지는 것은 이 단계에서 구조로 막지 못한다(S2). 그래서 공개 쪽이 바로 물러나게 하고, 남는 한계로 적는다. |
|  | (1) **경로 묶음별 동시 한도.** 시장 개요 4, 순위 2, 보드 1, 흐름 1을 둔다. 따로 **계정당 키움 경로 동시 1**을 둔다. 자리가 없으면 기다리지 않고 바로 `503`과 `retryAt`을 낸다. 보드·흐름·시장 개요는 키움을 실제로 부를 때만 자리를 잡는다. 캐시 적중만으로 끝나는 요청은 자리를 쓰지 않는다. 순위는 모듈 안의 캐시를 밖에서 알 수 없으므로 늘 자리를 잡는다. | |
|  | (2) **TR 예산은 요청 수가 아니라 TR 수로 센다.** 흐름과 보드의 공개 진입 함수가 캐시에 없는 종목을 받을 때마다 예산에서 TR 하나를 뺀다. 흐름은 종목 하나, 보드는 100종목 묶음 하나가 TR 하나다. 예산이 없으면 그 종목을 `missing`으로 돌린다. 흐름 예산은 전체 분당 60, 계정당 분당 60이다. 보드 예산은 45초 창당 전체 45다. | |
|  | (3) **흐름은 요청 안에서 동시에 5종목까지만 받는다.** 지금은 `join_all`로 60개를 한꺼번에 받는다. | |
|  | (4) **흐름 캐시를 분에 맞춘다.** 공개 경로에서는 같은 KST 분에 받은 값을 유효로 본다. 공개 모드 웹은 흐름을 분이 바뀐 뒤 2~10초 사이의 무작위 시각에 다시 받는다. 운영자 경로의 45초 규칙은 그대로다. | |
|  | (5) **시장 개요 카드 응답을 캐시한다.** 공개 모듈이 질의 단위로 15초 동안 캐시한다. 지금 카드에는 캐시가 없다(`cards.rs:78`). 샘플러가 받는 것은 장중 흐름(intraday)뿐이다. | |
|  | (6) **순위는 공개 리스너에서 5쪽까지만 받는다.** 더 많이 요청해도 5쪽으로 줄인다. 공개 모드 웹은 5쪽만 요청한다. | |
|  | (7) **공개 경로가 키움 오류 `Gated`나 한도 대기를 받으면** 기다리지 않고 바로 짧은 `retryAt`과 `503`을 낸다. | |
|  | (8) **공개 오류 본문은 고정 문구다.** 키움 오류의 원문(`ApiFailure::kiwoom`의 `e.to_string()`, 포털 IP 등록 안내, 토큰 파일 오류)과 `manualActionRequired`를 싣지 않는다(검토 R3). | |
|  | (9) **계산한 상한.** 운영자 화면의 같은 TR 요청이 공개 부하 때문에 더 기다리는 시간은 (그 TR을 부르는 공개 묶음의 동시 한도 × 공개 요청 하나가 그 TR을 동시에 쌓는 최대 수) ÷ 5초다. 흐름 `ka10080`은 1×5÷5 = **1초**, 보드 `ka10095`는 1×1÷5 = **0.2초**, 순위는 2×5÷5 = **2초**다. 시장 개요는 웜에서 4×3÷5 = **2.4초**다. 시장 개요 `flow`의 하루 첫 콜드(기간마다 최대 약 62회)는 응답 캐시와 투자자 일 캐시가 차기 전 한 번뿐이다. 그 한 번은 최대 약 12초까지 늘 수 있다. 이것은 받아들일 한계로 둔다. 실제 값은 시험이 합성 transport와 가짜 시계로 단정한다. | |
| D11 | **스크리너 한도는 임시다.** 공개 리스너의 `/api/screener/run`에 다음을 둔다. 동시 4(판정 CPU용, 자리가 없으면 바로 503). 계정당 분당 2회. 공개 전체 분당 3회. 스크리너 상태(`/api/screener/status`)는 공개 모듈이 2초 동안 공용으로 캐시한다. 스냅샷 플랜이 병합되면 동시 한도와 전체 분당 한도를 풀고 계정 버킷만 남긴다. | 지금 `run_screen`은 실행할 때마다 `summaries.collect`로 전 종목의 오늘 KRX 시세를 받는다. 약 3,960종목이고 `ka10095` 약 40회다. 시간은 약 8초로 계산했지만 아직 재지 않았다. 재는 일은 `screener-timing`이 한다. 장 밖·주말에도 받는다. 동시 실행은 같은 대상·기준의 수집 하나에 **합류하므로**(`summary.rs:127-134`), 동시 한도로는 TR이 줄지 않는다. 비용은 이어지는 실행이다. 8.5초마다 한 번이면 초당 4.7회다(검토 P5). 그래서 TR은 분당 실행 수로 묶고, 동시 한도는 판정 CPU와 DuckDB 잠금만 지킨다. 상태 1초 폴링은 업데이트 쓰기와 DuckDB `Mutex<Connection>`을 다툰다(P9). |
| D11a | **알려진 한계(IP).** IP를 모르므로 로그인 시작 버킷을 한 사람이 다 쓸 수 있다. 그동안 다른 사람은 로그인을 시작하지 못한다. P4에서 Funnel이 클라이언트 IP를 넘기는지 확인한 뒤 IP별 버킷으로 고친다. | 확인하지 않은 헤더를 믿는 것보다는 전체 버킷이 막히는 쪽이 낫다. 대기 로그인 한도(기본 10,000)는 분당 30으로는 차지 않는다. |
| D12 | **압축과 화면 파일.** | 검토 P2 측정: 1.4MB JS를 brotli 기본 품질로 압축하는 데 1.50초가 걸렸고, 품질 4는 24ms였다. 576KB 보드 응답은 0.58초였다. woff2도 다시 압축했다. 이 압축은 운영자 리스너와 같은 tokio 작업 스레드에서 돈다. 그래서 운영자 리스너도 같은 문제를 겪는다. 운영자 리스너 쪽 변경은 `http.rs` 한 줄이다. 화면 파일은 배포 사이에 바뀌지 않으므로 시작 때 한 번 압축하면 된다. 실시간은 브라우저와 키움 사이에서 바로 오가고 Funnel을 거치지 않는다. 큰 응답은 첫 로딩의 JS(약 1.41MB 한 덩어리), 보드(약 576KB), 스크리너·재무·ETF다(1.5절 4번 정정). |
|  | (1) **두 리스너 모두** 실시간 압축 품질을 4로 낮춘다. 이미 압축된 형식(`font/woff2`, `image/*`, `application/zip` 등)은 압축하지 않는다. | |
|  | (2) 공개 리스너는 화면 파일을 시작 때 한 번 읽어 메모리에 둔다. br(품질 11)과 gzip 사본도 시작 때 블로킹 스레드에서 만들고, `ETag`와 `304`로 답한다. 지금은 요청마다 `tokio::fs::read`로 통째로 읽고 `ETag`가 없다. | |
|  | (3) e2e가 첫 로딩 바이트 수를 기록한다(P14). P4에서는 Funnel 너머의 첫 로딩 시간과 보드 응답 시간을 잰다. | |
|  | (4) 빌드 때 미리 압축하는 것과 JS 나누기는 하지 않는다. 시작 때 압축이 같은 효과를 내고, 번들 나누기는 화면 작업이다. | |

### 로그인과 세션

| # | 결정 | 이유 |
|---|---|---|

### 한 프로세스의 위험과 쿠키·출처 공유

공개 리스너와 운영자 리스너가 같은 프로세스에 있다. 그 프로세스에는 운영자 실전 키와 주문 라우트가 있다. 허용 목록은 라우트를 나눌 뿐이다. 그 밖의 실패(공유 처리 코드의 실수, panic, 자원 고갈)는 인터넷에서 운영자 화면이나 계좌에 닿을 수 있다. 이것을 **알려진 위험**으로 둔다.

**쿠키·출처 공유 분석** (같은 호스트의 443과 8443일 때, `c795199b` 기준)

1. **쿠키.** 쿠키는 포트로 나뉘지 않는다. 그래서 공개 세션 쿠키도 운영자 리스너로 가는 요청에 실린다. 운영자 리스너는 쿠키를 읽지도 두지도 않는다(`crates/server/src/`에 쿠키 처리가 없다). 그래서 지금은 해가 없다. 운영자 리스너가 나중에 쿠키 인증을 쓰면 섞이므로, 그때는 D28이 필요하다.
2. **같은 사이트.** `ts.net`은 공개 접미사라서, 같은 호스트의 두 포트도, 같은 tailnet의 두 노드도 같은 사이트다(검토 R9, `/usr/share/publicsuffix/public_suffix_list.dat`에서 확인). 그러므로 `SameSite=Lax`는 공개 화면에서 운영자로 가는 요청을 막지 않는다. 막는 것은 출처 검사(D5, D27)다.
3. **공개 화면의 스크립트(XSS 등)가 운영자 리스너로 요청하는 경우.** 운영자가 tailnet 기기로 공개 화면을 열었을 때만 생긴다. 운영자 PC의 브라우저에서 연 임의의 외부 사이트도 같은 길로 운영자 리스너에 요청할 수 있다.
   - **쓰기**: 쓰기 가드는 Origin을 비교하므로 막는다. 가드 밖 `POST` 아홉과 사용자 자료 `PUT`은 다르다. `PUT`과 JSON 본문은 preflight를 부르고, 운영자 리스너에는 CORS 응답이 없으므로 브라우저가 보내지 않는다. 그러나 단순 `POST`는 preflight 없이 간다. `POST /api/financial-update`는 본문이 없어도 전 종목 DART 갱신을 시작한다(R2). D27(2)·(3)이 막는다.
   - **읽기**: CORS가 없으므로 응답은 읽히지 않는다. 그러나 요청은 가므로 키움 `GET`이 운영자 키 한도를 쓴다. Origin을 붙이는 요청은 D27(2)가 막는다. Origin이 없는 `no-cors` 요청은 `Sec-Fetch-Site`를 보내는 브라우저에서 D27(3)이 막는다. 그 헤더를 보내지 않는 오래된 브라우저의 `no-cors` `GET`은 남는다(받아들일 한계).
   - **`/api/ws`**: 지금 검사가 없고 WebSocket에는 CORS가 없다. 그래서 운영자 실시간 시세, 연결 상태, 계좌 변경 알림을 읽을 수 있다. 첫 단계에서 반드시 막을 구멍이다. 브라우저는 WebSocket에 늘 Origin을 붙이므로 D27(2)가 막는다.
   - **DNS rebinding**: Host가 공격자 이름이 되므로 D27(1)이 막는다.
4. **운영자 화면의 스크립트가 공개 리스너로 요청하는 경우.** 공개 리스너는 모든 요청의 Host와 Origin을 정확히 비교하고(D5), CORS 응답이 없다. 그래서 막힌다.

**다음 단계의 목표: 운영자 키가 없는 별도 공개 프로세스.** 이렇게 옮기면 D26에 남은 위험(잠금 오염, 공유 코드의 실수, CPU 고갈, 대기열 관문 전파)이 구조로 사라진다.

| 막는 것 | 풀 방법 |
|---|---|
| 스크리너 일봉 저장소(DuckDB)는 두 프로세스가 함께 열 수 없다 | 업데이트 뒤 읽기 전용 사본을 만든다. 또는 스냅샷 플랜 뒤의 메모리 판정 자료를 내보낸다 |
| 공용 자료가 운영자 시세 키로 키움을 부르는데, 같은 키를 두 프로세스가 쓸 수 없다(ADR 0004) | 공개 프로세스 전용 공용 자료 키를 둔다. 또는 운영자 프로세스가 유닉스 소켓으로 읽기 전용 내부 API를 낸다 |
| 종목 목록과 시세 캐시가 운영자 프로세스 메모리에 있다 | 위 내부 API나 스냅샷 파일로 넘긴다 |
| 재무 SQLite | WAL이라 여러 프로세스가 읽을 수 있다. 막지 않는다 |
| 계정 DB | 공개 쪽만 쓴다. 막지 않는다 |

1. 처음에 `adr-public`, `acct-browser-session`, `screener-timing`이 함께 돈다.
2. `acct-browser-session` 뒤에 `public-listener`가 돈다.
3. 그 뒤 `public-user-data`가 돈다.
4. 그 뒤 `web-public-mode`, 그 뒤 `browser-key-vault`가 돈다.

순차로 둔 이유는 다음과 같다.

- `public-listener`는 `acct-browser-session`의 라이브러리 진입점을 붙인다.
- `public-user-data`는 `public-listener`의 공개 라우터, 세션 문, 한도 설정, 계수에 보드·흐름과 사용자 자료를 더한다.
- `web-public-mode`는 `public-listener`의 서버 모드 생성 타입과 로그인 경로를 쓰고, `public-user-data`가 바꾼 흐름 응답 타입을 읽는다.
- `browser-key-vault`는 `web-public-mode`가 비워 둔 자리에 키 화면을 넣는다. `csp.txt`를 고칠 수 있으므로, 같은 폴더를 고치는 `public-user-data` 뒤에 둔다.

이 플랜 안에서 순서 없이 같은 파일을 고치는 작업은 없다.

### 스크리너 공용 스냅샷

사용자가 공개 리스너의 스크리너 제한이 너무 심하다고 했다. 원인은 실행할 때마다 전 종목의 오늘 시세를 새로 받는 것이다(D11). 사용자가 정한 설계(2026-11-22)는 다음과 같다.

1. 서버가 장중 **30초마다** 전 종목의 오늘 시세를 한 번 받아 **최신 하나만 덮어쓴다**. 모든 실행과 모든 사용자가 그것을 같이 쓴다. 결과에는 시세 기준 시각을 보인다.
2. 장 밖에서는 마감 시세를 다시 쓴다. 오늘 봉이 저장된 뒤와 휴장일에는 거의 받지 않는다. 수정주가 대조에 필요한 만큼만 받는다.
3. 오늘 스냅샷은 날짜가 바뀌면 버린다. 일봉 저장소(DuckDB)는 그대로 둔다.
4. 과거 일봉은 판정용으로 메모리에 준비해 두고, 업데이트 때 다시 만든다. 실행은 메모리에서 판정한다. 같은 조건식, 같은 스냅샷이면 결과를 다시 쓴다.
5. 운영자 리스너도 같은 방식으로 맞춘다(기본값).
6. 새 ADR을 쓴다. ADR 0014의 "실행할 때 조회한 오늘 시세"를 "장중 최대 30초 전 스냅샷"으로 바꾼다. 또 ADR 0010의 수정주가 대조가 스냅샷으로도 성립하는지 적는다.
7. 첫 단계는 계측이다. 지금 실행을 오늘 시세 받기와 판정으로 나눠 재고, 동시 판정 1·2·4·8도 잰다(검토 P13). D11의 동시 한도 값의 근거가 된다.
8. 스냅샷이 병합되면 공개 리스너의 스크리너 동시 한도와 전체 분당 한도를 풀고 계정 버킷만 남긴다.
9. 분봉 스크리너는 이번 범위가 아니다.

**나누는 방법.** 7번만 이 플랜의 `screener-timing`으로 한다. 1~6번과 8번은 **별도 플랜 `screener-snapshot`**으로 한다. 이유는 셋이다.

- `screener/**`는 다른 탭의 `market-port-rest`(실행 중)와 `source-select-server`도 다시 짠다. 탭이 달라 `after`로 걸 수 없다. 별도 플랜은 그 둘이 병합된 뒤 쓰면 순서가 저절로 지켜진다.
- 스냅샷은 `market-port-rest`가 만드는 시세 원천 구조 위에 올라가야 한다.
- ADR을 구현과 함께 써야 ADR 0014와 코드가 오래 어긋나지 않는다.

**히트맵 보드가 스냅샷을 읽는 안.** 스냅샷이 생기면 보드는 사용자마다 따로 키움을 부르지 않고 스냅샷을 읽을 수 있다. 그러면 D10(2)의 보드 예산이 필요 없어진다. 코드로 확인한 사실은 다음과 같다.

- 같은 TR이다. 보드는 `quotes::quotes`를 거쳐 `StockQuotes`를 부른다. 응답 행(`wire::QuoteRow`)에 보드가 쓰는 값(`cur_prc`, `base_pric`에서 나오는 등락률, `trde_prica`)이 다 있다.
- 거래소가 다르다. 응답에는 거래소 칸이 없고, 요청한 코드가 거래소를 정한다. 스크리너 스냅샷은 KRX 전용인데 보드의 기본은 통합이다.
- 대상이 다르다. 스크리너 대상(`listed`)에 ETF가 드는지는 확인하지 않았다.
- 통합 거래소를 더하면 30초마다 호출이 약 40회에서 80회로 는다. 그 TR 한도의 약 2.7/5를 늘 쓰게 된다.

제안: `screener-snapshot`의 범위에 넣지 않는다. 그 뒤 작업 `heatmap-snapshot`(사용자 결정 5)으로 둔다.

## 다음 단계 (이 플랜의 작업이 아니다)

첫 단계가 병합된 뒤 각각 플랜으로 만든다. 순서는 권장이다.

1. **브라우저 키움 엔진.** 다중 증권사 플랜의 `market-port-stream`과 `kis-orders`가 병합된 뒤에 한다. 할 일은 다음과 같다.
   - `crates/kiwoom-core`에 실시간 해석, 계좌·주문 TR, 오류 분류, 발급 판단을 둔다. 그 플랜의 `market_source` 구조를 따른다.
   - 이것을 `kiwoom-wasm`으로 감싼다.
   - SharedWorker를 쓰고, 키마다 Web Locks를 둔다. 배포 사이에는 옛 엔진이 물러난다. SharedWorker가 없으면 대표 탭이 맡는다.
   - 발급 기록은 IndexedDB에 둔다.
   - 대기열은 키마다 둔다.
2. **브라우저 실시간.** 체결·호가 WebSocket, 구독 관리(200개, 30초 유예), `domain` 집계(WASM), `/api/ws`와 같은 `ServerMessage`, 숨긴 탭 시험, 실시간 알림을 한다.
3. **브라우저 계좌·주문.** 계좌·주문 TR, 주문 사용 스위치, 주문 명령 기록, 계좌 실시간(`00`·`04`)을 한다. ADR 0029를 따른다.
4. **스크리너 공용 스냅샷(`screener-snapshot`).** 위 1~6번과 8번이다. `market-port-rest`와 `source-select-server`가 병합된 뒤 쓴다.
5. **분봉 스크리너와 히트맵 흐름의 실시간 분봉화.** 수집기의 실시간 체결로 분봉을 만들어 수집 대상 종목부터 한다. 같은 분봉으로 공개 히트맵 흐름이 `ka10080`을 부르지 않게 바꾼다. 그러면 D10(2)의 흐름 예산이 필요 없어진다.
6. **대기열 안의 공개 우선순위와 계수 보강.** 공개용 `Priority` 단계를 따로 두어, 공개 요청이 운영자 화면 요청 뒤에 서게 한다. 관문(`Gated`)이 운영자 쪽으로 번지는 것도 끊는다. 순위·시장 개요 모듈 안의 캐시 적중을 직접 센다. 다중 증권사 플랜 뒤에 한다.
7. **종목 조회 라우트 공개.** 사용자 결정 1에 따른다.
8. **패스키 잠금.** 호스트 이름과 자기 도메인 이전 시점이 정해진 뒤에 한다.
9. **공개 시작.** 운영 단계 P0~P5다.
10. **거두기.** 커넥터 계정 모드와 별도 `vally-account` 실행을 지운다.
11. **별도 공개 프로세스.** 위 표대로 한다.
12. **히트맵 보드가 스냅샷을 읽기(`heatmap-snapshot`).** `screener-snapshot` 뒤에 한다(사용자 결정 5).
13. **보드 미스 모아 받기.** 계정이 여럿일 때 오래된 종목을 모아 100개씩 한 번에 받는다(검토 P4 뒷부분). 12번이 보드의 TR 대부분을 없애므로, 그 뒤에도 필요할 때만 한다.

## 받아들일 한계

- **같은 프로세스(D26).** 공개 처리 중 panic이 `std::sync::Mutex`를 오염시키면, 운영자 쪽(`market/hub.rs`, `bars.rs` 등의 `lock().expect`)도 계속 실패한다. 다음 단계 11이 없앤다.
- **대기열 공유(D10).** 공개 요청은 운영자 화면과 같은 `Priority::Screen` 단계로 나간다. 그래서 같은 TR에서 계산한 상한(흐름 1초, 보드 0.2초, 순위 2초, 시장 개요 웜 2.4초)만큼 운영자를 늦출 수 있다. 시장 개요 `flow`의 하루 첫 콜드는 한 번 약 12초까지 늘 수 있다. 공개 부하가 만든 실패가 공용 관문(`GATE_WAIT` 30초, 반복 실패 시 5분, ADR 0009)을 닫으면, 운영자 조회에도 `Gated`가 번진다. 다음 단계 6이 없앤다.
- **IP를 모름(D11a).** 로그인 시작 버킷을 한 사람이 다 쓸 수 있다.
- **오래된 브라우저의 `no-cors` `GET`(D27).** `Sec-Fetch-Site`를 보내지 않는 브라우저의 Origin 없는 `GET`은 운영자 리스너에 닿는다. 응답은 읽히지 않는다.
- **비밀번호 전환 뒤 조각(D18).** 지워도 브라우저 저장소에 옛 키·암호문 조각이 남을 수 있다.
- **가입 상한 선점(D16).** 차단 목록이 있으므로 받아들인다.
- **추정 부하표.** 10·50·100명 부하표는 사용 패턴 가정에 기댄 추정이다. Funnel의 실제 한계는 P4에서 잰다.

## 사용자가 정해야 하는 결정

구현을 막는 결정은 없다. 모든 작업은 아래 권장안으로 시작한다.

1. **차트 과거 봉과 종목 조회를 누가 주는가** (권장: 서버).
   - 지금 `/api/bars`(`BarService`)는 시세 키로 차트 TR을 부르고 서버 캐시(ADR 0003)에 둔다.
   - 권장안은 공개 리스너가 서버 캐시로 주고, 브라우저는 실시간 체결로 현재 봉만 잇는 것이다. 운영자 키 한도를 더 쓰므로 D10과 같은 방식(TR 예산, 동시 한도, 계산한 상한)을 받는다.
   - 다른 안은 브라우저가 사용자 키로 받는 것이다. 이러면 브라우저 일이 넷이 된다.
2. **한도 기본값.** `public-listener` 지시서의 표에 있는 값으로 시작한다. 모두 설정이다. 바꿀 근거는 `GET /api/public-usage`와 분 단위 로그다.
3. **공개 입구의 호스트 이름** (권장: 별도 노드의 443, D28). P0에서 정한다.
   - 가. 별도 노드(권장): 주소는 `https://<공개 노드>.<tailnet>.ts.net`이다. host-only 쿠키와 출처가 나뉜다. 운영자 노드에는 Funnel 권한이 없다. 대신 기기 하나와 systemd 단위 하나가 는다. 같은 사이트라는 점은 그대로라서 D27이 필요하다.
   - 나. 같은 호스트의 8443: 운영 절차가 가장 적다. 쿠키를 같이 보내지만, 운영자 리스너가 쿠키를 쓰지 않으므로 지금은 해가 없다.
   - 공개 전에 정해야 한다. 나중에 바꾸면 사용자들의 키 보관소가 빈다.
4. **스크리너 스냅샷을 별도 플랜으로 하는 것** (권장: 별도 플랜, 위 이유).
5. **히트맵 보드가 스냅샷을 읽을 때의 범위** (권장: `heatmap-snapshot`에서 정한다).
   - 가. 통합 거래소와 ETF를 스냅샷에 더한다.
   - 나. 스냅샷에 있는 종목만 스냅샷에서 읽는다.

검증을 약하게 하는 작업은 없다. `chute.toml`은 바꾸지 않는다.
