# Funnel 공개 첫 단계 플랜: 공개 리스너, 브라우저 로그인, 브라우저 키 보관

작성일 2026-11-22. 승인 시점의 기록이며 구현 중 바뀐 것은 반영하지 않는다.

## 사용자가 풀려는 문제

사용자는 이 도구를 여러 사람이 웹 화면만 열어 쓰는 서비스로 열려 한다. 공개 방법은 Tailscale Funnel이다. 지금 서버 PC의 `tailscale serve`(ADR 0036)를 바탕으로 무료 요금제로 시작한다. 구조는 PR #754의 ADR 0038 초안에 있다. 사용자 키움 키는 각자 브라우저에만 두고, 수집은 운영 서버 한 곳에서 한다.

사용자의 말: "좋아. funnel 하는걸로 하고 /orch 으로 플래닝해줘."

지금 코드로는 다음이 막는다.

- 로그인은 루프백 흐름뿐이다. 계정 서버(`crates/account-server`)가 일회용 코드를 `http://127.0.0.1:<포트>/auth/complete`로 보내고(`app.rs`의 `connector_url`), 커넥터가 그것을 커넥터 토큰으로 바꾼다. 원격 브라우저에서는 끝나지 않는다. 계정 서버에는 브라우저 세션이 없다.
- `vally-server`에는 사람을 가리는 계층이 없다. 루프백이나 설정한 tailnet 이름으로 오면 모든 라우트에 닿는다. 쓰기 가드(`write_guard.rs`)는 Host·Origin·Content-Type 형식만 본다. 사용자 자료 `PUT`, 스크리너·재무 갱신 `POST`, `/api/ws`, 모든 읽기에는 가드가 없다. 같은 프로세스에 운영자의 실전 키와 주문 라우트가 있다. 그대로 Funnel로 열면 인터넷의 누구나 운영자 계좌에 닿는다.
- 응답에 CSP 같은 보안 헤더가 없다(`http.rs`).
- 사용자 자료는 한 사람의 로컬 SQLite(`data/vally.db`)다. 히트맵 보드(`heatmap_board`)도 그 DB의 테마 하나를 읽는다.

## 확정된 결정

사용자가 정했다(2026-11-22).

1. 여러 사람이 쓰는 서비스로 연다. 사용자가 프로그램을 설치하는 방식(ADR 0023의 커넥터 설치)은 쓰지 않는다.
2. **역할 나누기.** 공용 자료는 운영 서버가 운영자 키(수집 키 포함)로 받고 캐시해서 로그인한 모든 사용자에게 준다. 종목 목록, 일봉 저장소, 스크리너, 재무, ETF, 순위, 시장 개요, 히트맵이 여기에 든다. 브라우저가 사용자 키로 하는 일은 셋뿐이다.
   - 내가 보는 종목의 실시간(WebSocket 체결·호가)
   - 계좌 실시간(WebSocket `00`·`04`)
   - 토큰, 계좌 조회, 주문(REST)
3. 사용자 키움 키는 브라우저에서 입력해 브라우저에만 저장한다. 서버로 보내지 않는다.
4. **키 보호의 기본은 브라우저가 알아서 잠그는 것이다.** 꺼낼 수 없는(`extractable: false`) AES-GCM 키를 IndexedDB에 두고, 키움 키와 토큰을 그 키로 암호화한다. 사용자 입력은 없다. 원하는 사용자만 잠금 비밀번호나 패스키(WebAuthn PRF)를 켠다. 어느 방식이든 키는 서버로 가지 않는다.
5. 수집기는 운영 서버 한 곳에서만 돌린다.
6. 공개 방법은 Tailscale Funnel이다. 무료 요금제로 시작하고 나중에 자기 도메인으로 옮길 수 있다.
7. Google·Naver 로그인, `(provider, subject)` 계정 식별, 셋업 범위는 ADR 0023 그대로다.
8. PR #754(ADR 0038)는 먼저 병합하지 않는다. `adr-public`이 흡수해 2번 역할 나누기로 고친 판을 쓴다. #754는 오케스트레이터가 닫는다.
9. 가입 상한은 100, 공개 포트는 8443이다. 키움 규칙은 Rust 코어를 WASM으로 쓴다. 첫 단계 뒤 다음 단계를 플랜으로 만든다.
10. 실제 Funnel 켜기, IdP 앱 등록, 배포(운영 단계 P1·P2·P4)는 나중에 따로 승인한다(ask #8을 이어받는다).
11. 히트맵 기능은 이 플랜이 새로 짜지 않는다. 공개 리스너에 히트맵 읽기 라우트를 넣는 데까지만 한다.
12. 한도는 모두 설정으로 두고 기본값을 문서에 적는다. 조정 근거(429·503 횟수, 대기 시간, 캐시 적중)를 경로별로 센다. 요청 제한은 계정 단위이고, 공개 리스너 전체 상한을 하나 둔다(D7·D7a·D7b).
13. 스크리너는 공용 스냅샷 방식으로 바꾼다. 장중 30초마다 한 번 받아 모두가 같이 쓰고, 운영자 리스너도 같은 방식으로 맞춘다(아래 "스크리너 공용 스냅샷"). 분봉 스크리너는 나중에 한다.
14. 한 프로세스 위험을 알려진 위험으로 적고 첫 단계에서 줄인다. 쿠키·출처 공유를 분석하고 별도 호스트 이름 안을 검토한다. 히트맵 보드가 스냅샷을 쓰는 안을 검토한다(아래 "한 프로세스의 위험과 쿠키·출처 공유", "스크리너 공용 스냅샷").

## 이번 플랜의 범위

공개 서버의 뼈대와 브라우저 키 보관까지가 첫 단계다. 첫 단계가 끝나면 다음이 된다.

- 운영 서버가 운영자용 주소와 따로 연 **공개 리스너**에서, 로그인한 사용자에게 공용 자료와 계정별 셋업을 준다. 운영자 라우트는 공개 리스너에 없다.
- 브라우저가 공개 주소에서 Google·Naver로 직접 로그인한다.
- 브라우저가 키움 키를 암호화해 저장하고, 엄격한 CSP 아래에서 돈다.
- 지금 서버 PC의 로컬 전용 운영과 수집은 그대로 돈다.

브라우저 키움 엔진(실시간, 계좌 실시간, 토큰·계좌·주문)은 다음 단계다(아래 "다음 단계" 1). 그 일은 `crates/server/src/kiwoom/`과 `trading/`, `market/`을 꺼내 쓰는데, 지금 다른 탭의 다중 증권사 플랜(`order-accounts` 실행 중, `market-port-rest`·`market-port-stream`·`source-select-server`·`kis-orders` 대기)이 바로 그 파일들을 다시 짜고 있다. 그 작업들이 병합된 뒤 증권사 공통 구조 위에서 꺼내는 것이 충돌도 적고 다시 할 일도 적다.

## 스스로 정한 결정과 이유

사용자가 바꾸라고 하면 바꾼다.

### 공개 서버 구조

| # | 결정 | 이유 |
|---|---|---|
| D1 | 공개 모드는 지금 `vally-server` 프로세스에 **두 번째 리스너**(공개 리스너)를 더해 받는다. `VALLY_PUBLIC_BIND`(루프백만)와 `VALLY_PUBLIC_ORIGIN`이 둘 다 있을 때만 뜬다. 없으면 지금과 똑같다. | 운영자 리스너(8080)와 같은 프로세스라 스크리너 DuckDB, 재무 DB, 종목 목록, 시세 캐시, 운영자 키의 요청 대기열을 그대로 나눠 쓴다. 공개 인스턴스를 따로 띄우면 DuckDB 파일을 두 프로세스가 열 수 없고, 같은 키움 키로 두 프로세스가 붙게 된다(ADR 0004). 운영자 리스너는 바뀌지 않으므로 지금 운영이 끊기지 않는다. |
| D2 | 공개 리스너의 라우터는 **허용 목록**으로 만든다. 넣는 것: 화면 파일, 로그인·세션(`/v1/…`), 서버 모드 조회, 공용 자료 읽기(종목 목록·검색, 스크리너 실행·상태, ETF, 재무 읽기, 순위, 시장 개요, 히트맵 흐름), 계정별 셋업과 히트맵 보드(D9), 수집 현황(운영자 계정만). 넣지 않는 것: `/api/ws`, `/api/system/*`, `/api/trading/*`, 커넥터 계정 라우트, 셋업 내보내기·가져오기, 스크리너·재무 갱신 `POST`. 차트 봉, 현재가·당일 요약, 기본 정보, 투자자, 체결·호가·프로그램 조회는 사용자 결정 1이 정해질 때까지 넣지 않는다. | 공용 자료는 운영 서버가 준다(확정 2). 운영자 라우터를 걸러서 만들면 새 라우트가 운영자 라우터에 생길 때 공개 리스너에 저절로 열린다. 허용 목록이면 그렇지 않다. 읽기와 쓰기가 한 모듈에 섞인 스크리너·재무는 공개 모듈이 `(메서드, 경로)` 허용 목록으로 감싸서, 그 밖의 경로는 404로 낸다. 시험이 운영자 라우트 목록을 공개 리스너에 보내 모두 404인지 확인한다. |
| D3 | Funnel은 **8443 포트**로 공개 리스너만 연다: `tailscale funnel --bg --https=8443 http://127.0.0.1:<공개 포트>`. 443의 `tailscale serve`(tailnet 전용, 운영자 리스너)는 그대로 둔다. | Funnel은 포트 단위로 켠다. 그래서 운영자 리스너는 망 수준에서 인터넷에 닿지 않는다. 지금 운영자 주소도 바뀌지 않는다. 사용자 주소는 `https://<서버>.<tailnet>.ts.net:8443`이다. 호스트 이름을 운영자 주소와 나누는 안(D28)은 사용자 결정 6이다. 코드는 `VALLY_PUBLIC_ORIGIN`만 보므로, 어느 안이든 코드는 같다. |
| D4 | 계정 기능은 `account-server` 크레이트를 라이브러리로 써서 공개 리스너 프로세스 안에 붙인다. `server`가 `account-server`에 의존하고 그 반대는 없다. 별도 `vally-account` 실행과 커넥터 루프백 흐름은 지우지 않는다. | 세션 확인이 함수 호출이 된다. ADR 0023의 "계정 서버는 `server`·`collector`·`domain`에 의존하지 않는다"는 그대로 지켜진다. |
| D5 | 공개 리스너는 **모든 요청**의 Host를 확인한다. Host는 `VALLY_PUBLIC_ORIGIN`의 호스트(포트 포함)와 정확히 같아야 한다. Origin이 있으면 그 출처와 같아야 한다. `GET`·`HEAD`·`OPTIONS`가 아닌 요청은 Origin이 반드시 있고 `Content-Type: application/json`이어야 한다. | 인터넷에 열리면 읽기도 보호 대상이다. 브라우저는 `fetch`의 `POST`·`PUT`·`DELETE`에 늘 Origin을 붙인다. Funnel이 Host를 어떤 모양으로 넘기는지는 P4에서 확인한다. |
| D6 | 공개 리스너의 `/api/*`는 서버 모드 조회를 빼고 모두 세션이 있어야 한다. 세션이 없으면 `401`과 `{"error":"signed_out"}`을 낸다. 화면 파일과 로그인 시작은 세션 없이 받는다. | 로그인하지 않은 요청이 닿는 범위를 화면 파일, 로그인, 모드 조회로 줄인다. |
| D7 | 요청 제한은 프로세스 안에서 **계정 단위**로 한다. 계정마다 토큰 버킷 하나를 둔다(기본 초당 20, 묶음 100). 같은 계정의 세션이 여럿이어도 한 버킷을 쓴다. 그 위에 **공개 리스너 전체 버킷**을 하나 더 둔다. 모든 계정의 합계이고 기본은 초당 200, 묶음 400이다. 로그인 시작에는 전체 버킷(기본 분당 30)과 기존 대기 로그인 한도를 둔다. 넘으면 `429`와 `Retry-After`를 낸다. 시계는 주입한다. IP별 제한은 이번에 하지 않는다. | 세션 단위로 세면, 한 계정이 세션을 여러 개 만들어 한도를 늘릴 수 있다. 전체 버킷이 없으면 계정 100개 × 계정 한도가 그대로 서버 PC와 Funnel로 온다. Funnel 뒤에서 클라이언트 IP가 어떤 헤더로 오는지는 확인하지 않았고, 확인되지 않은 헤더를 믿으면 위조된다. |
| D7a | **모든 한도는 설정(env)으로 뺀다.** 다시 빌드하지 않고 바꿀 수 있어야 한다. 이름과 기본값은 `docs/public-operations.md`의 한 표에 둔다. 대상은 계정 버킷, 전체 버킷, 로그인 버킷, 키움 경로 동시 한도, 키움 경로 계정 버킷, 히트맵 보드의 갱신 창당 새 종목 상한, 스크리너 동시 한도다. 설정 해석은 `crates/server/src/public/` 안에 두고, `config.rs`에는 부르는 한 줄만 더한다. | 기본값은 근거 없이 정한 첫 값이다. 운영하면서 바꿀 수 있어야 한다. `config.rs`는 다른 탭의 작업도 고친다. |
| D7b | **조정 근거를 센다.** 공개 리스너는 경로별로 다음을 센다: 응답 수, `429`와 `503` 횟수, 동시 한도에서 기다린 시간(합계와 최대), 운영자 시세 키의 TR 호출 수. 이 값들을 운영자 리스너 전용 상태 API(`GET /api/public-usage`, 공개 리스너에는 없다)와 분 단위 로그 한 줄로 낸다. 캐시 적중 수는 둘로 나눠 센다. 히트맵 보드는 `public-user-data`가 보드 안에서 직접 센다. 스크리너는 스냅샷 플랜(아래 "스크리너 공용 스냅샷")이 결과 재사용을 직접 센다. 순위·시장 개요·히트맵 흐름은 그 모듈을 고치지 않으므로, 요청 수 대비 TR 호출 수로 추정한다. | 한도를 바꿀 근거가 남아야 "운영하면서 조정"이 된다. 세 모듈은 다른 탭 작업이 고치는 중이라, 모듈 안의 적중을 직접 세는 일은 다음 단계로 미룬다. |
| D8 | 수집 현황(`/api/collector/*`)은 공개 리스너에서 **요청한 세션의 계정**이 `VALLY_COLLECTOR_ADMINS`에 있어야 보인다. 운영자 리스너의 판정은 그대로다. | 지금 판정은 서버에 저장된 커넥터 계정으로 하므로, 공개하면 누구나 같은 판정을 받는다. 키, 주문, 갱신, 시스템 설정 같은 나머지 운영 기능은 공개 리스너에 아예 없다(D2). |

### 공용 자료를 여러 사용자에게 줄 때의 부담

| # | 결정 | 이유 |
|---|---|---|
| D9 | 공개 리스너의 사용자 자료 라우트(관심종목, 조건식, 히트맵 테마, 화면 상태, 레이아웃, 드로잉)는 지금과 **같은 경로, 같은 JSON**으로 받는다. 저장은 계정 서버 저장소의 그 계정 셋업 문서에 한다. revision 규칙, 삭제 표시, 크기 한도는 ADR 0024와 `crates/setup` 그대로다. 히트맵 보드(`/api/heatmap/board`)는 공개 리스너에서 세션 계정의 히트맵 테마 문서로 계산한다. 보드의 계산 함수가 테마 문서를 인수로 받게 하는 최소 변경만 하고, 히트맵 동작은 바꾸지 않는다. | 셋업 문서 본문이 지금 HTTP 본문 JSON 그대로라서 웹 저장 계층을 바꾸지 않아도 된다. 보드가 운영자 DB의 테마를 읽으면 모든 사용자가 운영자의 테마를 보게 된다. |

| D11 | **스크리너 동시 실행은 임시 한도다.** 공개 리스너의 `/api/screener/run`은 동시에 한도(기본 2)만큼만 돈다. 넘으면 기다리다 시간이 지나면 `503`을 낸다. 계정 버킷도 받는다. 스냅샷 플랜이 병합되면 동시 한도를 풀고 계정 버킷만 남긴다. 그 일은 스냅샷 플랜의 마지막 작업이 한다. | 지금 `run_screen`은 실행할 때마다 `summaries.collect`로 전 종목의 오늘 KRX 시세를 운영자 키로 새로 받는다. 약 3,960종목이고, `StockQuotes`를 100개씩 약 40회 부르며, 약 8초 걸린다. 장 밖과 주말에도 그렇다. 공개 사용자 여럿이 동시에 돌리면 운영자 키 한도와 수집 마감이 밀린다. 원인을 없애는 것이 스냅샷이다. |
| D11a | **알려진 한계(IP).** IP를 모르므로 로그인 시작 전체 버킷(D7)을 한 사람이 다 쓸 수 있다. 그동안 다른 사람은 로그인을 시작하지 못한다. P4에서 Funnel이 클라이언트 IP를 넘기는지 확인한 뒤 IP별 버킷으로 고친다. | 확인되지 않은 헤더를 믿는 것보다는, 전체 버킷이 막히는 쪽이 낫다. |
| D12 | **Funnel 대역폭.** 실시간은 브라우저와 키움 사이에서 바로 오가고 Funnel을 거치지 않는다. 공개 리스너는 지금처럼 압축(`CompressionLayer`)과 해시 붙은 정적 파일의 `immutable` 캐시를 쓴다. Funnel의 실제 대역폭 한계는 P4에서 재고, 막히면 자기 도메인으로 옮기는 시점을 앞당기는 근거로 쓴다. | 무료 Funnel의 한계를 저장소가 모른다. 큰 응답은 공용 자료(스크리너 결과, 재무, ETF)뿐이다. |

### 한 프로세스의 위험과 쿠키·출처 공유

공개 리스너와 운영자 리스너가 같은 `vally-server` 프로세스에 있다. 그 프로세스에 운영자 실전 키와 주문 라우트가 있다. 허용 목록은 라우트를 나눌 뿐이다. 그 밖의 실패(공유 처리 코드의 실수, panic, 자원 고갈)는 인터넷에서 운영자 화면이나 계좌에 닿을 수 있다. 이것을 **알려진 위험**으로 둔다. 첫 단계에서 줄이는 장치와 남는 것은 다음과 같다.

| # | 결정 | 이유 |
|---|---|---|
| D26 | **공개 리스너의 격리 장치** (`public-listener`의 성공 조건에 넣는다). (1) 공개 라우터 전체를 panic 잡기 층(`tower-http`의 `CatchPanicLayer`)으로 감싼다. 공개 처리에서 panic이 나면 그 요청만 500이고, 운영자 리스너는 계속 응답한다. (2) 공개 리스너 전체의 동시 처리 요청 수 상한(기본 64)과 요청 시간 상한(기본 30초)을 둔다. 둘 다 설정이다(D7a). 공개 요청이 몰려도 런타임 작업, 블로킹 스레드, DuckDB 읽기 연결을 다 쓰지 못한다. (3) 키움을 부르는 공개 경로는 D10의 동시 한도를 받는다. 운영자 대기열 전체를 차지하지 못한다. (4) 공개 리스너는 운영자 SQLite(`data/vally.db`)를 쓰지 않는다. 사용자 자료는 계정 DB에 있다(D9). | 같은 프로세스에서 막을 수 있는 것은 "공개 쪽 실패가 프로세스 전체로 번지지 않게" 하는 데까지다. 지금 빌드는 `panic = "abort"`가 아니라서, axum의 요청 panic은 그 연결 작업만 끝낸다. 하지만 공개 요청이 쥔 `std::sync::Mutex`가 panic으로 오염되면, 같은 잠금을 쓰는 운영자 처리도 실패할 수 있다. 이것은 같은 프로세스에서는 구조로 막지 못한다. 남는 위험으로 적는다. |
| D27 | **운영자 리스너도 출처를 본다** (`public-listener`가 한다). 운영자 리스너는 Origin이 있는데 자기 출처(루프백이면 `http://<Host>`, tailnet 이름이면 `https://<Host>`)가 아니면 **모든 메서드와 `/api/ws` 업그레이드**를 거절한다. 지금은 쓰기만 이 검사를 받는다. `http.rs`의 라우터에 층 하나를 더하는 최소 변경으로 한다(D25). 개발 프록시처럼 Origin이 다르게 오는 지금의 개발 흐름이 깨지지 않는지 확인한다. | 아래 분석 3번. 지금 `/api/ws`에는 Origin·Host 검사가 없다(`ws.rs`). WebSocket에는 CORS가 걸리지 않는다. 그래서 다른 출처의 스크립트도 운영자 실시간을 읽을 수 있다. |
| D28 | **공개 입구를 별도 호스트 이름으로 여는 안** (사용자 결정 6, 권장). 서버 PC에 두 번째 `tailscaled`를 띄운다. 상태 폴더와 소켓을 따로 쓰고 `--tun=userspace-networking`으로 돈다. 이것이 tailnet의 별도 노드(예: `<공개 노드>.<tailnet>.ts.net`)가 된다. `funnel` 노드 속성은 그 노드에만 준다. 그 노드의 443에서 `tailscale --socket=<두 번째 소켓> funnel --bg 443 http://127.0.0.1:<공개 포트>`로 공개 리스너만 연다. 운영자 노드에는 Funnel 권한이 없다. | 호스트가 다르면 host-only 쿠키를 서로 보내지 않는다. 출처가 포트가 아니라 이름으로 나뉜다. 운영자 노드가 실수로 Funnel을 켤 권한 자체가 없다. 공개 주소에 포트가 붙지 않아 IdP callback도 깔끔하다. 비용은 기기 하나, systemd 단위 하나, 운영 절차가 조금 는다. `tsnet`(Tailscale을 프로그램에 넣는 Go 라이브러리)은 `vally-server`가 Rust라서 쓸 수 없다. 별도 Go 프록시를 하나 더 두는 셈이 되어 고르지 않았다. |

**쿠키·출처 공유 분석** (D3대로 같은 호스트의 443과 8443일 때. main `175d5a76` 기준)

1. **쿠키.** 쿠키는 포트로 나뉘지 않는다. 그래서 공개 세션 쿠키(`__Host-vally_session`, host-only)는 운영자 리스너(443)로 가는 요청에도 실린다. 운영자 리스너는 쿠키를 읽지도 두지도 않는다(`crates/server/src/`에 쿠키 처리가 없다). 그래서 지금은 해가 없다. 나중에 운영자 리스너가 쿠키 인증을 쓰기 시작하면 공개 쿠키와 섞이므로, 그때는 D28이 필요하다.
2. **같은 사이트.** 둘은 출처가 다르지만 같은 사이트일 수 있다. 그러면 `SameSite`가 공개 화면에서 운영자로 가는 요청을 막지 않는다. `ts.net`이 Public Suffix List에 어떤 모양으로 들어 있는지에 따라, 이름이 다른 노드끼리도 같은 사이트인지가 갈린다. P3에서 확인한다. 어느 쪽이든 아래 출처 검사로 막는다.
3. **공개 화면의 스크립트(XSS 등)가 운영자 리스너로 요청하는 경우.** 운영자 리스너는 tailnet 기기에서만 닿는다. 그래서 이 경우는 운영자가 자기 기기로 공개 화면을 열었을 때만 생긴다.
   - **쓰기**: 지금 쓰기 가드가 Origin을 `https://<Host>`와 비교하므로 막힌다. 가드 밖 `POST` 넷(스크리너 갱신·취소·실행, 순위)과 사용자 자료 `PUT`은 다르다. `PUT`과 `Content-Type: application/json`은 preflight를 부르고, 운영자 리스너에 CORS 응답이 없으므로 브라우저가 보내지 않는다. 그러나 `text/plain` 같은 단순 `POST`는 preflight 없이 간다. 스크리너 갱신 같은 부작용이 생길 수 있다. D27이 막는다.
   - **읽기**: CORS 응답 헤더가 없으므로 스크립트가 응답을 읽지 못한다. 요청 자체는 가므로, 키움을 부르는 `GET`은 운영자 키 한도를 쓴다. D27이 막는다.
   - **`/api/ws`**: Origin 검사가 없고 WebSocket에는 CORS가 없다. 스크립트가 운영자 실시간 시세, 키움 연결 상태, 계좌 변경 알림을 읽을 수 있다. 첫 단계에서 실제로 막아야 할 구멍이다. D27이 막는다.
   - **계좌번호 조회**: `GET /api/trading/account-number`는 Host만 본다. CORS가 없으므로 응답은 읽지 못한다. D27이 요청 자체를 막는다.
4. **운영자 화면의 스크립트가 공개 리스너로 요청하는 경우.** 공개 리스너는 모든 요청의 Origin을 자기 출처와 정확히 비교하고(D5), CORS 응답이 없다. 그래서 막힌다.

**다음 단계의 목표: 운영자 키가 없는 별도 공개 프로세스.** 공개 리스너를 운영자 키·주문 코드가 없는 다른 프로세스로 옮기면, D26에 남은 위험(잠금 오염, 공유 코드의 실수, CPU 고갈)이 구조로 사라진다. 그 길을 막는 것과 풀 방법은 다음과 같다.

| 막는 것 | 풀 방법 |
|---|---|
| 스크리너 일봉 저장소(DuckDB)는 두 프로세스가 함께 열 수 없다 | 업데이트가 끝날 때마다 읽기 전용 사본을 공개 프로세스 폴더에 만든다. 또는 스크리너 스냅샷 플랜 뒤의 메모리 판정 자료를 운영자 프로세스가 내보내고, 공개 프로세스가 받는다 |
| 순위, 시장 개요, 히트맵 같은 공용 자료가 운영자 시세 키로 키움을 부른다. 같은 키를 두 프로세스가 쓸 수 없다(ADR 0004) | 공개 프로세스 전용으로 공용 자료 키를 하나 더 둔다(주문 코드 없는 프로세스). 또는 운영자 프로세스가 공용 자료를 유닉스 소켓의 읽기 전용 내부 API로 내준다 |
| 종목 목록과 시세 캐시가 운영자 프로세스 메모리에 있다 | 위 내부 API나 스냅샷 파일로 넘긴다 |
| 재무 SQLite | WAL이라 여러 프로세스가 읽을 수 있다. 막지 않는다 |
| 계정 DB | 공개 쪽만 쓴다. 막지 않는다 |

이 일은 스크리너 스냅샷 플랜과 다중 증권사 플랜 뒤에 한다(다음 단계 11).

병렬: 처음에 `adr-public`, `acct-browser-session`, `screener-timing`이 함께 돈다. `acct-browser-session` 뒤에 `public-listener`가 돈다. 그 뒤 `public-user-data`와 `web-public-mode`가 함께 돈다. 둘이 끝나면 `browser-key-vault`가 돈다.

순차로 둔 이유:

- `public-listener`는 `acct-browser-session`이 내놓은 라이브러리 진입점(라우터, 세션 확인)을 붙인다.
- `public-user-data`는 `public-listener`의 공개 라우터와 세션 문에 라우트를 더하고, `acct-browser-session`의 셋업 저장소 함수를 부른다.
- `web-public-mode`는 `public-listener`가 만든 서버 모드 생성 타입과 로그인 경로를 쓴다.
- `browser-key-vault`는 `web-public-mode`가 공개 모드에서 비워 둔 시스템 설정 자리에 키 화면을 넣는다. `crates/server/src/public/csp.txt`를 고칠 수 있으므로, 같은 폴더를 고치는 `public-user-data` 뒤에 둔다.

이 플랜 안에서 순서 없이 같은 파일을 고치는 작업은 없다. `adr-public`, `acct-browser-session`, `screener-timing`은 겹치는 파일이 없다.

### 스크리너 공용 스냅샷

사용자가 공개 리스너의 스크리너 동시 2개 제한(D11)이 너무 심하다고 했다. 원인은 실행할 때마다 전 종목의 오늘 시세를 새로 받는 것이다(D11의 이유). 사용자가 정한 설계는 다음과 같다(2026-11-22).

1. 서버가 장중 **30초마다** 전 종목의 오늘 시세를 한 번 받아, **최신 하나만 덮어쓴다**. 모든 실행과 모든 사용자가 그것을 같이 쓴다. 결과에는 시세 기준 시각을 보인다.
2. 장 밖에서는 마감 시세를 다시 쓴다. 오늘 봉이 저장된 뒤와 휴장일에는 거의 받지 않는다. 수정주가 대조에 필요한 만큼만 받는다.
3. 오늘 스냅샷은 날짜가 바뀌면 버린다. 일봉 저장소(DuckDB)는 그대로 둔다.
4. 과거 일봉은 판정용으로 메모리에 준비해 두고, 업데이트 때 다시 만든다. 실행은 메모리에서 판정한다. 같은 조건식, 같은 스냅샷이면 결과를 다시 쓴다.
5. 운영자 리스너도 같은 방식으로 맞춘다(기본값).
6. 새 ADR을 쓴다. ADR 0014의 "실행할 때 조회한 오늘 시세"를 "장중 최대 30초 전 스냅샷"으로 바꾼다. ADR 0010의 수정주가 대조(기준가와 저장된 종가가 30% 넘게 다를 때 감지)가 스냅샷으로도 성립하는지 적는다.
7. 첫 단계는 계측이다. 지금 실행 시간을 오늘 시세 받기와 판정으로 나눠 잰다(가짜 transport와 가짜 시계, 실제 키움 호출 없음).
8. 스냅샷이 병합되면 공개 리스너의 스크리너 동시 한도를 풀고 계정 버킷만 남긴다.
9. 분봉 스크리너는 이번 범위가 아니다(다음 단계에 한 줄로 적는다).

**나누는 방법.** 7번(계측)만 이 플랜의 `screener-timing`으로 한다. 1~6번과 8번은 **별도 플랜 `screener-snapshot`**으로 뺀다. 이유는 셋이다.

- `screener/**`는 다른 탭 다중 증권사 플랜의 `market-port-rest`(오늘 시세 수집을 시세 원천 구조로 옮긴다)와 `source-select-server`도 다시 짠다. 탭이 달라서 `after`로 순서를 걸 수 없다. 별도 플랜은 그 두 작업이 병합된 뒤 쓰고 시작하면 순서가 저절로 지켜진다.
- 스냅샷 받기는 `market-port-rest`가 만든 시세 원천 구조 위에 올라가야 한다. 먼저 짜면 그 작업이 다시 옮겨야 한다.
- ADR도 그 플랜이 구현과 함께 쓴다. ADR만 먼저 병합하면 코드가 ADR 0014대로 도는 동안 문서와 코드가 오래 어긋난다.

`screener-timing`은 새 시험 파일 하나만 더하고 서버 코드는 고치지 않는다. 그래서 지금 바로 돌아도 다른 탭 작업과 부딪히지 않는다. 그 숫자가 `screener-snapshot` 플랜의 출발점이 된다. 8번(D11 풀기)은 `screener-snapshot`의 마지막 작업이 `public-listener`가 만든 설정의 기본값을 바꾸는 것으로 한다.

**히트맵 보드가 스냅샷을 읽는 안.** 스냅샷이 생기면 보드가 사용자마다 따로 키움을 부르지 않고 스냅샷을 읽게 할 수 있다. 그러면 D10(3)의 새 종목 상한이 필요 없어지고 운영자 키 부담이 준다. 지금 코드(main `175d5a76`)로 확인한 사실은 다음과 같다.

- 같은 TR이다. 보드는 `quotes::quotes`를 거쳐 `StockQuotes`를 100종목씩 부른다. 스크리너 수집(`screener/summary.rs`)도 `StockQuotes`다. 응답 행(`wire::QuoteRow`)에 보드가 쓰는 값이 다 있다: 현재가(`cur_prc`), 기준가(`base_pric`)에서 나오는 등락률, 거래대금(`trde_prica`), 거래량(`trde_qty`). 보드가 쓰는 것은 `change_rate`와 `traded_million_won`뿐이다(`heatmap_board/board.rs`의 `board_theme`).
- 거래소가 다르다. 응답 행에는 거래소 칸이 없다. 거래소는 요청한 종목 코드(`StockQuotes::of_venues`)로 정해진다. 스크리너 스냅샷은 KRX만 받는다(ADR 0014). 보드의 기본 거래소는 통합(`Venue::Combined`)이고 NXT도 받는다. 그래서 KRX 스냅샷만으로는 기본 보드를 그릴 수 없다.
- 대상이 다르다. 스크리너 대상은 일봉 저장소의 `listed` 표다. 보드 테마에는 ETF도 들어간다. `listed`에 ETF가 드는지는 확인하지 않았다. 스냅샷 플랜에서 확인한다.
- 비용: 통합 스냅샷을 따로 받으면 30초마다 `StockQuotes` 호출이 약 40회 → 약 80회가 된다. 같은 키의 `StockQuotes` 한도(초당 5, ADR 0035) 가운데 약 2.7회를 늘 쓰게 된다. 관심종목 현재가 조회도 같은 TR을 쓴다.

제안: 보드가 스냅샷을 읽는 일은 `screener-snapshot`의 범위에 넣지 않는다. 그 플랜이 병합된 **뒤의 작업**(`heatmap-snapshot`, 같은 플랜의 뒷 작업이나 다음 플랜)으로 둔다. 그 작업이 할 일은 셋이다. 스냅샷에 통합 거래소와 ETF를 더할지 정하는 것(사용자 결정 7). 보드가 스냅샷에 있는 종목은 스냅샷에서 읽고, 없는 종목만 지금 경로로 받게 하는 것. 그 뒤 D10(3)의 상한 기본값을 푸는 것. 스냅샷 플랜은 KRX 스크리너 규칙(ADR 0014·0010)을 바꾸는 일이라 그것만으로 충분히 크다. 거래소·대상 범위를 늘리는 것은 비용 결정이 따로 필요하다. 이번 플랜의 히트맵 최소 변경 원칙은 그대로다.

2. **브라우저 실시간.** 내가 보는 종목의 체결·호가 WebSocket을 다룬다. 구독 관리(200개 한도, 30초 유예)를 하고, 봉 이어 붙이기는 `domain` 집계를 WASM으로 쓴다. 엔진은 탭에 지금 `/api/ws`와 같은 `ServerMessage`를 보내 화면 코드를 바꾸지 않는다. 숨긴 탭에서 시험한다. 실시간 알림(ADR 0005)도 여기에 든다.
3. **브라우저 계좌·주문.** 계좌·주문 TR, 주문 사용 스위치, 주문 명령 기록, 계좌 실시간(`00`·`04`)을 다룬다. ADR 0029 규칙 그대로다.
4. **스크리너 공용 스냅샷 플랜(`screener-snapshot`).** 위 "스크리너 공용 스냅샷"의 1~6번과 8번이다. 다중 증권사 플랜의 `market-port-rest`와 `source-select-server`가 병합된 뒤 쓴다. `screener-timing`의 숫자를 출발점으로 삼는다.

## 운영 단계 (병합 뒤, ★는 사용자 승인)

이 단계들은 `tasks.json`의 작업이 아니다. `public-listener`, `public-user-data`, `web-public-mode`가 병합된 뒤에는 로그인부터 tailnet 안에서 확인할 수 있다.

| 단계 | 누가 | 내용 |
|---|---|---|
| P1 ★ | 사용자 | Google Cloud OAuth 클라이언트와 Naver 앱을 등록한다. callback은 `https://<서버>.<tailnet>.ts.net:8443/v1/auth/google/callback`과 `…/naver/callback`이다. client id·secret은 서버 PC의 env 파일(600)에만 둔다 |
| P2 ★ | 오케스트레이터 | 서버 PC 배포에 공개 리스너 설정을 더하고 승인 뒤 `orch deploy run`으로 반영한다(`docs/public-operations.md`) |
| P3 | 오케스트레이터 | Funnel 없이 tailnet 전용으로 8443을 연다(`tailscale serve --bg --https=8443 http://127.0.0.1:<공개 포트>`). 개발 PC 브라우저로 로그인, 셋업 저장, 공용 자료 읽기, 운영자 라우트 404를 확인한다. 쿠키·출처도 확인한다. 공개 화면을 연 브라우저에서 운영자 주소로 가는 요청에 어떤 쿠키가 실리는지 본다. 공개 출처에서 운영자 `/api/ws`를 열거나 단순 `POST`를 보내면 거절되는지 본다(D27). `ts.net` 이름끼리 같은 사이트로 다뤄지는지 본다(D28 분석 2). D28을 골랐으면 이 단계에서 두 번째 `tailscaled` 노드를 띄우고, 그 노드의 443을 tailnet 전용으로 먼저 연다 |
| P4 ★ | 사용자·오케스트레이터 | 사용자가 관리 콘솔에서 tailnet 정책의 서버 PC에 `funnel` 노드 속성을 더한다. 오케스트레이터가 `tailscale funnel --bg --https=8443 http://127.0.0.1:<공개 포트>`로 켠다. 확인할 것: 인터넷에서 오는 Host 모양(포트 포함 여부), 클라이언트 IP 헤더, 443이 여전히 tailnet 전용인지, 운영자 라우트가 404인지, 큰 응답(스크리너 결과)의 전송 시간. D28을 골랐으면 `funnel` 속성은 공개 노드에만 있고 운영자 노드는 Funnel을 켤 수 없는지도 확인한다 |
| P5 | 오케스트레이터 | 되돌리기를 확인한다: `tailscale funnel --https=8443 off`를 하고, 공개 리스너 설정을 지우고 재시작하면 지금과 같아야 한다 |

## 사용자가 정해야 하는 결정

구현을 막는 결정은 없다. 모든 작업은 아래 권장안으로 시작한다.

1. **차트 과거 봉과 종목 조회를 누가 주는가** (권장: 서버).
   - 지금 코드에서는 `/api/bars`·`/api/bars/jump`(`bars.rs`의 `BarService`)가 시세 키로 키움 차트 TR을 부르고, 결과를 서버 캐시(ADR 0003)에 둔다. 일봉은 수집한 일봉 저장소가 있다.
   - 권장안: 과거 봉, 현재가·당일 요약, 기본 정보, 투자자, 체결·호가 조회를 공개 리스너가 서버 캐시로 준다. 브라우저는 실시간 체결로 현재 봉만 이어 붙인다. 과거 봉은 누구에게나 같아서, 같은 종목·주기는 캐시 한 벌을 모두가 쓴다. 이렇게 하면 브라우저의 일이 확정 2의 셋으로 남는다. 대신 운영자 키 한도를 더 쓰므로 D10의 보호를 받는다.
   - 다른 안: 브라우저가 사용자 키로 과거 봉을 받는다. 한도가 사용자마다 나뉘지만, 브라우저 일이 넷이 되고, 차트 해석 코드도 WASM으로 옮겨야 한다.
   - 정해지면 다음 단계 7로 한다.
2. **다른 탭 작업과의 순서** (권장: `public-listener`, `web-public-mode`, `browser-key-vault`는 다중 증권사 플랜의 `order-accounts`가 병합된 뒤 시작한다). 탭이 달라 `after`로 걸 수 없으니 오케스트레이터가 지킨다. 나머지 대기 작업과는 D25의 최소 변경으로 병렬로 둔다.
3. **다음 단계 1의 시작 시점** (권장: 다중 증권사 플랜의 `market-port-stream`과 `kis-orders`가 병합된 뒤). 먼저 하면 `kiwoom/`·`trading/`·`market/`을 두 플랜이 동시에 다시 짠다.
4. **한도 기본값** (D7a 표의 값으로 시작한다). 계정 버킷 초당 20·묶음 100, 전체 버킷 초당 200·묶음 400, 로그인 분당 30, 키움 경로 동시 2, 키움 경로 계정 분당 30, 보드 갱신 창당 새 종목 500, 스크리너 동시 2(스냅샷 뒤 해제). 모두 설정이라 다시 빌드하지 않고 바꾼다. 바꿀 근거는 D7b의 계수(`GET /api/public-usage`와 분 단위 로그)다.
5. **스크리너 스냅샷을 별도 플랜으로 빼는 것** (권장: 별도 플랜). 위 "스크리너 공용 스냅샷"의 이유대로다. 이 플랜에 넣으면 `market-port-rest`·`source-select-server`가 병합될 때까지 오케스트레이터가 그 작업을 손으로 붙잡아 둬야 한다.
