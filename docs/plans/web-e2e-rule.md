# web/를 고치는 작업이 관련 e2e를 돌리도록 저장소 규칙을 더한다

- 작성일: 2026-11-17
- 승인 시점의 기록이며 구현 중 바뀐 것은 반영하지 않는다.

## 사용자가 풀려는 문제

PR #450으로 전체 e2e가 chute의 머지 뒤 검사(`[[post_verify]]`)에서 빠졌다. batch `[[verify]]`에도 e2e가 없고 `preflight = "never"`다. 그래서 화면 PR이 다른 화면을 깨뜨려도 사용자가 전체 e2e를 수동으로 돌리기 전까지 아무도 모른다. 이 빈틈을 줄이려고 `web/`를 고치는 작업자가 관련 e2e spec을 직접 돌려 통과를 확인하게 하는 저장소 규칙을 더한다.

## 확정된 결정

- 규칙은 orch 절차가 아니라 이 저장소의 `AGENTS.md`에 둔다. orch는 전역 스킬이고, 작업자는 저장소 규칙을 `AGENTS.md`에서 읽는다.
- 넣을 뜻: "`web/`를 고치는 작업은 관련 e2e spec을 돌려 통과를 확인한다. 전체 e2e는 chute가 자동으로 돌리지 않는다(`docs/web-checks.md`)." 문구는 저장소 문체에 맞춘다.
- 관련 spec을 고르는 짧은 기준은 `docs/web-checks.md`에 둔다.
- 작업마다 전체 e2e를 돌리라고 하지 않는다. 전체 실행은 8분 이상 걸리고 PC 부하가 크다.
- 문서만 바꾼다. `chute.toml`, 시험, 코드는 건드리지 않는다.

## 스스로 정한 결정과 이유

- **규칙 줄은 `AGENTS.md`의 `## 개발 문서` 아래, "웹 검사·E2E·브라우저 진단 작업 전 …" 줄 바로 아래에 둔다.** 같은 문서를 가리키는 줄끼리 모여 있어야 작업자가 둘을 함께 읽는다. `AGENTS.md`에는 한 줄만 더하고, 고르는 기준은 `docs/web-checks.md`로 보낸다.
- **고르는 기준은 `docs/web-checks.md`의 `## E2E` 절, 전체 e2e 수동 실행 단락 근처에 둔다.** 그 단락이 "전체 e2e는 자동으로 돌지 않는다"를 이미 말하므로, 바로 이어서 "그래서 작업마다 관련 spec을 돌린다"를 적으면 이유와 규칙이 한자리에 있다.
- **기준은 spec이 화면을 겉에서 시험한다는 사실에 맞춘다.** `web/e2e/*.spec.ts`가 `../src/`에서 가져오는 것은 대부분 생성된 API 타입(`src/api/generated/*`), 차트 설정, 그리기 도우미 같은 모듈이고 화면 컴포넌트는 거의 없다. 그래서 import를 따라가는 방식(Playwright `--only-changed` 같은)으로는 컴포넌트 변경과 관련된 spec이 잡히지 않는다. 기준은 대략 이렇다: 고친 spec 자체, 고친 기능 영역 이름으로 된 spec(`drawing-*`, `financial-*`, `screener-*`, `chart-*` 등), 바뀐 화면의 문구·역할·`data-testid`를 쓰는 spec(`rg`로 찾는다), 공용 부품(헤더, 레이아웃, 설정, 공통 훅)을 고치면 그 부품을 거치는 주요 흐름 spec 몇 개. 정확한 문구와 예시는 작업자가 실제 spec 구성을 보고 정한다.
- **spec 여러 개를 한 번에 돌리는 명령 예시를 함께 적는다.** `python3 scripts/web.py e2e`는 인수를 Playwright로 그대로 넘기므로 파일 여러 개나 `--grep`을 받는다. 준비 단계(설치, WASM, 타입 검사, Vite 빌드)가 실행마다 한 번이니 spec을 나눠 여러 번 돌리지 말고 한 번에 넘기라고 적는다.
- **작업은 하나다.** 바뀌는 파일이 `AGENTS.md`와 `docs/web-checks.md` 둘이고 규칙과 기준을 함께 검토해야 뜻이 통한다.

## 범위 밖

- `chute.toml`(batch `[[verify]]`에 e2e를 넣거나 `preflight`를 바꾸는 일).
- e2e 시험, `scripts/web.py`, Playwright 설정.
- orch 절차 문서.
- 바뀐 파일로 관련 spec을 자동으로 골라 주는 도구.
- `docs/plans/`의 이전 계획 문서.

## 사용자가 정해야 하는 결정

1. **이 규칙을 지켰는지 확인할 방법을 둘지.** 이 플랜은 문서 규칙만 더하므로 작업자가 관련 spec을 돌리지 않아도 chute가 막지 않는다. 지킴을 강제하려면 PR 본문에 돌린 spec과 결과를 적게 하거나, 바뀐 파일로 spec을 골라 돌리는 검사를 chute에 넣는 별도 작업이 필요하다. 이번에는 하지 않는다.
2. **전체 e2e를 언제 돌릴지.** 관련 spec만으로는 먼 화면의 회귀를 놓칠 수 있다. 전체 실행 시점은 계속 사용자가 정한다(`docs/web-checks.md`의 수동 실행 명령).
