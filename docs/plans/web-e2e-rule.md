# 머지 뒤 e2e를 180분 간격으로 되살리고, web/ 작업이 관련 e2e를 돌리게 한다

- 작성일: 2026-11-17
- 승인 시점의 기록이며 구현 중 바뀐 것은 반영하지 않는다.

## 사용자가 풀려는 문제

PR #450으로 전체 e2e가 chute의 머지 뒤 검사(`[[post_verify]]`)에서 빠졌다. batch `[[verify]]`에도 e2e가 없고 `preflight = "never"`다. 그래서 화면 PR이 다른 화면을 깨뜨려도 사용자가 전체 e2e를 손으로 돌리기 전까지 아무도 모른다.

처음 요청은 `web/`를 고치는 작업자가 관련 e2e spec을 돌려 통과를 확인하게 하는 저장소 규칙이었다. 이어서 사용자가 머지 뒤 e2e를 다시 넣기로 했다. 사용자의 말(그대로): "post e2e 추가해줘". 오늘 문제는 간격 0으로 e2e가 쉬지 않고 돌아 PC 부하를 키운 것이었으므로, 되살리면서 시작 간격을 둔다.

## 확정된 결정

- `chute.toml`에 PR #450이 지운 `[[post_verify]] e2e` 단락을 되돌린다. `run`, `probe`, `timeout`, `failed`, `paths`는 `7d6d93c~1`의 것 그대로다.
- `post_verify_interval = 180`(분)을 더한다.
- `docs/web-checks.md`의 "전체 e2e는 … 자동으로 돌지 않는다" 단락을 고친다. 머지 뒤 검사가 180분 간격으로 기본 브랜치의 tip을 검사하고 실패하면 범인 머지를 찾아 알린다는 것을 적고, 그 사이에 손으로 돌리는 명령은 그대로 둔다.
- `web/`를 고치는 작업은 관련 e2e spec을 돌려 통과를 확인한다는 규칙을 `AGENTS.md`에 둔다. 머지 뒤 검사가 최대 몇 시간 늦게 돌기 때문에 여전히 필요하다. 문구는 "머지 뒤 검사는 몇 시간 간격으로만 돈다"는 뜻으로 쓴다. 규칙은 orch 절차가 아니라 이 저장소의 `AGENTS.md`에 둔다(orch는 전역 스킬이다).
- 관련 spec을 고르는 짧은 기준은 `docs/web-checks.md`에 둔다. 작업마다 전체 e2e를 돌리라고 하지 않는다(8분 이상, PC 부하).
- 규칙을 지켰는지 확인하는 장치는 따로 두지 않는다. 작업자 보고서에 돌린 spec이 남는다.
- 전체 e2e는 되살린 머지 뒤 검사가 돌린다.
- 시험과 코드는 건드리지 않는다.

## 스스로 정한 결정과 이유

- **설치된 chute(a64be36)로 미리 확인했다.** `7d6d93c~1`의 `chute.toml`에 `post_verify_interval = 180` 한 줄을 더한 임시 파일로 `chute config-check --file …`을 돌리니 종료 코드 0으로 "설정이 올바르다 … (검증 단계 6개)", "머지 뒤 검사 단계 1개 e2e · paths: web/, … · 시간 제한 1800초"가 나왔다.
- **간격의 뜻을 chute 문서대로 적는다.** chute README에 따르면 `post_verify_interval`은 머지 뒤 검사를 시작하는 최소 간격(분)이고 앞 검사를 시작한 때부터 센다. 검사는 tip이 마지막 통과 커밋이나 마지막 실패 커밋과 다를 때만 돌고, 사이 커밋을 하나씩 검사하지 않고 tip만 검사한다. 그래서 문서에는 "3시간마다 반드시 돈다"가 아니라 "앞 검사를 시작하고 180분이 지난 뒤 tip이 바뀌었으면 tip을 검사한다"는 뜻으로 적는다.
- **범인 찾기의 비용은 간격으로 줄지 않는다.** 진짜 실패하면 chute는 마지막 통과 커밋과 tip 사이의 머지를 이분 탐색하며 대략 log₂(머지 수)번 단계 전체를 더 돈다. 간격이 길면 그 사이 머지가 늘어 탐색 횟수가 조금 늘 수 있지만, 검사가 쉬지 않고 시작되던 부하는 사라진다. 사용자가 범인 찾기를 포함해 되살리기로 했으므로 이 동작은 바꾸지 않는다.
- **`post_verify_hold`는 적지 않는다(기본 false).** 켜면 머지 뒤 검사가 실패한 동안 그 단계의 `paths`에 걸리는 PR을 batch가 가져가지 않는다. 요청에 없고, 켜면 큐가 막히는 경우가 생긴다.
- **작업은 하나, PR 하나로 한다.** `AGENTS.md`의 새 문구와 `docs/web-checks.md`의 고친 단락은 머지 뒤 검사가 다시 돈다는 사실을 전제로 한다. 문서만 먼저 머지되면 사실과 다른 안내가 남는다. 바뀌는 파일은 `chute.toml`, `AGENTS.md`, `docs/web-checks.md` 셋이고 함께 검토해야 뜻이 통한다. `chute.toml`을 고치므로 PR은 chute에서 사람 승인을 기다린다.
- **`AGENTS.md`의 규칙 줄은 `## 개발 문서` 아래 "웹 검사·E2E·브라우저 진단 작업 전 …" 줄 바로 아래에 둔다.** 같은 문서를 가리키는 줄끼리 모여 있어야 작업자가 둘을 함께 읽는다. `AGENTS.md`에는 한 줄만 더하고 고르는 기준은 `docs/web-checks.md`로 보낸다.
- **고르는 기준은 `docs/web-checks.md`의 `## E2E` 절, 머지 뒤 검사 단락 바로 다음에 둔다.** "머지 뒤 검사는 몇 시간 간격으로만 돈다"는 이유와 "그래서 작업마다 관련 spec을 돌린다"는 규칙이 한자리에 있게 한다.
- **기준은 spec이 화면을 겉에서 시험한다는 사실에 맞춘다.** `web/e2e/*.spec.ts`가 `../src/`에서 가져오는 것은 대부분 생성된 API 타입(`src/api/generated/*`), 차트 설정, 그리기 도우미 같은 모듈이고 화면 컴포넌트는 거의 없다. 그래서 import를 따라가는 방식(Playwright `--only-changed` 같은)으로는 컴포넌트 변경과 관련된 spec이 잡히지 않는다. 기준은 대략 이렇다: 고친 spec 자체, 고친 기능 영역 이름으로 된 spec(`drawing-*`, `financial-*`, `screener-*`, `chart-*` 등), 바뀐 화면의 문구·역할·`data-testid`를 쓰는 spec(`rg`로 찾는다), 공용 부품(헤더, 레이아웃, 설정, 공통 훅)을 고치면 그 부품을 거치는 주요 흐름 spec 몇 개. 정확한 문구와 예시는 작업자가 실제 spec 구성을 보고 정한다.
- **spec 여러 개를 한 번에 돌리는 명령 예시를 함께 적는다.** `python3 scripts/web.py e2e`는 인수를 Playwright로 그대로 넘기므로 파일 여러 개나 `--grep`을 받는다. 준비 단계(설치, WASM, 타입 검사, Vite 빌드)가 실행마다 한 번이니 나눠 돌리지 말고 한 번에 넘기라고 적는다.

## 사용자가 정해야 하는 결정

1. **남아 있는 머지 뒤 검사 기록을 어떻게 할지.** 작성 시점 `chute status --json`의 `post_verify`는 마지막 통과 커밋 c995df4(#422), 실패 커밋 7a4db6c(`e2e/list-format.spec.ts:70`, 범인 #423, batch `b20261117-120342`)다. c995df4 뒤로 기본 브랜치에 머지가 24개 있다. chute 문서대로라면 되살린 뒤 첫 검사에서 tip이 같은 시험으로 실패하고 #423이 아직 기본 브랜치에 있으면 다시 찾지도 알리지도 않는다. 다른 시험으로 실패하면 c995df4와 tip 사이를 이분 탐색해 단계 전체를 대략 5번 더 돈다(전체 e2e 한 번 8분 이상). 이 PR이 머지되기 전에 #423의 실패를 고치거나 되돌리기(`chute revert b20261117-120342`)로 처리할지, 그대로 둘지 정한다. 이 플랜의 작업은 chute 상태를 건드리지 않는다.
