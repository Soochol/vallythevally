# 계정 로그인과 계정별 셋업 실행 플랜

작성일 2026-11-17. 승인 시점의 기록이며 구현 중 바뀐 것은 반영하지 않는다.

## 사용자가 풀려는 문제

지금 이 도구는 로그인이 없고, 사용자 자료는 `data/vally.db` 하나에 있다(ADR 0006). 사용자는 여러 사람이 각자 로그인해서 자기 셋업으로 쓰는 프로젝트로 바꾸고 싶어 한다. 사용자의 말은 다음과 같다.

1. "현재 프로젝트를 사용자 로그인하고, 사용자별로 셋업을 할수 있는 프로젝트로 리팩토링하고 싶어."
2. "사용자 키는 자기 pc에만 있고 / 모든 셋업은 사용자별로 다르고 / 그러면 모든 데이터는 키움 키 api로 각자 사용자 pc에서 가져와서 뿌려주는건가 ?"
3. "A, D안 비교"
4. "로그인은 google naver Oauth만 지원"

키움 키와 시세는 각 사용자 PC에 두고, 셋업만 우리 서버에 계정별로 둔다.

## 지금 코드의 사실 (기준 커밋 `1ffeb0c`)

- 앱 서버는 `crates/server`(바이너리 `vally-server`)다. 키움 연결, 시세 캐시, 실시간, 스크리너 일봉 저장소, 재무자료, 화면 파일 서빙을 모두 한 프로세스가 맡는다. 받는 주소는 루프백만 허용한다(`config.rs`의 `BindAddr`).
- 사용자 자료는 `crates/server/src/userdata.rs`와 `drawings.rs`가 SQLite(`VALLY_DB_PATH`, 기본 `data/vally.db`)에 읽고 쓴다. HTTP는 `user_routes.rs`(`/api/watchlists`, `/api/screens`, `/api/layouts`, `/api/layouts/{id}`, `/api/ui-state`)와 `drawings.rs`(`/api/drawings`, `/api/drawings/{id}`)다. 마이그레이션은 `crates/server/migrations/0001`~`0011`이다.
- 자료마다 `revision`이 있다. 저장할 때 `check_newer`가 보낸 revision이 저장된 값보다 크지 않으면 `stale_revision`으로 거절한다. 웹은 revision을 `Math.max(Date.now(), 이전 + 1)`로 만든다(`web/src/persist/saver.ts`). 그래서 revision은 사실상 밀리초 시각이고, 늦게 고친 쪽이 이긴다.
- 관심종목(그룹 포함), 조건식, 화면 상태는 서버에 하나씩 있다. 레이아웃과 드로잉은 id마다 하나씩 있다. 레이아웃과 드로잉 삭제는 지금 revision 없이 지운다. 알림은 아직 저장하지 않는다.
- 키움 키는 저장소 밖 키 파일(`kiwoom/key_file.rs`), 토큰은 토큰 파일(`kiwoom/token_file.rs`)에 있다. 두 파일 모두 `kiwoom/private_file.rs`의 규칙(디렉터리 700, 파일 600, 다른 사용자에게 열려 있으면 읽지 않음)을 따른다.
- `/api/system/*` 쓰기는 `system_routes.rs`의 `guard_writes`·`check_write`가 Content-Type, Host, Origin을 검사한다. 다른 쓰기 라우트에는 이 검사가 없다.
- 웹은 시작할 때 `web/src/persist/boot.ts`가 화면 상태, 레이아웃, 관심종목을 한 번 읽고, 그 뒤에는 자동 저장으로 서버에 쓴다. 서버가 사용자 자료가 바뀌었다고 알려 주는 메시지는 없다.
- E2E는 네이티브 서버 없이 애플리케이션 응답 고정값(`web/e2e/fixtures/scenario.ts`)으로 돈다(ADR 0016).
- 병합 검사(`chute.toml`)는 `clippy -p server -p hoga-format -p collector`, `cargo test -p server`, `cargo test -p hoga-format -p collector`, 웹 검사, 병합 뒤 E2E를 돌린다. 새 크레이트는 여기에 넣지 않으면 검사를 받지 않는다.

## 확정된 결정

사용자가 직접 정했거나 오케스트레이터와의 대화에서 확인했다.

1. 키움 키와 시세는 각 사용자 PC에 두고, 셋업만 계정 서버에 계정별로 둔다.
2. **시세는 사용자 PC에서만 다룬다.** 키움 키·토큰, 시세 캐시, 실시간, 스크리너 일봉 저장소, 지표 계산은 각 사용자 PC의 커넥터에만 둔다. 우리 서버는 시세를 거치거나 저장하지 않는다. 사용자 사이에 시세 캐시를 나누지 않는다. 키를 우리 서버에 보관하지 않는다.
3. **셋업은 우리 서버에 계정별로 둔다.** 관심종목·관심종목 그룹, 레이아웃·창, 드로잉, 조건식, 화면 상태를 계정 단위로 저장하고, 커넥터가 로컬 사본을 두고 동기화한다.
4. **로그인은 Google·Naver OAuth만** 지원한다. 비밀번호 로그인은 없다.
5. client secret과 callback은 계정 서버에만 둔다. 커넥터 로그인은 루프백 흐름으로 한다. 브라우저가 계정 서버 OAuth로 최상위 이동하고, 계정 서버가 `http://127.0.0.1:<포트>/auth/complete`로 일회용 코드를 넘기고, 커넥터가 그 코드를 장기 토큰으로 바꿔 저장소 밖 상태 파일(600)에 둔다.
6. 브라우저는 커넥터가 서빙하는 `127.0.0.1` 화면만 상대한다. 계정 서버와는 커넥터가 이야기한다.
7. 계정은 `(provider, subject)`로 식별한다. 이메일로 계정을 자동 연결하지 않는다.
8. 시험은 가짜 IdP를 주입한다. 실제 Google·Naver·키움은 호출하지 않는다.
9. 첫 실행 셋업 마법사의 순서는 로그인 → 키움 키 입력 → 공인 IP 확인과 포털 등록 확인 → 연결 → 기본 셋업이다. 키와 연결은 기존 `/api/system/kiwoom/*`를 쓴다.
10. 작업 순서는 ADR → 셋업 형식 → 계정 서버 → 커넥터 로그인 → 동기화 → 웹 로그인 화면과 마법사다.

## 스스로 정한 결정과 이유

사용자가 정할 결정(아래 절)도 권장안으로 구현을 시작할 수 있게 정했다. 사용자가 바꾸라고 하면 바꾼다.

### 구조

| # | 결정 | 이유 |
|---|---|---|
| D1 | 커넥터는 지금의 `crates/server`(`vally-server`)다. 새 바이너리를 만들거나 이름을 바꾸지 않는다. | 시세, 화면, 로컬 자료, 키 파일이 이미 다 이 프로세스에 있다. 커넥터가 할 일은 로그인과 동기화를 더하는 것뿐이다. |
| D2 | 계정 서버는 새 크레이트 `crates/account-server`(바이너리 `vally-account`)다. `server`·`collector`·`domain` 크레이트에 의존하지 않는다. | 키움 코드와 DuckDB가 계정 서버 바이너리에 들어가지 않는다. "계정 서버는 시세를 다루지 않는다"가 의존성 그래프로 보이고, `cargo tree`로 확인할 수 있다. |
| D3 | 두 쪽이 함께 쓰는 셋업 형식은 새 작은 크레이트 `crates/setup`에 둔다. serde 타입, 형식 버전, 크기 한도만 갖는다. | 계정 서버가 `server` 크레이트를 끌어오지 않고도 같은 타입을 쓴다. 형식이 바뀌면 두 쪽이 함께 컴파일 오류를 낸다. |
| D4 | 커넥터에 계정 서버 주소(`VALLY_ACCOUNT_SERVER_URL`)가 없으면 **로컬 전용 모드**다. 지금과 똑같이 로그인 화면 없이 돈다. 주소가 있으면 로그인해야 화면을 쓴다. | 개발, 기존 시험과 E2E, `verify-vally` 스킬이 그대로 산다. 계정 서버가 없는 사람도 쓸 수 있다. |
| D5 | 계정 서버 저장소는 SQLite와 sqlx다(ADR 0006과 같은 도구). 프로세스는 하나다. | 셋업은 계정당 수 MB, 쓰기는 사람 손 속도라 한 프로세스와 SQLite로 충분하다. 저장소 전체의 도구가 하나로 남는다. 운영 방식은 사용자가 정한다(아래 1번). |

### 로그인

| # | 결정 | 이유 |
|---|---|---|
| D6 | 루프백 흐름: 커넥터가 `state`와 PKCE(S256) 쌍을 만들고 브라우저를 계정 서버 `start`로 보낸다. 계정 서버는 IdP를 거쳐 돌아온 뒤 일회용 코드(60초, 한 번만, `code_challenge`에 묶음)를 만들어 `http://127.0.0.1:<포트>/auth/complete?code=…&state=…`로 보낸다. 커넥터는 `state`가 자기가 시작한 로그인인지 확인하고 `code_verifier`로 코드를 장기 토큰으로 바꾼다. | RFC 8252의 루프백 방식이다. `state` 확인이 남의 로그인 결과를 받는 일(로그인 CSRF)을 막고, PKCE가 다른 로컬 프로그램이 코드를 가로채도 쓰지 못하게 한다. |
| D7 | 계정 서버는 돌아갈 주소의 호스트를 `127.0.0.1`로 고정하고 포트(1024~65535)만 받는다. 다른 호스트나 경로로는 보내지 않는다. | 열린 리다이렉트를 구조로 막는다. RFC 8252는 `localhost`보다 IP 리터럴을 권한다. |
| D8 | 계정 서버는 `start`에서 `__Host-` 쿠키에 난수를 두고 IdP callback에서 같은 브라우저인지 확인한다. 쿠키는 로그인 흐름에만 쓰고 세션 쿠키는 없다. | 다른 사람이 시작한 흐름을 피해자 브라우저에서 끝내게 하는 공격을 계정 서버 쪽에서도 막는다. 브라우저는 계정 서버의 세션이 필요 없다(결정 6). |
| D9 | Google은 authorization code 흐름에 scope `openid`만 쓴다. id_token은 토큰 엔드포인트에서 TLS로 직접 받으므로 서명 대신 `iss`·`aud`·`exp`·`nonce`를 확인하고 `sub`만 쓴다. Naver는 접근 토큰으로 회원 프로필 API를 한 번 불러 `response.id`만 쓴다. IdP의 접근 토큰은 저장하지 않는다. | OpenID Connect Core 3.1.3.7은 토큰 엔드포인트에서 TLS로 직접 받은 id_token에 TLS 서버 검증을 서명 검증 대신 쓸 수 있게 한다. JWKS 관리가 없어진다. |
| D10 | IdP 엔드포인트 주소는 설정으로 바꿀 수 있다. 시험은 루프백 가짜 IdP 서버(Google형 authorize·token, Naver형 authorize·token·profile)를 띄우고 실제 어댑터 코드를 그대로 돌린다. | 키움 루프백 어댑터 시험과 같은 방식이다. 가짜 trait 구현만 시험하면 실제 HTTP 어댑터가 시험 밖에 남는다. |
| D11 | 커넥터 토큰은 32바이트 난수의 불투명 문자열이다. 계정 서버는 SHA-256 해시만 저장한다. 90일 동안 쓰지 않으면 만료하고, 로그아웃하면 폐기한다. 커넥터는 이 토큰을 `$XDG_STATE_HOME/vallythevally/account.json`(`VALLY_ACCOUNT_STATE_PATH`로 바꿈)에 `private_file` 규칙으로 둔다. | 키 파일과 같은 수준으로 다룬다(ADR 0004·0021). 계정 서버 DB가 새도 토큰을 쓸 수 없다. |
| D12 | 한 계정에는 identity가 하나다. 같은 사람이 Google과 Naver로 따로 들어오면 서로 다른 계정이다. 계정에 다른 provider를 붙이는 기능은 범위 밖이다. | 이메일 자동 연결을 하지 않으므로(결정 7) 붙이는 길은 로그인한 상태에서 명시적으로 하는 것뿐이고, 첫 구현에 필요하지 않다. |
| D13 | 계정 서버에 계정 삭제(`DELETE /v1/account`)를 둔다. identity, 토큰, 셋업을 모두 지운다. 커넥터는 로컬 사본을 지우지 않고 소유 표시만 지운다. | 로컬 사본은 사용자 PC의 자료다. |
| D14 | 커넥터의 새 쓰기 라우트(`/api/setup/*`, `/api/account/*`)는 `/api/system/*`와 같은 Content-Type·Host·Origin 검사를 받는다. `setup-format`이 `system_routes.rs`의 검사를 여러 라우트가 쓸 수 있게 꺼낸다. `GET /auth/complete`는 Host 검사와 `state` 일치로 막는다. | 로그인 없는 로컬 서버가 계정 토큰을 다루게 되므로 보호를 그대로 넓힌다. |
| D15 | 계정 서버 API는 커넥터만 부른다(서버 대 서버). CORS 헤더를 내지 않는다. 브라우저는 `start`와 IdP callback에만 최상위 이동으로 온다. | 브라우저가 계정 서버를 직접 부를 일이 없으면 다른 출처 문제가 생기지 않는다. |

### 셋업과 동기화

| # | 결정 | 이유 |
|---|---|---|
| D16 | 셋업은 **문서**의 모음이다. 문서는 `(종류, id)`로 구분한다. 종류는 관심종목·조건식·화면 상태(각 하나), 레이아웃·드로잉(id마다 하나)이다. 문서 본문은 지금 HTTP API 본문 JSON 그대로이고, 문서마다 revision과 삭제 여부를 갖는다. | 지금 저장 단위와 revision 규칙을 그대로 쓴다. 새 병합 규칙을 만들지 않는다. |
| D17 | 셋업 내보내기·가져오기(`GET /api/setup/export`, `PUT /api/setup/import`)를 먼저 만든다. 내보낸 묶음이 동기화가 주고받는 형식의 원형이다. 가져오기는 로컬 셋업 전체를 바꾸고, 기존 검증 함수(`check_watchlists` 등)를 통과한 것만 받는다. | 동기화 없이도 백업과 PC 옮기기에 쓸 수 있고, 형식을 동기화보다 먼저 시험으로 굳힌다. |
| D18 | 충돌은 문서 단위로 **revision이 큰 쪽이 이긴다**. 병합하지 않는다. 진 쪽 내용은 버린다. | 지금 로컬 저장 규칙(`check_newer`)과 같다. revision이 밀리초 시각이라 늦게 고친 쪽이 이긴다. 충돌은 두 PC를 동시에 오프라인으로 고칠 때뿐이다. 사용자가 바꿀 수 있다(아래 3번). |
| D19 | 삭제는 revision을 가진 삭제 표시로 남긴다. 레이아웃·드로잉 삭제 때 커넥터가 `max(저장된 revision + 1, 지금 밀리초)`를 매긴다. | 삭제 표시가 없으면 다른 PC가 지운 문서를 다시 올린다. |
| D20 | 계정 서버는 문서 본문을 해석하지 않는다. 종류, id 모양, 문서 크기, 계정 전체 크기만 검사한다. 커넥터가 받을 때 기존 검증 함수로 확인하고, 통과하지 못한 문서는 적용하지 않고 로그와 동기화 상태에 남긴다. | 계정 서버에 도메인 코드를 두지 않는다(D2). 잘못된 문서의 피해는 그 계정에만 간다. 종류가 닫혀 있으므로 계정 서버가 시세를 받을 길이 구조로 없다. |
| D21 | 문서 크기 한도는 지금 라우트 한도(`user_routes.rs`의 `LAYOUT_LIMIT`, `WATCHLISTS_LIMIT`, `JSON_LIMIT` 등)를 `crates/setup`으로 옮겨 두 쪽이 같이 쓴다. 계정 전체 한도는 32MB다. | 커넥터가 받는 것과 계정 서버가 받는 것이 같아진다. 무료 저장소를 다른 용도로 쓰는 일을 막는다. |
| D22 | 계정 서버는 계정마다 늘어나는 순번을 문서 쓰기에 매기고, 커넥터는 "이 순번 이후 바뀐 문서"를 받는다. | 전체를 매번 받지 않고, 놓친 변경 없이 이어 받는다. |
| D23 | 동기화 시점: 로그인 직후, 커넥터 시작 때(로그인돼 있으면), 로컬 쓰기 뒤 5초 모아 보내기, 5분마다 받기. 계정 서버에 닿지 못하면 최대 5분까지 늘려 가며 다시 시도한다. 그동안 화면은 로컬 사본으로 그대로 돈다. | 시세는 원래 로컬이라 계정 서버가 없어도 쓸 수 있어야 한다. |
| D24 | 받은 변경은 열린 화면을 바로 바꾸지 않는다. 커넥터가 WebSocket에 새 메시지 `setup_changed`를 보내고, 화면은 "다른 PC에서 바뀐 셋업이 있습니다"와 새로 고침 단추를 보인다. | 지금 웹은 시작 때 한 번 읽고 그 뒤에는 자기 편집만 쓴다. 편집 중인 레이아웃을 밑에서 바꾸면 자동 저장과 엉킨다. 기존 `hello`·`status` 모양은 바꾸지 않는다(시스템 설정 플랜 D9와 같은 이유). |
| D25 | 로컬 사본은 한 계정의 것이다. 커넥터 DB에 소유 계정을 적는다. 다른 계정으로 로그인하면 바로 바꾸지 않고, 화면이 "이 PC의 셋업은 다른 계정 것입니다"와 "지우고 바꾸기"를 보인다. 올리지 못한 변경이 있으면 그 수를 함께 보인다. | 다른 계정의 셋업이 섞여 올라가는 일을 막는다. 사본을 계정마다 따로 두면 실행 중에 DB를 바꿔 열어야 해서 복잡해진다. |
| D26 | 소유 계정이 없는 로컬 자료(지금의 `data/vally.db`)로 처음 로그인하면: 계정 셋업이 비어 있으면 로컬 자료를 올린다. 계정에도 셋업이 있으면 화면이 "이 PC 셋업 올리기"와 "계정 셋업 받기"를 묻는다. | 지금 쓰는 자료를 잃지 않는다. 사용자가 바꿀 수 있다(아래 5번). |
| D27 | 키움 키, 토큰, 등록 IP 기록, OpenDART 키, 스크리너 저장소, 재무자료 저장소는 셋업이 아니다. 내보내기와 동기화에 들지 않는다. | 결정 2. 시험으로 내보낸 묶음에 이 값들이 없음을 확인한다. |

## 작업과 순서

| 작업 | 내용 | 방식 | 방식의 이유 | 뒤에 |
|---|---|---|---|---|
| `adr-accounts` | ADR 0023·0024 새로 쓰기, 0006 대체 표시, 용어집 | `basic` | 문서만 고친다 | 없음 |
| `setup-format` | `crates/setup` 형식 크레이트, 커넥터 내보내기·가져오기 | `poteto` | 가져오기가 로컬 자료 전체를 바꾸고, 두 배포물이 함께 쓸 형식을 정한다 | 없음 |
| `acct-auth` | `crates/account-server` 골격, Google·Naver OAuth, 루프백 코드 교환, 토큰, 계정 삭제, 가짜 IdP 시험 | `poteto` | 인증과 보안, 새 배포물 설계 | 없음 |
| `acct-setup-api` | 계정 서버의 셋업 문서 API(쓰기 규칙, 순번, 한도) | `poteto` | 계정별 자료 저장과 삭제, 동시 쓰기 | `acct-auth`, `setup-format` |
| `conn-login` | 커넥터 계정 모드, 로그인 시작·완료, 로그아웃, 계정 상태 파일, 소유 계정, 상태 밀어 주기 | `poteto` | 인증 토큰 저장과 로컬 쓰기 보호 | `acct-auth`, `setup-format` |
| `conn-sync` | 로컬 동기화 기록과 삭제 표시, 보내기·받기 고리, 충돌 규칙, 첫 로그인 선택, `setup_changed` | `poteto` | 상태 저장·삭제, 동시성, 여러 모듈에 걸친 새 설계 | `conn-login`, `acct-setup-api` |
| `ui-login` | 로그인 화면, 계정 메뉴, 계정 바꾸기 확인, 로그아웃·삭제 | `poteto` | 인증 흐름과 계정 삭제를 다루는 화면 | `conn-login` |
| `ui-setup-wizard` | 첫 실행 마법사, 첫 로그인 셋업 선택, 동기화 상태 줄, 바뀐 셋업 알림 | `poteto` | 로컬·계정 셋업을 덮어쓰는 선택을 다룬다 | `ui-login`, `conn-sync` |

병렬: 처음에 `adr-accounts`, `setup-format`, `acct-auth`가 함께 돈다. `acct-auth`와 `setup-format`이 끝나면 `conn-login`과 `acct-setup-api`가 함께 돈다. `conn-login` 뒤에 `ui-login`이, `conn-login`과 `acct-setup-api` 뒤에 `conn-sync`가 함께 돈다. 마지막에 `ui-setup-wizard`가 돈다.

순차로 둔 이유:

- `acct-setup-api`는 `acct-auth`가 만든 크레이트 골격·DB·토큰 확인을 쓰고, `setup-format`의 문서 타입과 한도를 쓴다.
- `conn-login`의 시험은 `acct-auth`의 계정 서버를 같은 프로세스에 띄워 실제 계약으로 로그인한다. `setup-format`이 꺼낸 공용 쓰기 검사를 `/api/account/*`에 걸고, 같은 `api.rs`·`http.rs`·`crates/server/Cargo.toml`을 고친다.
- `conn-sync`는 `conn-login`의 계정 토큰·소유 계정과 `acct-setup-api`의 문서 API를 쓴다. 둘 다 `userdata.rs`와 커넥터의 계정 모듈을 다시 짠다.
- `ui-login`은 `conn-login`이 내보낸 생성 타입과 `/api/account/*`를 쓴다.
- `ui-setup-wizard`는 `ui-login`의 로그인 화면 자리와 계정 메뉴를 고치고, `conn-sync`의 동기화 상태와 첫 로그인 선택 API를 쓴다.

같은 파일에 몇 줄씩 더하는 곳(병렬, 각 지시서에 최소 변경으로 적었다):

- `Cargo.toml`(workspace members), `Cargo.lock`, `chute.toml`: `setup-format`과 `acct-auth`.
- `Cargo.lock`: `conn-login`(dev-dependency 추가)과 `acct-setup-api`.
- `web/src/api/generated/`의 계정 상태 타입: `conn-sync`가 필드를 더하고 `ui-login`이 읽는다. `conn-sync`는 더하기만 하고 상태 이름을 바꾸지 않는다.

## 다른 플랜과 겹치는 곳

이 플랜을 쓰는 시각에 같은 저장소에서 도는 작업은 없다. 방금 병합된 `ui-polish` 플랜(`docs/plans/ui-polish.md`)은 위 막대, 거래소 고르기, 관심종목, 도킹 탭을 고친다. 이 플랜의 화면 작업과는 `web/e2e/fixtures/scenario.ts`와 `docs/design-system.md` 정도만 겹칠 수 있어 순서를 두지 않는다. 화면 작업자는 그 파일들을 최소 변경으로 하고 PR 전에 최신 `main`으로 맞춘다. 승인 뒤 다른 작업이 `crates/server/src/userdata.rs`, `drawings.rs`, `web/src/persist/`를 고치면 `conn-sync`와 충돌한다. 오케스트레이터는 그 작업들을 `conn-sync` 앞이나 뒤로 줄 세운다.

## 범위 밖

- 계정 서버와 커넥터의 실제 배포: 호스팅, 도메인, TLS 리버스 프록시, 백업, OS별 설치본, 자동 업데이트. 사용자 결정(아래 1·6번) 뒤 별도 플랜으로 한다.
- Google·Naver 앱 등록과 실제 client id·secret. 사람만 할 수 있다(아래 2번).
- 휴대폰에서 쓰기. 커넥터가 PC에서만 돈다.
- 두 PC에서 동시에 열린 화면의 실시간 병합. 받은 변경은 새로 고침으로 보인다(D24).
- 한 계정에 provider 여럿 붙이기, 계정 사이 셋업 공유, 관리자 화면.
- 셋업 기록(이전 판 되돌리기), 진 쪽 문서 보관.
- 알림의 저장과 동기화(알림은 아직 저장하지 않는다).
- 호가 복기 수집기(ADR 0022), 재무자료와 스크리너 저장소의 공유.
- `/api/system/*`·`/api/setup/*`·`/api/account/*` 밖의 기존 쓰기 라우트에 Host·Origin 검사 넓히기.
- 실제 Google·Naver·키움에 접속하는 시험.

## 사용자가 정해야 하는 결정

구현을 막는 결정은 없다. 모든 작업은 권장안으로 시작하고, 실제 배포 전에 아래가 정해져야 한다.

1. **계정 서버 운영**: 어디에 띄울지(호스팅, 도메인), DB를 SQLite로 둘지 Postgres로 바꿀지. 권장은 작은 VM 하나에 TLS 리버스 프록시, SQLite, 매일 파일 백업이다(D5). Postgres로 바꾸려면 `acct-auth` 전에 알려 주어야 마이그레이션을 두 번 쓰지 않는다.
2. **Google·Naver 앱 등록**: Google Cloud OAuth 클라이언트와 Naver 개발자센터 앱을 만들고 callback 주소(`https://<도메인>/v1/auth/google/callback`, `…/naver/callback`)를 등록한다. 다른 사람이 로그인하려면 Google OAuth 동의 화면 게시와 Naver 검수가 필요할 수 있다(실제 콘솔에서 확인 필요).
3. **동기화 충돌 정책**: 권장은 문서 단위로 늦게 고친 쪽이 이기고 진 쪽은 버리는 것이다(D18). 진 쪽을 "충돌 사본"으로 남기길 원하면 `conn-sync` 범위가 커진다.
4. **오프라인일 때 커넥터 동작**: 권장은 한 번 로그인한 뒤에는 계정 서버 없이도 로컬 사본으로 계속 쓰고, 다시 닿으면 동기화하는 것이다(D23). 계정 서버 주소가 있는 커넥터의 첫 사용에는 로그인이 필요하다(D4).
5. **지금의 `data/vally.db` 옮기기**: 권장은 첫 로그인 때 계정이 비어 있으면 자동으로 올리고, 둘 다 있으면 묻는 것이다(D26).
6. **커넥터 배포 방식**: OS별 설치, 업데이트, 배포본의 기본 계정 서버 주소. 이 플랜은 소스 빌드만 다룬다.
