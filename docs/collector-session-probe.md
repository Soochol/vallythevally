# 한 IP에서 WebSocket 세션 수와 연속 토큰 발급 재기

[ADR 0026](adr/0026-collector-supervisor-collects-common-and-preferred-stocks.md)은 감독 데몬 하나가 수집 키 약 15개의 WebSocket 세션을 한 PC에서 여는 설계다. [플랜](plans/collector-build.md)은 그 전제 둘을 아직 재 보지 않았다.

- 한 공인 IP에서 세션 15개가 열리는가.
- `au10001`(토큰 발급)을 여러 키에 잇달아 불러도 되는가.

이 문서는 사용자가 장중에 직접 재는 절차다. 자동 시험과 자동 작업은 실제 키움을 부르지 않는다. 지금 있는 `collector collect --items`로 잰다. `collect`는 프로세스마다 자기 토큰을 받으므로 키마다 env 파일을 하나씩 두고 프로세스를 여러 개 띄우면 세션이 여러 개가 된다. 결과는 사람이 아래 표에 적고, ADR 0026의 "아직 정하지 않은 것"을 고쳐 채운다. 그 고침은 이 문서의 일이 아니다.

## 준비

키 하나의 준비 절차는 [`hoga-collector.md`](hoga-collector.md)의 "실제 수집 절차"를 따른다. 여기서는 키가 여러 개일 때 달라지는 것만 적는다.

1. **키 K개.** 지금 가진 수집 키를 모두 쓴다. 앱 서버의 `VALLY_KIWOOM_APP_KEY`는 넣지 않는다(같으면 `collect`가 시작하지 않는다).
2. **키마다 env 파일 하나, 권한 600.** 파일은 저장소 밖에 두고 절대 경로로 가리킨다. 키마다 토큰 파일과 잠금 파일 경로가 달라야 한다. 같으면 프로세스끼리 잠금과 토큰을 공유해 재려는 것이 재어지지 않는다.

   ```sh
   install -m 600 /dev/null ~/.config/probe/key1.env
   printf '%s\n' \
     'VALLY_COLLECTOR_APP_KEY=<1번 수집 키>' \
     'VALLY_COLLECTOR_APP_SECRET=<그 시크릿>' \
     "VALLY_COLLECTOR_TOKEN_PATH=$HOME/.local/state/probe/key1/token.json" \
     "VALLY_COLLECTOR_LOCK_PATH=$HOME/.local/state/probe/key1/collector.lock" \
     >> ~/.config/probe/key1.env
   install -d -m 700 ~/.local/state/probe/key1
   ```

   키 2, 3, …도 `key2.env`, `key2/`처럼 번호만 바꿔 같은 모양으로 만든다. 이 키들은 주문도 넣을 수 있는 실계좌 키다. 저장소, 이슈, 로그에 적지 않는다.
3. **키움 포털의 공인 IP 등록을 확인한다.** 지금 이 PC의 공인 IP가 등록돼 있어야 한다. 미등록이면 토큰 발급이 8050으로 거절된다.
4. **hoga-ops와 키가 겹치지 않는지 확인한다.** 돌고 있는 hoga-ops의 키(`KIWOOM_APP_KEY_2`~`5`)와 같은 키가 이 키들에 없어야 한다. 같은 키를 두 곳에서 쓰면 서로 연결을 끊어 세션이 끊긴 것이 이 실험 때문인지 알 수 없다. 수집기는 이것을 알 수 없으니 직접 대조한다.
5. **실행 파일을 빌드한다.** `cargo build --locked -p collector`. 자세한 것은 "실제 수집 절차"의 4번이다.
6. **종목을 키마다 나눈다.** 키마다 1~2개, 서로 겹치지 않게 정한다. 같은 종목을 두 세션에 등록하면 중복 수신과 세션 끊김이 섞여 읽기 어렵다.
7. **폴더를 만든다.** 로그와 데이터는 키마다 다른 폴더에 둔다.

   ```sh
   mkdir -p ~/probe/logs ~/probe/data/key1
   ```

## 순서

정규장(09:00~15:30)에 잰다. 시간 외에는 REAL 프레임이 거의 없어 세션이 살아 있는지 알기 어렵다.

키 수 N을 1, 2, 4, …, K로 늘린다. 각 단계에서 30분 이상 둔다. 발급 간격은 두 경우를 모두 잰다. 같은 N을 두 번 재려면 날을 달리하거나 모든 프로세스를 끄고 충분히 쉰 뒤 다시 한다. 두 경우를 같은 날 이어 재면 앞의 발급이 뒤의 결과에 영향을 줄 수 있으니 날짜 열에 적어 구분한다.

- **간격 5초**: 키마다 `collect`를 5초 간격으로 하나씩 띄운다.
- **간격 0초**: 한 단계의 프로세스를 거의 동시에 띄운다.

한 프로세스는 이렇게 띄운다. 키 번호 `i`만 바꾼다.

```sh
VALLY_COLLECTOR_ENV_FILE=$HOME/.config/probe/key1.env \
  target/debug/collector collect --data ~/probe/data/key1 --items 005930,000660 \
  > ~/probe/logs/key1.log 2>&1 &
```

로그는 표준 오류로 나오므로 `2>&1`로 파일에 모은다.

간격 5초로 N개를 띄우는 예다(키 1~4, 종목은 키마다 다르게 준다).

```sh
sleep 5
VALLY_COLLECTOR_ENV_FILE=$HOME/.config/probe/key2.env \
  target/debug/collector collect --data ~/probe/data/key2 --items 035720 \
  > ~/probe/logs/key2.log 2>&1 &
```

다음 단계로 넘어갈 때는 앞 단계의 프로세스를 끄지 않고 새 키를 더한다. 처음 띄우는 키는 토큰이 없어 `au10001`을 부르고, 이미 쓸 수 있는 토큰이 토큰 파일에 있으면 부르지 않는다. 그래서 발급 간격을 재려면 단계마다 새로 더하는 키의 토큰 파일이 없는 상태여야 한다. 간격 두 경우를 다시 재기 전에는 토큰 파일을 지운다.

각 프로세스는 SIGINT(Ctrl-C)나 SIGTERM으로 끈다.

## 볼 것

단계마다 30분 동안 다음을 본다. 로그는 `~/probe/logs/key<i>.log`, 원문은 `~/probe/data/key<i>/raw/<날짜>/`의 `.jsonl.zst`다. 원문은 `zstdcat`으로 읽는다. 줄 모양은 [`hoga-collector.md`](hoga-collector.md)의 "원문 파일"에 있다.

| 볼 것 | 어디서 | 뜻 |
|---|---|---|
| `수집을 시작합니다` | 각 로그 | LOGIN과 REG가 끝나 세션이 열렸다. 시각을 적는다 |
| LOGIN 거절 | 로그의 `LOGIN이 토큰 무효로 거절됐습니다`, 멈춤 메시지 `LOGIN이 거절돼 멈춥니다` | 세션 수 한도나 키 겹침일 수 있다. 거절 내용(`rejection`)을 그대로 적는다 |
| REG 거절 | 로그의 `REG가 … 거절돼 멈춥니다` | 등록 한도나 종목 문제. 세션 수와 직접 관계가 있는지 거절 내용으로 판단한다 |
| `down` 줄과 까닭 | 원문의 `{"event":"down","reason":"…"}` | 세션이 끊겼다. 까닭(닫힘 코드, 30초 무응답, 응답 시간 초과 등)과 `recv_ms`를 적는다 |
| 기존 세션의 끊김 | 새 키를 더한 시각 전후의 다른 프로세스 원문 | 새 세션이 열릴 때 이미 열려 있던 세션이 끊기는지 본다. 끊겼다면 몇 번째 세션을 더한 때인지 적는다 |
| 토큰 발급 거절 코드 | 로그의 토큰 오류, 멈춤 메시지 `토큰을 받지 못해 멈춥니다` | 8050, 8005 등 코드를 그대로 적는다 |
| 발급 간격 | 각 로그의 시작 시각과 토큰 발급 시각 | 키마다 발급이 몇 초 간격으로 나갔는지 적는다 |
| 현황 | 로그의 1분 현황 줄 | 세션마다 프레임이 계속 들어오는지 본다. 멈췄는데 `down`이 없으면 그것도 적는다 |

원문에서 `down`만 뽑아 보는 예다.

```sh
zstdcat ~/probe/data/key1/raw/*/*.jsonl.zst | grep '"event":"down"'
```

프로세스가 멈춤으로 끝났다면 종료 코드 1과 표준 오류의 까닭, 할 일을 함께 적는다. 멈춤의 종류와 할 일은 [`hoga-collector.md`](hoga-collector.md)의 "끝나는 경우와 종료 코드"에 있다. 멈춘 프로세스는 다시 띄우지 않고 그 단계를 실패로 적는다.

## 멈출 조건

**8050이 나오면 바로 모든 프로세스를 끄고 키움 포털을 확인한다.** 8050은 계정 단위 잠금일 수 있어 다른 키의 발급도 같이 막힌다. 더 띄우면 잠금이 길어진다. 포털에서 공인 IP 등록과 반복 발급 잠금 해제 여부를 확인하고, 풀린 것을 확인한 뒤에 다음 날 다시 시작한다.

그 밖에 다음에서도 그 단계에서 더 늘리지 않는다.

- LOGIN이나 REG가 거절돼 프로세스가 멈췄다.
- 새 세션을 더할 때마다 기존 세션이 끊긴다.
- 키가 겹쳤을 수 있다(원인을 모르는 연속 끊김). 키 겹침부터 다시 확인한다.

## 기록할 표

단계마다 한 줄을 적는다.

| 날짜 | 키 수 | 발급 간격 | 끊긴 세션 수 | 끊긴 시각 | 거절 코드 | 메모 |
|---|---|---|---|---|---|---|
| | | | | | | |

- 발급 간격은 5초, 0초 같은 값과 실제로 로그에서 읽은 간격을 함께 적는다.
- 끊긴 시각은 원문 `down` 줄의 `recv_ms`를 KST로 바꿔 적는다.
- 거절 코드가 없으면 `없음`이라고 적는다.

이 표를 채운 뒤 [ADR 0026](adr/0026-collector-supervisor-collects-common-and-preferred-stocks.md)의 "아직 정하지 않은 것"에서 "한 공인 IP에서 WebSocket 세션 15개가 되는지"와 "`au10001`을 여러 키에 연달아 불러도 되는지"를 실측값으로 고쳐 채운다. 세션이 15개에 못 미치면 같은 절에 적힌 대로 수집 PC를 나누는 쪽으로 정한다.
